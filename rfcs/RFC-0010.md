# RFC-0010: Generic Annotation Resource

- Status: Draft
- Category: Experimental Resource Type
- Version: 0.1
- Date: 2026-09-05
- Depends on: RFC-0004, RFC-0006, RFC-0008, RFC-0009
- Modifies OpenSmell Core 0.1: No

## 1. Summary

This RFC explores a generic Annotation resource for attaching
scheme-defined information to another OpenSmell resource.

The proposed resource type is:

```text
org.opensmell.annotation
```

with resource type version:

```text
0.1
```

An Annotation identifies:

1. itself as an OpenSmell resource;
2. the resource being annotated;
3. the versioned Scheme required to interpret the annotation data; and
4. the scheme-defined data itself.

The Annotation resource does not define the semantics of the data it
carries.

This RFC is experimental and non-normative.

---

## 2. Motivation

RFC-0004 defines a semantic annotation model capable of preserving
positive, negative, and unresolved semantic information.

For example, the scheme:

```text
org.opensmell.semantic.annotations
```

can distinguish:

```text
present
absent
unknown
```

instead of reducing semantic information to a positive-only descriptor
list.

RFC-0004 originally applies this scheme through an OpenSmell Core
Representation contained in an Odor document.

RFC-0008 subsequently introduced an experimental Generic ResourceGraph
capable of transporting independently identified resources and unknown
future resource types.

RFC-0009 then introduced an experimental Molecule resource representing
chemical identity independently from Odor, Stimulus, Observation, and
semantic annotation data.

These experiments expose a missing relationship.

A Molecule resource may need to carry associated semantic information,
but that information should not necessarily become part of the Molecule
resource itself.

Likewise, dataset semantic annotations are not necessarily experimental
Observations.

Creating artificial Observation resources merely to attach categorical
metadata would conflate annotation with measurement or observation.

The Generic Annotation resource explores a separate mechanism:

```text
Resource
   ^
   |
 subject
   |
Annotation
   |
   +-- Scheme
   |
   +-- data
```

This separates the identity of the annotated resource from the
scheme-defined information asserted about it.

---

## 3. Design Principle

The central design principle of this RFC is:

> An Annotation identifies what resource is being annotated and what
> versioned Scheme interprets the annotation data, without requiring the
> generic Annotation resource to understand those data.

Consequently:

- Annotation MUST NOT define universal odor categories.
- Annotation MUST NOT define universal measurement semantics.
- Annotation MUST NOT assume that its subject is a Molecule.
- Annotation MUST NOT assume that its subject is an Odor.
- Annotation MUST NOT require its subject to be locally resolvable.
- Annotation MUST NOT interpret scheme-defined data.
- Scheme-specific validation belongs outside the generic Annotation
  resource model.

---

## 4. Resource Type

The resource type identifier defined by this experiment is:

```text
org.opensmell.annotation
```

The resource type version defined by this experiment is:

```text
0.1
```

A serialized Annotation therefore contains:

```json
{
  "type": "org.opensmell.annotation",
  "type_version": "0.1",
  "id": "annotation-1",
  "subject": {
    "resource_id": "resource-1"
  },
  "scheme": {
    "id": "org.example.annotation-scheme",
    "version": "0.1"
  },
  "data": {}
}
```

---

## 5. Fields

### 5.1 `type`

`type` identifies the Resource Type.

For Annotation 0.1 it MUST be:

```text
org.opensmell.annotation
```

### 5.2 `type_version`

`type_version` identifies the version of the Annotation resource
contract.

For this RFC it MUST be:

```text
0.1
```

The Resource Type Version is distinct from the annotation Scheme
version.

For example:

```json
{
  "type": "org.opensmell.annotation",
  "type_version": "0.1",
  "scheme": {
    "id": "org.example.semantic",
    "version": "7"
  }
}
```

is conceptually valid.

`type_version` describes how to interpret the Annotation resource
structure.

`scheme.version` describes how to interpret `data`.

These version domains MUST NOT be conflated.

### 5.3 `id`

`id` is the OpenSmell Resource ID of the Annotation itself.

It MUST be a non-empty string.

The Annotation ID is independent from the Resource ID of its subject.

The current experiment does not impose stronger RFC-0006 Resource ID
syntax requirements.

### 5.4 `subject`

`subject` identifies the resource being annotated.

It uses the experimental OpenSmell Reference structure:

```json
{
  "resource_id": "molecule-1"
}
```

`subject` is REQUIRED.

Its `resource_id` MUST be a non-empty string.

Reference extension fields MAY be present and MUST be preserved by
conforming round-trip implementations.

The referenced resource does not need to occur in the same
GenericResourceGraph.

Unresolved references are therefore valid.

The Annotation resource does not constrain the Resource Type of its
subject.

A subject may therefore identify a Molecule or another present or future
OpenSmell resource.

### 5.5 `scheme`

`scheme` identifies the versioned rules required to interpret `data`.

It contains:

```json
{
  "id": "org.example.scheme",
  "version": "0.1"
}
```

Both `id` and `version` are REQUIRED non-empty strings.

Additional Scheme fields MAY be transported as extensions and MUST be
preserved by conforming round-trip implementations.

The generic Scheme model does not interpret the version string.

The generic Scheme model also does not require Scheme IDs to use the
RFC-0008 Resource Type namespace rules.

Scheme identifiers and Resource Type identifiers are distinct concepts.

### 5.6 `data`

`data` contains the scheme-defined annotation payload.

It MUST be a JSON object.

The generic Annotation resource MUST NOT interpret its contents.

The meaning and additional validation rules for `data` belong to the
Scheme identified by:

```text
scheme.id
scheme.version
```

An empty object is structurally valid at the generic Annotation layer:

```json
"data": {}
```

A specific Scheme MAY impose stronger requirements.

### 5.7 Extension fields

Additional fields MAY occur on an Annotation resource.

Unknown fields MUST be preserved by conforming round-trip
implementations.

The following names are reserved by Annotation 0.1 and cannot be used as
extension fields in the object model:

```text
type
type_version
id
subject
scheme
data
```

Extensions MAY also occur inside `subject` and `scheme`.

## 6. Generic Scheme

During the Annotation experiment, OpenSmell introduces an experimental
generic Scheme model consisting of:

```text
id
version
extra
```

Its purpose is to identify versioned interpretation rules for
scheme-defined data without coupling the Scheme to one particular
container.

Conceptually:

```text
Scheme
   |
   +-- id
   +-- version
   +-- extensions
```

The experimental Scheme introduced during this work remains separate
from the OpenSmell 0.1 Core Scheme model.

This RFC does not modify the Core.

RFC-0007 also contains the historical experimental `ResultScheme`
concept for Observation results. RFC-0007 deliberately kept that model
separate from the Core while its architecture was experimental.

RFC-0010 does not modify RFC-0007 and does not replace `ResultScheme`.

A future RFC may investigate whether Core Scheme, ResultScheme, and the
generic experimental Scheme should converge.

Such convergence is explicitly outside the scope of RFC-0010.

## 7. Relationship to RFC-0004

RFC-0004 defines:

```text
org.opensmell.semantic.annotations
```

version:

```text
0.1
```

as a semantic annotation interpretation scheme.

RFC-0010 does not redefine that scheme.

Instead, Annotation can transport RFC-0004-compatible data while
attaching it to a ResourceGraph resource.

For example:

```json
{
  "type": "org.opensmell.annotation",
  "type_version": "0.1",
  "id": "annotation-1",
  "subject": {
    "resource_id": "molecule-1"
  },
  "scheme": {
    "id": "org.opensmell.semantic.annotations",
    "version": "0.1"
  },
  "data": {
    "annotations": [
      {
        "value": "floral",
        "language": "en",
        "state": "present"
      },
      {
        "value": "spice",
        "language": "en",
        "state": "absent"
      }
    ]
  }
}
```

The Annotation resource itself does not know what `present` or `absent`
means.

Those semantics remain defined by the RFC-0004 scheme.

This distinction is important:

```text
Annotation
    = attachment mechanism

org.opensmell.semantic.annotations
    = interpretation rules
```

---

## 8. Relationship to Molecule

RFC-0009 defines the experimental resource type:

```text
org.opensmell.molecule
```

A Molecule represents chemical identity.

Semantic categories do not belong to the generic Molecule identity
contract merely because a particular dataset associates them with a
molecule.

Instead:

```text
Molecule
   ^
   |
 subject
   |
Annotation
```

allows chemical identity and semantic assertions to evolve
independently.

For example:

```json
{
  "format": "org.opensmell.experimental.generic-resource-graph",
  "version": "0.1",
  "resources": [
    {
      "type": "org.opensmell.molecule",
      "type_version": "0.1",
      "id": "molecule-1",
      "smiles": "CCO"
    },
    {
      "type": "org.opensmell.annotation",
      "type_version": "0.1",
      "id": "annotation-1",
      "subject": {
        "resource_id": "molecule-1"
      },
      "scheme": {
        "id": "org.opensmell.semantic.annotations",
        "version": "0.1"
      },
      "data": {
        "annotations": [
          {
            "value": "example",
            "language": "en",
            "state": "present"
          }
        ]
      }
    }
  ]
}
```

## 9. Annotation Is Not Observation

Annotation and Observation represent different concepts.

An Observation describes information obtained with respect to a
Stimulus and optionally an ObservationTarget.

An Annotation attaches scheme-defined information to a resource.

A dataset classification does not automatically become an Observation
merely because OpenSmell transports it.

For example, a source dataset asserting:

```text
molecule X -> floral = present
```

may be represented as an Annotation without inventing:

- a Stimulus;
- an ObservationTarget;
- experimental conditions; or
- an Observation event.

If the source data actually describe an experimental observation, the
Observation model may be appropriate instead.

The source semantics, rather than transport convenience, should
determine which resource model is used.

---

## 10. Unknown Schemes

The generic Annotation resource MUST NOT require prior knowledge of
every annotation Scheme.

For example:

```json
{
  "scheme": {
    "id": "org.example.future-annotation-model",
    "version": "93"
  },
  "data": {
    "future": {
      "payload": true
    }
  }
}
```

is structurally transportable.

An implementation may be unable to semantically validate or interpret
the payload while still preserving it.

This follows the broader OpenSmell extensibility principle that unknown
interpretation schemes should not make otherwise structurally valid
data untransportable.

---

## 11. Unknown Annotation Resource Versions

RFC-0008 distinguishes known and unknown Resource Type Versions.

An implementation registering:

```text
org.opensmell.annotation / 0.1
```

does not thereby understand:

```text
org.opensmell.annotation / 9.0
```

When transported through an RFC-0008 GenericResourceGraph, an unknown
future Annotation Resource Type Version should therefore remain
transportable as a GenericResource rather than being incorrectly parsed
using the Annotation 0.1 contract.

This behavior is part of RFC-0008 registry dispatch rather than
scheme-version dispatch.

---

## 12. Unresolved Subjects

Annotation subjects may be unresolved.

For example:

```json
{
  "type": "org.opensmell.annotation",
  "type_version": "0.1",
  "id": "annotation-1",
  "subject": {
    "resource_id": "external-resource-42"
  },
  "scheme": {
    "id": "org.example.scheme",
    "version": "0.1"
  },
  "data": {}
}
```

is valid even if:

```text
external-resource-42
```

does not occur in the same graph.

This permits annotations to reference externally managed or separately
transported resources.

---

## 13. Provenance

Annotation provenance is important because an annotation is an
assertion originating from some source.

This RFC does not yet define a normative provenance model.

Experimental provenance MAY be transported through extension fields.

For example:

```json
{
  "provenance": {
    "source": "OdorNet"
  }
}
```

The generic Annotation resource MUST preserve such extension data but
does not interpret it.

Future work may determine whether provenance requires a shared
OpenSmell model.

## 14. OdorNet Validation

The Annotation model was tested against the complete enriched OdorNet
dataset used by the OpenSmell experiments.

Each of the 8,892 dataset rows was converted into:

- one RFC-0009 Molecule resource; and
- one Annotation resource referencing that Molecule.

This produced:

```text
8,892 Molecule resources
8,892 Annotation resources
17,784 total resources
17,784 unique Resource IDs
106,704 semantic annotation states
```

The semantic states were:

```text
present: 13,442
absent:  77,457
unknown: 15,805
```

The graph was serialized, passed through strict JSON, parsed through the
RFC-0008 GenericResourceGraph registry, and serialized again.

The recovered graph contained:

```text
8,892 Molecules
8,892 Annotations
8,892 resolved Annotation subjects
106,704 recovered semantic states
```

Observed mismatches:

```text
SMILES:          0
InChIKey:        0
subject:         0
semantic state:  0
provenance:      0
resource type:   0
```

The recovered semantic-state totals exactly matched the source totals.

This experiment demonstrates that the proposed separation:

```text
Molecule
+
Annotation
+
Scheme
```

can transport the RFC-0004 semantic annotation information associated
with OdorNet molecules without placing semantic categories inside the
Molecule resource and without creating artificial Observation
resources.

The sequential Resource IDs used by this validation tool are
experiment-local identifiers and are not proposed as universal
Molecule or Annotation identity rules.

---

## 15. Forward Compatibility

Annotation 0.1 is designed around preservation rather than exhaustive
knowledge.

Conforming transport implementations should preserve:

- unknown Annotation extension fields;
- unknown Reference extension fields;
- unknown Scheme extension fields;
- unknown Scheme identifiers;
- unknown Scheme versions;
- opaque scheme-defined `data`.

RFC-0008 remains responsible for transport of unknown Resource Types
and unknown Resource Type Versions.

---

## 16. Non-Goals

RFC-0010 does not define:

- a universal odor vocabulary;
- a universal semantic taxonomy;
- a universal annotation payload;
- a universal provenance model;
- a confidence model;
- chemical identity;
- molecule equivalence;
- experimental observations;
- measurements;
- stimuli;
- observation targets;
- rendering instructions;
- diffuser commands;
- physical odor reproduction;
- normative Resource ID generation;
- normative Scheme ID syntax;
- Scheme version ordering;
- Scheme version compatibility rules;
- convergence with Core Scheme;
- convergence with RFC-0007 ResultScheme.

---

## 17. Security and Robustness Considerations

Annotation data and extensions are open-ended JSON structures.

Implementations should therefore consider:

- deeply nested payloads;
- very large arrays or objects;
- duplicate semantic information defined by a particular Scheme;
- untrusted extension data;
- unresolved references;
- unknown Schemes;
- future Resource Type Versions.

The generic Annotation parser should validate only the structural
contract it understands.

Scheme-specific semantic validation should occur separately.

Strict JSON serialization should reject non-standard numeric values such
as NaN and Infinity when Annotation resources are transported through
the RFC-0008 GenericResourceGraph JSON serialization layer.

---

## 18. Proposed Portable Conformance Work

Before Annotation 0.1 can be considered for promotion beyond Draft, the
following portable evidence should be produced:

1. an experimental JSON Schema for Annotation 0.1;
2. language-independent structural conformance vectors;
3. preservation vectors for Annotation, Reference, and Scheme
   extensions;
4. Python schema/parser agreement tests;
5. an independent JavaScript structural verifier;
6. cross-language preservation checks;
7. RFC-0008 interoperability vectors containing Molecule, Annotation,
   unknown Resource Types, and unknown Annotation Resource Type
   Versions;
8. regression validation against the complete OdorNet experiment.

The portable vectors should distinguish structural Annotation
validation from Scheme-specific semantic validation.

For example, a structurally valid Annotation using an unknown Scheme
must remain valid at the Annotation layer.

---

## 19. Open Questions

The experiment intentionally leaves several questions unresolved:

1. Should the generic experimental Scheme eventually replace or
   converge with RFC-0007 ResultScheme?
2. Should the generic experimental Scheme eventually converge with the
   OpenSmell Core Scheme?
3. Should Annotation support more than one subject?
4. Should provenance become a shared structured OpenSmell concept?
5. Should Annotation itself carry external identifiers?
6. Should annotations be allowed to target another Annotation?
7. Are additional relationship semantics required beyond `subject`?
8. Should future specifications define a generic mechanism for
   scheme-specific validation registration?
9. Should a future graph layer expose generic reference discovery for
   resource types such as Annotation?
10. Which independent datasets should be used to validate Annotation
    beyond OdorNet?

These questions should be informed by real interoperability needs rather
than resolved solely for API symmetry.

---

## 20. Current Recommendation

Keep Annotation experimental.

The current evidence supports the architectural distinction between:

```text
resource identity
annotation attachment
scheme-defined interpretation
```

and demonstrates successful lossless transport on a real dataset.

However, one dataset and one primary annotation Scheme are not
sufficient evidence to make the resource normative.

The next step is portable structural conformance and cross-language
interoperability testing while preserving the ability to revise the
model incompatibly.
