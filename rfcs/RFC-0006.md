# RFC-0006: Resource Identification and Deterministic Source Identity

- Status: Draft
- Target: Future OpenSmell version
- Last updated: 2026-09-03

## 1. Abstract

This RFC proposes an experimental resource-identification architecture for
OpenSmell.

The model distinguishes:

1. OpenSmell Resource IDs;
2. external identifiers;
3. source identities;
4. references;
5. representation scheme identifiers.

OpenSmell Resource IDs are opaque UUIDs.

Two generation modes are currently explored:

- UUIDv4 for newly created resources without deterministic source identity;
- UUIDv5 for deterministic resources imported from external datasets.

Deterministic UUIDv5 generation is based on structured source identity
serialized into canonical generation material.

The current experiment supports both atomic and composite source identities.

Composite source-identity member names are restricted to canonical ASCII
structural role names. Source-identity values remain Unicode strings and are
preserved exactly without implicit Unicode normalization.

This RFC does not modify OpenSmell 0.1 and remains experimental.


## 2. Motivation

OpenSmell needs stable identifiers for resources such as:

- odors;
- molecules;
- stimuli;
- observations;
- measurement targets;
- future device-independent resources.

Existing datasets use heterogeneous identifiers.

Examples include:

- PubChem CIDs;
- dataset-specific stimulus identifiers;
- subject identifiers;
- ROI identifiers;
- compound names;
- locally generated identifiers.

These identifiers belong to different namespaces and have different
semantics.

Using them directly as OpenSmell Resource IDs would couple OpenSmell identity
to external systems and make cross-dataset graph construction difficult.

OpenSmell therefore needs its own resource identity layer while preserving
source identifiers separately.


## 3. Scope

This RFC addresses:

- OpenSmell Resource IDs;
- UUID textual representation;
- random Resource ID generation;
- deterministic Resource ID generation;
- structured source identity;
- canonical generation material;
- external identifier preservation;
- reference behavior;
- unresolved references;
- identity stability;
- cross-language interoperability.

This RFC does not define:

- universal molecule identity;
- chemical equivalence;
- odor equivalence;
- stimulus equivalence;
- observation equivalence;
- deduplication algorithms;
- global dataset registries;
- dereferenceable network identifiers;
- physical rendering identifiers.


## 4. Terminology

### 4.1 Resource

An identifiable OpenSmell object.

Examples may include a molecule, stimulus, observation, target, or odor.

### 4.2 Resource ID

An opaque identifier assigned to an OpenSmell resource.

### 4.3 External identifier

An identifier assigned by an external system.

Example:

```json
{
  "scheme": "pubchem.cid",
  "value": "240"
}
```

### 4.4 Source identity

Dataset-local identity information used to identify the source object from
which an OpenSmell resource was created.

### 4.5 Atomic source identity

A source identity represented by one string.

Example:

```json
"113L_038"
```

### 4.6 Composite source identity

A source identity consisting of multiple named structural components.

Example:

```json
{
  "stimulus": "1001_3.12e-13",
  "target": "111L_001"
}
```

### 4.7 Reference

A value that points to another OpenSmell Resource ID.

### 4.8 Scheme identifier

An identifier defining interpretation rules for a representation.

Example:

```text
org.opensmell.perceptual.measurements
```

Scheme identifiers are not Resource IDs.


## 5. Identification Layers

OpenSmell distinguishes multiple identification layers.

### 5.1 Scheme identifiers

Scheme identifiers identify interpretation rules.

Example:

```text
org.opensmell.semantic.descriptors
```

### 5.2 OpenSmell Resource IDs

Resource IDs identify OpenSmell resource instances.

Example:

```text
f485e819-2af5-502a-9489-4554ec11716c
```

### 5.3 External identifiers

External identifiers preserve identifiers assigned by external systems.

Example:

```json
{
  "scheme": "pubchem.cid",
  "value": "240"
}
```

### 5.4 Source identities

Source identities preserve dataset-local identity used during deterministic
import.

Example:

```json
{
  "stimulus": "1001_3.12e-13",
  "target": "111L_001"
}
```

These layers MUST NOT be treated as interchangeable.


## 6. Resource ID Requirements

A future OpenSmell Resource ID system should provide:

- uniqueness within the relevant OpenSmell graph;
- practical global collision resistance;
- offline generation;
- stability;
- opacity;
- external-system independence;
- referenceability;
- round-trip preservation;
- cross-language reproducibility for deterministic generation.


## 7. UUID Candidate

The current experimental Resource ID format is UUID.

UUID is defined by RFC 9562.

RFC 9562 supersedes RFC 4122.

UUIDs provide:

- 128-bit identifiers;
- offline generation;
- established textual representation;
- widespread library support;
- multiple generation strategies.

This RFC currently explores UUIDv4 and UUIDv5.


## 8. UUID Textual Representation

The experimental OpenSmell canonical UUID representation is:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

using lowercase hexadecimal characters.

Example:

```text
f485e819-2af5-502a-9489-4554ec11716c
```

RFC 9562 permits uppercase and lowercase hexadecimal characters in textual
UUID representations.

OpenSmell experimentally requires lowercase canonical form to reduce
representational ambiguity.

The current validator validates canonical UUID syntax and does not restrict
the UUID version.

Producer generation policy and accepted UUID syntax are intentionally
separate concerns.


## 9. UUIDv4 Generation

Resources created without deterministic source identity may receive a
UUIDv4.

Example Python implementation:

```python
from uuid import uuid4

resource_id = str(uuid4())
```

UUIDv4 generation is appropriate when identity does not need to be
reconstructed independently from source data.


## 10. UUIDv5 Deterministic Generation

Resources imported from datasets may need stable identifiers across
independent imports.

The current experiment uses UUIDv5.

Conceptually:

```text
UUIDv5(namespace, canonical_generation_name)
```

The same:

- namespace;
- dataset identity;
- resource type;
- source identity;
- canonical serialization

produces the same Resource ID.


## 11. Experimental UUID Namespace

The current experimental namespace is:

```text
7f0f1d72-83c7-4f57-a1f6-4bc43bb26e58
```

This namespace is fixed only for experimental reproducibility.

It MUST NOT become the permanent OpenSmell namespace accidentally.

A future standards decision MUST explicitly decide whether to:

- retain it;
- replace it;
- define multiple namespaces;
- define a formal namespace allocation mechanism.


## 12. Deterministic Identity Model

The deterministic generation model currently uses three logical components:

```text
dataset
resource_type
source_identity
```

These components are structurally encoded before UUIDv5 generation.

Metadata that does not define source identity MUST NOT affect deterministic
Resource ID generation.


## 13. Atomic Source Identity

A resource may have a single source identifier.

Example:

```text
113L_038
```

Its source identity is represented directly as a string:

```json
"113L_038"
```

The corresponding canonical generation structure is conceptually:

```json
{
  "dataset": "burton_2022",
  "resource_type": "target",
  "source_identity": "113L_038"
}
```


## 14. Composite Source Identity

Some source resources are identified by multiple components.

For example, an observation may be uniquely identified by:

```text
stimulus + target
```

Its source identity is represented structurally:

```json
{
  "stimulus": "1001_3.12e-13",
  "target": "111L_001"
}
```

This structure preserves component boundaries explicitly.


## 15. Rejected Delimiter-Based Identity Encoding

An earlier experiment used generation names such as:

```text
dataset:resource_type:source_id
```

This encoding is ambiguous.

For example:

```text
dataset = abc:def
resource_type = target
source_id = 123
```

and another logical decomposition could produce the same flattened string.

This is a serialization ambiguity, not a UUID cryptographic collision.

Delimiter concatenation is therefore rejected for deterministic structured
identity.


## 16. Rejected Flattened Composite Identity

An intermediate experiment encoded observation identity as:

```text
stimulus|target
```

This has the same structural ambiguity.

For example:

```text
stimulus = a|b
target = c
```

and:

```text
stimulus = a
target = b|c
```

would collapse to the same flattened text.

Composite source identity MUST therefore preserve component structure.


## 17. Experimental Canonical Generation Algorithm

The current experimental algorithm is:

1. validate `dataset`;
2. validate `resource_type`;
3. validate `source_identity`;
4. construct an object containing exactly:

```text
dataset
resource_type
source_identity
```

5. serialize the object using the experimental canonical JSON rules;
6. encode the resulting text as UTF-8;
7. generate UUIDv5 using the experimental namespace.

No additional metadata participates in generation.


## 18. Canonical Serialization

The current Python prototype is equivalent to:

```python
json.dumps(
    payload,
    sort_keys=True,
    separators=(",", ":"),
    ensure_ascii=False,
)
```

However, this Python expression alone is NOT the definition of
cross-language canonicalization.

The interoperability profile additionally constrains the source-identity data
model so that different language runtimes cannot legitimately produce
different member ordering for supported composite source identities.

The current experimental rules are:

- no insignificant whitespace;
- top-level member names are fixed by the algorithm;
- composite source-identity member names are sorted deterministically;
- composite member names use the restricted ASCII structural-key grammar
  defined in Section 21;
- Unicode values are serialized directly when JSON permits;
- JSON-required escaping is preserved;
- Unicode normalization is not performed implicitly;
- lone Unicode surrogate code points are rejected.

These restrictions are part of the canonicalization model and not merely
implementation details.


## 19. UTF-8 Generation Octets

The canonical generation string is encoded as UTF-8 before UUIDv5
generation.

Conceptually:

```text
structured identity
        ↓
canonical JSON text
        ↓
UTF-8 octets
        ↓
UUIDv5
```

Cross-language interoperability therefore requires agreement on both:

- canonical text;
- UTF-8 octets.


## 20. UUIDv5 Generation

UUIDv5 is generated using:

```text
namespace UUID
+
canonical generation name
```

The current experimental namespace is:

```text
7f0f1d72-83c7-4f57-a1f6-4bc43bb26e58
```

The canonical generation name is encoded as UTF-8 according to the rules in
this RFC before being supplied to the UUIDv5 algorithm.

UUIDv5 uses SHA-1 as specified by RFC 9562.

The use of UUIDv5 here is for deterministic identity generation, not for
security-sensitive hashing.


## 21. Current Source-Identity Constraints

The current experimental `source_identity` type is:

```text
string
OR
map<string, string>
```

An atomic source identity MUST be:

- a non-empty string;
- composed only of Unicode scalar values.

A composite source identity MUST:

- be non-empty;
- contain string keys;
- contain string values;
- contain non-empty values;
- use keys matching:

```text
^[a-z][a-z0-9_.-]*$
```

Composite keys are therefore restricted to lowercase ASCII structural role
names.

Examples of valid keys include:

```text
stimulus
target
subject
source_id
source-id
source.id
field1
a.b-c_d9
```

Examples of invalid keys include:

```text
Target
1target
target name
é
咖
😀
```

The restriction applies to structural member names only.

Composite values remain Unicode strings.

Nested mappings, arrays, numbers, booleans, and null values are not currently
allowed inside `source_identity`.


## 22. External Identifiers

External identifiers SHOULD be preserved separately from OpenSmell Resource
IDs.

A provisional structure is:

```json
{
  "id": "f485e819-2af5-502a-9489-4554ec11716c",
  "identifiers": [
    {
      "scheme": "pubchem.cid",
      "value": "240"
    }
  ]
}
```

`pubchem.cid` is illustrative and not normative in this RFC.

External identifier values are represented as strings to avoid imposing
external identifier semantics on the OpenSmell core.


## 23. Source Identity Preservation

When deterministic identity is derived from source data, the original source
identity SHOULD remain preservable.

For example:

```json
{
  "id": "f485e819-2af5-502a-9489-4554ec11716c",
  "source_identity": "113L_038"
}
```

or:

```json
{
  "id": "6136624f-5105-52f1-875e-53a177ef2134",
  "source_identity": {
    "stimulus": "1001_3.12e-13",
    "target": "111L_001"
  }
}
```

The generated Resource ID does not replace source provenance.


## 24. References

References between OpenSmell resources SHOULD use OpenSmell Resource IDs.

Example:

```json
{
  "stimulus": "11111111-2222-4333-8444-555555555555"
}
```

References are opaque.

Consumers SHOULD NOT infer semantic meaning from UUID contents.


## 25. Unresolved References

Structural preservation and reference resolution are separate concerns.

An unresolved reference MUST NOT automatically require:

- deleting the resource;
- inventing metadata;
- rewriting the identifier;
- assuming a source error.

A parser or importer may preserve unresolved references and report them
separately.

This behavior is important for imperfect scientific datasets.


## 26. Identity and Equality

Resource identity does not imply semantic equality.

Two resources may contain identical data but have different Resource IDs.

Likewise, two resources may refer to the same external entity while
representing different OpenSmell resources.


## 27. Identity and Content

Deterministic Resource IDs SHOULD be based on identity-defining source
information rather than mutable descriptive metadata.

For example, changing:

- labels;
- descriptions;
- annotations;
- provenance notes

SHOULD NOT automatically change a deterministic Resource ID unless those
fields are explicitly part of the source identity definition.


## 28. Dataset Identity

Dataset identity participates in deterministic generation.

Therefore:

```text
same source identity
+
different dataset
=
different Resource ID
```

This prevents accidental identity collapse across independent source
datasets.


## 29. Dataset Revisions

The current experiment treats dataset revision metadata separately from
dataset identity.

A metadata-only revision therefore does not necessarily change Resource IDs.

This remains an open design area.

Future OpenSmell versions may need to distinguish:

- dataset family identity;
- release identity;
- revision identity;
- immutable snapshot identity.


## 30. Resource Type Isolation

Resource type participates in deterministic generation.

Therefore:

```text
dataset = example
source_identity = 123
resource_type = molecule
```

and:

```text
dataset = example
source_identity = 123
resource_type = stimulus
```

produce different Resource IDs.

This prevents cross-type identity collapse.

## 40. Composite Identity Experiment

All 187,748 Burton observations were generated using composite source

No observation required delimiter-based identity concatenation.

## 41. Identity Stability Experiment

The following changes were tested independently.

Changing descriptive metadata while preserving:

```text
dataset
resource_type
source_identity
```

preserved the Resource ID.

Changing the dataset changed the Resource ID.

Changing the resource type changed the Resource ID.

Changing the source identity changed the Resource ID.

Repeated generation from identical identity material produced the same
Resource ID.


## 42. Structural-Boundary Experiments

Delimiter ambiguity was explicitly tested.

The identities:

```json
{
  "stimulus": "a|b",
  "target": "c"
}
```

and:

```json
{
  "stimulus": "a",
  "target": "b|c"
}
```

produce different canonical generation material and different UUIDs.

This confirms that structural encoding preserves identity boundaries.

## 44. Cross-Language Canonicalization Experiment

Independent Python and JavaScript implementations were used to reproduce
canonical generation material and UUIDv5 Resource IDs.

Initial tests using only Basic Multilingual Plane composite keys appeared to
confirm interoperability.

A later adversarial experiment compared the composite keys:

```text
U+E000
U+1F600
```

Python sorted them as:

```text
U+E000
U+1F600
```

while JavaScript's standard string ordering produced:

```text
U+1F600
U+E000
```

The resulting canonical JSON strings and UTF-8 octets differed.

This demonstrated that an underspecified rule such as "sort Unicode strings
lexicographically" is not sufficient for language-independent
canonicalization.

The difference is caused by runtime string-order semantics:

- Python ordering follows Unicode code-point ordering for these strings;
- JavaScript standard string ordering operates on UTF-16 code units.

The experiment directly motivated the ASCII structural-key restriction in
this RFC.

The experiment is retained in:

```text
tools/analyze_unicode_key_ordering.py
tools/analyze_unicode_key_ordering.js
```

as evidence for the design decision.

## 47. Cross-Language Interoperability Requirements

A conforming implementation of the current experimental deterministic
generation profile must reproduce the same:

```text
structured source identity
        ↓
canonical text
        ↓
UTF-8 octets
        ↓
UUIDv5
```

for the supported data model.

Implementations MUST NOT depend on implementation-specific ordering of
arbitrary Unicode object member names.

Composite source-identity member names MUST instead follow the ASCII
structural-key grammar:

```text
^[a-z][a-z0-9_.-]*$
```

This makes ordering portable across the tested Python and JavaScript
implementations and substantially reduces canonicalization complexity for
future implementations.


## 48. UUIDv5 and Canonical Names

UUIDv5 determinism depends entirely on exact generation-name octets.

Therefore, UUIDv5 alone does not solve interoperability.

If two implementations serialize logically identical source identity
differently, they will produce different UUIDs.

Canonical generation material is therefore part of the identity algorithm,
not an incidental implementation detail.

This requirement is consistent with RFC 9562's name-based UUID model, in
which the name used for UUID generation requires a canonical sequence of
octets.


## 49. Security Considerations

Resource IDs are identifiers, not authentication tokens.

Applications MUST NOT treat knowledge of a Resource ID as authorization.

UUIDv5 uses SHA-1 because that algorithm is part of the UUIDv5 definition.

The current use does not depend on SHA-1 collision resistance for
cryptographic security.

Nevertheless, future OpenSmell versions may evaluate other UUID generation
strategies, including UUIDv8-based custom schemes, if stronger hash
properties or different canonicalization requirements become necessary.


## 50. Privacy Considerations

Deterministic identifiers can reveal that two resources originated from the
same identity material when the generation namespace and algorithm are known.

Source identifiers may also contain sensitive information.

Implementations SHOULD avoid embedding personally identifying information
directly into source identities when a safer stable source identifier is
available.

OpenSmell Resource IDs themselves SHOULD remain opaque.


## 51. Current Experimental Invariants

The current prototype enforces or tests the following invariants:

1. Resource IDs use canonical lowercase UUID textual syntax.
2. Resource ID syntax validation does not currently restrict UUID version.
3. UUIDv4 is used for experimental random generation.
4. UUIDv5 is used for experimental deterministic generation.
5. Deterministic generation uses a fixed experimental namespace.
6. Dataset identity participates in generation.
7. Resource type participates in generation.
8. Source identity participates in generation.
9. Metadata outside source identity does not participate in generation.
10. Atomic source identity is supported.
11. Composite source identity is supported.
12. Composite identity preserves structural boundaries.
13. Composite keys use lowercase ASCII structural role names.
14. Composite keys match `^[a-z][a-z0-9_.-]*$`.
15. Composite values preserve Unicode scalar values.
16. Unicode normalization is not implicit.
17. Lone Unicode surrogate code points are rejected.
18. Canonical generation text is encoded as UTF-8.
19. Python and JavaScript reproduce the current 17 golden vectors.
20. Unresolved source references may be preserved.
21. Source identity remains distinct from OpenSmell Resource ID.


## 52. Open Questions

The following questions remain unresolved.

### 52.1 Permanent namespace

Should OpenSmell define one permanent UUID namespace or multiple namespaces?

### 52.2 UUID generation versions

Should future OpenSmell versions formally permit:

- UUIDv4;
- UUIDv5;
- UUIDv7;
- UUIDv8;
- other UUID variants?

### 52.3 Nil and Max UUID

Should Nil UUID and Max UUID be accepted as Resource IDs?

The current syntax validator may accept canonical UUID values regardless of
generation version.

A future specification should decide this explicitly.

### 52.4 Dataset registry

Should dataset identities eventually use registered names?

### 52.5 Dataset revisions

When should a dataset revision create new deterministic Resource IDs?

### 52.6 External identifier registry

Should schemes such as:

```text
pubchem.cid
cas.rn
```

be standardized by OpenSmell?

### 52.7 Unicode value policy

The current experiment preserves Unicode values exactly and performs no
implicit normalization.

This means a precomposed string such as:

```text
café
```

and an equivalent-looking decomposed Unicode sequence remain distinct
identity material.

A future RFC must decide whether this exact-preservation policy becomes
normative.

### 52.8 Canonical JSON standard

Should OpenSmell eventually adopt an external canonical JSON specification
instead of maintaining a deliberately constrained internal profile?

### 52.9 Resource graph namespace

Should all resource types share one Resource ID namespace, or should some
future resource categories use separate namespaces?

The current experiment favors one resource graph namespace with resource type
included in deterministic generation.

### 52.10 Dataset-local identity semantics

Who defines which fields constitute source identity for a particular dataset?

The current model assumes that an importer knows the identity semantics of
the source dataset.

A future specification may need an importer profile or dataset mapping
document that defines those fields explicitly.


## 53. Implementation Roadmap

Before RFC-0006 can become normative, the project should:

1. retain the experimental implementation separately from OpenSmell 0.1;
2. retain and version the golden interoperability vectors;
3. test at least one additional independent implementation language;
4. define the permanent namespace policy;
5. decide Nil and Max UUID behavior;
6. decide dataset identity and revision semantics;
7. decide whether the constrained canonical JSON profile is sufficient;
8. document migration behavior if the experimental namespace changes;
9. integrate Resource IDs only when future resource models require them;
10. keep source identifiers and external identifiers distinct from Resource
    IDs;
11. define how dataset-specific identity rules are documented;
12. evaluate whether a future standardized canonicalization mechanism should
    replace the current constrained profile.


## 54. Compatibility with OpenSmell 0.1

This RFC does not modify normative OpenSmell 0.1.

The current implementation remains under:

```text
opensmell.experimental
```

The OpenSmell 0.1 schema, parser, serializer, and public core model do not
depend on RFC-0006.

This allows the identity architecture to evolve without breaking the
released 0.1 format.

produce identical:

```text
canonical JSON text
UTF-8 octets
UUIDv5 Resource ID
```

The current result is:

```text
17 / 17 PASS
```

### 55.3 Unicode normalization

The experiment confirms that:

```text
NFC source identity
!=
decomposed source identity
```

under the current exact-preservation policy.

No implicit Unicode normalization is performed.

### 55.4 Unicode key-ordering failure discovered

An adversarial experiment using:

```text
U+E000
U+1F600
```

demonstrated that Python and JavaScript do not necessarily sort arbitrary
Unicode strings in the same order.

Python produced:

```text
U+E000
U+1F600
```

JavaScript produced:

```text
U+1F600
U+E000
```

The canonical strings and UTF-8 octets therefore differed.

This was a real interoperability defect in the earlier experimental
canonicalization design.

### 55.5 Unicode key-ordering resolution

The defect was resolved by restricting composite source-identity member names
to structural ASCII keys matching:

```text
^[a-z][a-z0-9_.-]*$
```

Unicode remains supported in identity values.

The updated 17-vector corpus passes independently in Python and JavaScript.

### 55.6 Surrogate handling

Lone Unicode surrogate code points are explicitly rejected from identity
strings.

This ensures that accepted identity material consists of Unicode scalar
values and can be encoded as UTF-8 according to the experimental generation
algorithm.

### 55.7 Burton full-dataset experiment

The Burton 2022 identity experiment processed:

```text
189,169 resources
```

consisting of:

```text

1,008 targets
187,748 observations
```

The experiment observed:

```text

189,169 unique UUIDs

```

All observations used structured composite source identity.

### 55.8 Burton reference anomalies

The Burton source data contains four target identifiers referenced by
observations but absent from the corresponding target metadata table:

```text
113L_038
113L_039
113R_064
113R_077
```

The experiment preserves these unresolved identities rather than inventing
metadata or discarding observations.

The dataset also contains four declared targets not referenced by behavior
observations:

```text
113L_122
113L_123
113R_135
113R_136
```

This provides practical evidence for separating structural identity from
reference resolution and source-data completeness.

### 55.9 Current evidence limits

The experimental results demonstrate interoperability for the tested model
and corpus.

They do not prove:

- mathematical impossibility of UUID collisions;
- interoperability across every programming language;
- correctness for arbitrary JSON data models;
- correctness for unsupported nested source identities;
- suitability of the experimental namespace as a permanent namespace;
- suitability of UUIDv5 as the final OpenSmell deterministic identifier
  mechanism.

The evidence should therefore be treated as strong implementation evidence,
not as a completed standardization proof.


## 56. Current Conclusion

The current experiments support the following provisional design.

OpenSmell Resource IDs SHOULD remain separate from external identifiers and
source identifiers.

UUID is a practical candidate for OpenSmell Resource IDs.

UUIDv4 is suitable for newly created resources that do not require
deterministic reconstruction.

UUIDv5 is a practical current candidate for deterministic dataset imports
provided that OpenSmell defines exact canonical generation material.

Deterministic identity SHOULD be constructed from:

```text
dataset
resource_type
source_identity
```

rather than from mutable metadata.

Source identity MAY be atomic:

```json
"113L_038"
```

or composite:

```json
{
  "stimulus": "1001_3.12e-13",
  "target": "111L_001"
}
```

Composite source identities MUST preserve structural boundaries and MUST NOT
use delimiter concatenation as their identity model.

For the current experimental canonicalization profile, composite structural
keys MUST match:

```text
^[a-z][a-z0-9_.-]*$
```

This restriction exists because direct experiments demonstrated that
arbitrary Unicode object-key ordering is not automatically portable between
Python and JavaScript.

Unicode identity values remain supported and are preserved exactly.

No implicit Unicode normalization is currently performed.

Lone surrogate code points are rejected.

The current experimental architecture has been exercised against:

- a real scientific dataset containing 189,169 generated resources;
- 187,748 composite observation identities;
- source-data reference anomalies;
- delimiter-boundary adversarial cases;
- Unicode normalization cases;
- Unicode escaping cases;
- a demonstrated Python/JavaScript Unicode key-ordering discrepancy;
- 17 cross-language golden interoperability vectors;
- independent Python and JavaScript UUIDv5 generation;
- a Python suite currently reporting 160 passing tests.

The architecture is therefore sufficiently mature to remain the leading
candidate for future OpenSmell resource identification.

However, RFC-0006 remains Draft.

The experimental namespace, dataset identity semantics, revision policy,
canonicalization strategy, UUID acceptance policy, and permanent
standardization rules MUST be resolved before this design becomes normative.
