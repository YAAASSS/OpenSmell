# RFC-0012 --- Experimental Rendering and Device Interoperability Architecture

-   **Status:** Draft
-   **Category:** Experimental Architecture
-   **Target:** Future OpenSmell version
-   **Normative for OpenSmell Core 0.1:** No
-   **Implementation status:** Experimental reference implementation
    exists

## Abstract

This RFC documents the experimental OpenSmell architecture that connects
device-independent olfactory resources to concrete rendering targets.

The architecture separates application intent, mapping policy, technical
device capabilities, device-facing rendering plans, adapter behavior,
message protocol, and transport.

Its central rule is:

> OpenSmell MUST NOT assume how an odor is physically reproduced.

Accordingly, this RFC does not define universal odor channels,
cartridges, chemical recipes, physical concentration semantics, diffuser
construction, or claims of perceptual equivalence between devices.

The architecture described here already exists experimentally in the
OpenSmell reference implementation. This RFC records and clarifies that
architecture; it does not promote it into OpenSmell Core 0.1.

------------------------------------------------------------------------

## 1. Motivation

OpenSmell Core 0.1 represents olfactory information independently of a
particular rendering device.

The experimental ResourceGraph work extends that principle to
heterogeneous resources and references.

A separate problem appears when an application wants a physical device
to act on that information.

A naive design could bind semantic descriptors, molecules, perceptual
values, or OpenSmell resources directly to hardware channels. Such a
design would make the data model dependent on a particular diffuser
architecture and would make cross-device interoperability difficult.

The experimental rendering architecture therefore introduces explicit
boundaries between:

1.  the OpenSmell resource an application wants to render;
2.  the policy that interprets that resource for a target;
3.  the technical commands a target accepts;
4.  the adapter that executes those commands;
5.  the protocol used to communicate with a remote device;
6.  the transport carrying protocol messages;
7.  the physical reproduction mechanism.

------------------------------------------------------------------------

## 2. Architectural principle

The experimental architecture is:

``` text
OpenSmell ResourceGraph
        |
        | application selects a resource
        v
RenderRequest
        |
        | mapping policy
        v
RenderingPlan
        |
        | technical validation
        v
DeviceCapabilities
        |
        | execution boundary
        v
DeviceAdapter
        |
        | optional remote-device protocol
        v
Device Protocol 0.1
        |
        | transport-independent messages
        v
DeviceTransport
        |
        | concrete transport profile
        v
Serial / future transports
        |
        v
Physical device
```

These layers are intentionally distinct.

A conforming implementation of one layer MUST NOT infer universal
semantics that belong to another layer.

------------------------------------------------------------------------

## 3. Scope

This RFC describes the responsibilities and boundaries of the
experimental rendering/device architecture.

It covers:

-   `RenderRequest`;
-   `DeviceCommand`;
-   `RenderingPlan`;
-   mapping policy;
-   `DeviceCapabilities`;
-   `DeviceAdapter`;
-   rendering orchestration;
-   `DeviceTransport`;
-   experimental Device Protocol 0.1;
-   `ProtocolDeviceAdapter`;
-   the current serial transport profile.

This RFC does not define a normative serialized rendering format for
OpenSmell Core.

------------------------------------------------------------------------

## 4. Non-goals

This RFC does not define:

-   a universal set of olfactory primaries;
-   universal meanings for device channel numbers;
-   cartridge chemistry;
-   molecule-to-cartridge mappings;
-   semantic-descriptor-to-cartridge mappings;
-   physical concentration units;
-   airflow models;
-   mixing physics;
-   perceptual equivalence between devices;
-   hardware discovery;
-   connection lifecycle;
-   scheduling or media synchronization;
-   streaming telemetry;
-   asynchronous completion;
-   safety limits for a particular physical actuator;
-   a claim that a rendering plan reproduces an odor faithfully.

Those concerns may be explored by future RFCs, device profiles, mapping
schemes, or hardware-specific implementations.

------------------------------------------------------------------------

## 5. RenderRequest

A `RenderRequest` expresses application intent.

The current experimental model contains:

-   `resource_id`: the identifier of the OpenSmell graph resource
    selected by the application;
-   `duration`: a positive finite requested duration in seconds.

A `RenderRequest` does not contain device channel commands.

A `RenderRequest` does not assert that the selected resource is
physically renderable.

The request duration expresses intent. A mapper or target may reject it
if the target cannot support it.

------------------------------------------------------------------------

## 6. Mapping policy

A mapper translates OpenSmell information into a device-facing
`RenderingPlan`.

Mapping is intentionally separate from both the source data and the
device capability model.

A mapping policy may depend on:

-   representation or resource schemes;
-   application configuration;
-   device-specific bindings;
-   external scientific models;
-   user configuration.

OpenSmell does not currently define a generic normative Mapper
interface.

The experimental reference implementation currently contains a
`SemanticChannelMapper`. A generic Mapper abstraction SHOULD NOT be
promoted until at least two materially different mapping implementations
demonstrate a stable common contract.

------------------------------------------------------------------------

## 7. SemanticChannelMapper experiment

The current `SemanticChannelMapper` interprets the experimental semantic
annotation scheme:

`org.opensmell.semantic.annotations` version `0.1`.

Its configured bindings associate semantic descriptor values with
device-facing channel numbers and normalized intensities.

Only annotations whose state is `present` produce commands.

`absent` and `unknown` states do not produce commands.

This behavior is a mapping-policy experiment. It MUST NOT be interpreted
as a universal rule that a descriptor such as `floral` corresponds to a
particular hardware channel.

Two devices may legitimately use different bindings for the same
OpenSmell resource.

------------------------------------------------------------------------

## 8. DeviceCommand

A `DeviceCommand` contains:

-   `channel`: a non-negative integer;
-   `intensity`: a finite normalized value in the closed interval
    `[0.0, 1.0]`.

The channel number is opaque to OpenSmell.

For example, OpenSmell does not define:

``` text
channel 0 = rose
channel 1 = coffee
channel 2 = vanilla
```

Such meanings, if they exist, belong to a device profile, mapper
configuration, or other device-specific layer.

Normalized intensity is likewise a command value. It is not
automatically a physical concentration, mass flow, voltage, duty cycle,
or perceptual intensity.

------------------------------------------------------------------------

## 9. RenderingPlan

A `RenderingPlan` is the device-facing result of mapping application
intent.

The current experimental plan contains:

-   zero or more `DeviceCommand` values;
-   a positive finite duration;
-   optional extension metadata.

A plan is transient execution information.

It is not currently an OpenSmell ResourceGraph resource and does not
become part of odor identity merely because it can render a selected
resource.

A mapper may include provenance-like execution metadata identifying the
source resource or annotations used to construct a plan. Such metadata
does not change the semantics of the source resources.

------------------------------------------------------------------------

## 10. DeviceCapabilities

`DeviceCapabilities` describes technical constraints advertised by a
rendering target.

The current experimental model contains:

-   `device_id`;
-   a set of channel capabilities;
-   minimum rendering duration;
-   maximum rendering duration;
-   optional extension data.

Each channel capability contains:

-   a non-negative channel number;
-   minimum normalized intensity;
-   maximum normalized intensity;
-   optional extension data.

Device capabilities describe what commands a target accepts.

They MUST NOT assign universal olfactory meaning to a channel.

For example, a capability may state that channel `2` accepts intensity
`0.0` through `0.8`. It does not state what odor, molecule, cartridge,
or physical mechanism channel `2` represents.

------------------------------------------------------------------------

## 11. Compatibility and concrete plan validation

The experimental pipeline performs two distinct forms of validation.

### 11.1 Mapping configuration compatibility

A mapper may determine whether its configured bindings are compatible
with a target's advertised capabilities.

This allows configuration errors to be rejected before a plan is
produced.

### 11.2 Concrete plan validation

The resulting `RenderingPlan` is then validated against the target
capabilities.

This second validation remains necessary because request-specific
properties, such as duration, are not fully represented by static mapper
configuration.

These checks are complementary rather than redundant.

------------------------------------------------------------------------

## 12. DeviceAdapter

`DeviceAdapter` is the experimental execution boundary between a
`RenderingPlan` and a concrete target.

The current structural contract exposes:

-   `capabilities -> DeviceCapabilities`;
-   `render(plan) -> object`.

Implementations do not need to inherit from a common base class.

The adapter is responsible for rejecting plans its target cannot
execute.

The adapter return value is intentionally not standardized by this RFC.

A `DeviceAdapter` does not by itself define:

-   transport;
-   connection lifecycle;
-   physical reproduction;
-   channel semantics;
-   scheduling.

A local simulator and a remote protocol-backed device can therefore
satisfy the same execution boundary.

------------------------------------------------------------------------

## 13. Rendering pipeline

The current high-level rendering operation is conceptually:

``` text
validate inputs
    |
validate adapter
    |
check mapper configuration against target capabilities
    |
map ResourceGraph + RenderRequest
    |
RenderingPlan
    |
validate concrete plan against target capabilities
    |
adapter.render(plan)
```

The reference implementation exposes operations that either:

-   build a validated rendering plan; or
-   build and immediately render the plan.

The pipeline coordinates responsibilities. It does not redefine mapping,
capabilities, or device behavior.

------------------------------------------------------------------------

## 14. Simulated targets

A simulated rendering target is useful for validating orchestration
without hardware.

The experimental `SimulatedDiffuser` can record accepted plans and may
be configured with technical capabilities.

Simulation demonstrates software behavior only.

A successful simulated render MUST NOT be described as evidence of
physical odor reproduction.

------------------------------------------------------------------------

## 15. Multi-device rendering

The same OpenSmell source resource and `RenderRequest` may produce
different valid plans for different devices.

For example:

``` text
same ResourceGraph
same RenderRequest
        |
        +--> Mapper configuration A --> Device A plan
        |
        +--> Mapper configuration B --> Device B plan
```

This is expected.

OpenSmell interoperability at this boundary means that
device-independent information can be interpreted through explicit
device-specific policies.

It does not mean that two resulting physical stimuli are perceptually or
chemically equivalent.

------------------------------------------------------------------------

## 16. DeviceTransport

`DeviceTransport` is the low-level request/response communication
boundary.

The current structural contract is:

``` text
exchange(message: string) -> string
```

The transport is unaware of:

-   ResourceGraph;
-   RenderRequest;
-   RenderingPlan semantics;
-   semantic annotations;
-   mapping policy;
-   physical odor reproduction.

This deliberately keeps the device message protocol independent of
serial, network, USB bridge, or in-memory communication mechanisms.

The synchronous request/response contract is sufficient for the current
experiment. It does not define streaming, unsolicited events,
cancellation, or asynchronous completion.

------------------------------------------------------------------------

## 17. MemoryDeviceTransport

`MemoryDeviceTransport` is a deterministic test transport.

It records outgoing textual messages and returns configured responses.

It performs no hardware or network I/O.

Its purpose is to test protocol and adapter behavior independently of a
physical communication layer.

------------------------------------------------------------------------

## 18. Experimental Device Protocol 0.1

The reference implementation contains a small transport-independent JSON
message protocol.

Its protocol version is:

`0.1`

The current message families are:

-   hello request;
-   hello response;
-   capabilities request;
-   capabilities response;
-   render request;
-   success response;
-   error response.

The protocol uses strict JSON serialization and rejects non-finite JSON
numeric constants such as NaN and Infinity.

Protocol messages are conceptually independent of transport framing.

### 18.1 Hello

A client may request the identity of the remote device.

The response identifies the device by a non-empty `device_id`.

### 18.2 Capabilities

A client may request the remote target's technical capabilities.

The response communicates the current experimental `DeviceCapabilities`
information:

-   device ID;
-   supported channels;
-   per-channel normalized intensity ranges;
-   minimum duration;
-   maximum duration.

### 18.3 Render

A render request transports:

-   rendering duration;
-   device commands.

The protocol does not transport universal odor-channel semantics.

### 18.4 Success and error

The current protocol supports a generic success response and a
structured error response containing an error code and human-readable
message.

Error-code governance is not yet standardized.

------------------------------------------------------------------------

## 19. ProtocolDeviceAdapter

`ProtocolDeviceAdapter` connects the `DeviceAdapter` boundary to the
experimental Device Protocol through a `DeviceTransport`.

Current initialization performs:

1.  HELLO;
2.  GET_CAPABILITIES;
3.  verification that both responses identify the same device.

The adapter stores the discovered capabilities.

Before transmitting a render request, it validates the plan locally
against those capabilities.

The remote device MUST nevertheless perform its own validation.
Client-side validation is not a physical safety boundary.

------------------------------------------------------------------------

## 20. Serial transport profile

The current `SerialDeviceTransport` is one concrete `DeviceTransport`.

It uses:

-   UTF-8 text;
-   one JSON protocol message per line;
-   newline-delimited framing;
-   configurable serial port;
-   configurable baud rate;
-   configurable timeout.

The current default baud rate is `115200`.

The serial framing belongs to the serial transport profile, not to the
transport-independent Device Protocol itself.

Other transports MAY use different framing while carrying the same
logical protocol messages.

------------------------------------------------------------------------

## 21. Response timing and command acceptance

The current synchronous transport API expects a response to each
request.

This RFC does not yet standardize whether a successful render response
means:

-   the render command was accepted;
-   physical execution has started;
-   physical execution has completed.

This distinction becomes important when rendering duration exceeds
transport timeouts.

For the first physical prototype, implementations SHOULD avoid blocking
the protocol response for the entire requested rendering duration.

A device may validate and accept the command, respond successfully, and
execute the timed output independently.

A future protocol revision or dedicated RFC MUST define completion
semantics if applications require confirmation of physical completion.

------------------------------------------------------------------------

## 22. Safety boundary

OpenSmell software-side validation is not sufficient to protect physical
hardware.

A physical rendering device MUST enforce its own technical and safety
constraints.

Depending on hardware, this may include:

-   allowed channels;
-   intensity limits;
-   duration limits;
-   safe startup state;
-   safe state after communication loss;
-   actuator duty-cycle limits;
-   thermal constraints;
-   mutually exclusive outputs;
-   purge or cooldown requirements;
-   emergency shutdown behavior.

These constraints are hardware-specific and are not fully modeled by the
current experimental capability model.

------------------------------------------------------------------------

## 23. Extension and future capability model

Real hardware may demonstrate the need for additional capability
information, for example:

-   simultaneous-channel limits;
-   minimum pulse duration;
-   duty-cycle restrictions;
-   purge requirements;
-   cooldown requirements;
-   command resolution;
-   cartridge availability;
-   hardware safety state.

Such fields SHOULD NOT be added speculatively.

They should be introduced only when implementation experience
demonstrates a portable interoperability requirement.

------------------------------------------------------------------------

## 24. Hardware validation strategy

The first physical OpenSmell experiment intentionally uses a simple
actuator, such as an LED connected to an ESP32, rather than an
odor-producing mechanism.

The purpose is to validate:

``` text
OpenSmell ResourceGraph
        ->
mapping
        ->
RenderingPlan
        ->
Device Protocol 0.1
        ->
SerialDeviceTransport
        ->
physical output
```

A visible LED response can validate:

-   mapping;
-   plan construction;
-   capability negotiation;
-   protocol serialization;
-   serial framing;
-   physical command delivery;
-   duration/intensity control behavior.

It cannot validate odor reproduction.

Only after this control path is stable should experiments introduce
olfactory actuators.

------------------------------------------------------------------------

## 25. Relationship to OpenSmell Core 0.1

This RFC does not modify OpenSmell Core 0.1.

In particular:

-   `RenderRequest` is not a Core representation;
-   `RenderingPlan` is not a Core odor representation;
-   device capabilities are not Core odor metadata;
-   device channels are not OpenSmell semantic descriptors;
-   the Device Protocol is not the `.osmell` document format;
-   serial framing is not part of Core serialization.

Core documents remain device-independent.

------------------------------------------------------------------------

## 26. Relationship to ResourceGraph

The experimental rendering pipeline currently selects resources from the
Generic ResourceGraph architecture explored by RFC-0008 and subsequent
RFCs.

This does not make rendering a required ResourceGraph feature.

ResourceGraph can be used for storage, exchange, annotation, scientific
data, or other purposes without any rendering device.

Likewise, future rendering implementations may consume information
through other explicit adapters without changing the Core format.

------------------------------------------------------------------------

## 27. Interoperability claims

The current experimental implementation supports a defensible software
claim:

> OpenSmell can carry device-independent olfactory information through
> an explicit mapping and device-interface architecture without
> assigning universal physical meaning to device channels.

The current implementation does not support the stronger claim:

> Different OpenSmell devices reproduce the same odor.

That would require scientific and hardware validation outside the scope
of this RFC.

------------------------------------------------------------------------

## 28. Conformance status

This RFC currently documents an implemented experimental architecture.

The repository contains extensive Python tests covering:

-   rendering primitives;
-   semantic mapping;
-   device capabilities;
-   simulated rendering;
-   multi-device rendering;
-   device adapter behavior;
-   rendering pipeline behavior;
-   device transport;
-   Device Protocol 0.1;
-   protocol-backed adapters;
-   protocol rendering end-to-end behavior;
-   serial transport;
-   serial/protocol integration.

At the time this RFC is introduced, the audited repository baseline is:

`1659 tests passed`

The project also contains portable Python/JavaScript conformance and
interoperability work for earlier ResourceGraph, identifier, Molecule,
Annotation, and reference-discovery experiments.

The Device Protocol does not yet have an equivalent portable independent
conformance corpus. That is the next interoperability task for this
architecture.

------------------------------------------------------------------------

## 29. Open questions

The following questions intentionally remain open:

1.  Should Device Protocol 0.1 ignore, preserve, or reject unknown
    message fields?
2.  What exactly does an `ok` response to a render request acknowledge?
3.  Should protocol messages eventually contain request identifiers for
    correlation?
4.  Are commands in one RenderingPlan always simultaneous?
5.  Is command ordering semantically significant?
6.  How should partial device failure be reported?
7.  When should capabilities be refreshed?
8.  How should connection loss affect active rendering?
9.  What frame-size limits should concrete transports enforce?
10. Which capability constraints prove sufficiently portable to
    standardize?
11. When a second materially different mapper exists, what common Mapper
    contract actually emerges?
12. Which parts of this architecture, if any, should eventually move out
    of `opensmell.experimental`?

These questions SHOULD be answered from implementation evidence rather
than speculation.

------------------------------------------------------------------------

## 30. Next steps

The immediate next steps are:

1.  define portable Device Protocol 0.1 conformance vectors;
2.  create an independent non-Python verifier for those vectors;
3.  decide whether a JSON Schema is useful for protocol message
    structure;
4.  validate the serial protocol against the first physical ESP32
    prototype;
5.  record response-timing and lifecycle behavior observed on real
    hardware;
6.  revise this experimental architecture only where those results
    justify it.

------------------------------------------------------------------------

## 31. Conclusion

OpenSmell's experimental rendering architecture deliberately separates
olfactory information from physical reproduction.

The central chain is:

``` text
resource
  -> request
  -> mapping
  -> rendering plan
  -> technical capabilities
  -> adapter
  -> protocol
  -> transport
  -> device
```

No layer in that chain creates a universal meaning for a physical device
channel.

This separation allows OpenSmell to explore physical rendering without
making the Core format dependent on a particular diffuser, cartridge
system, chemical model, or transport.

RFC-0012 therefore records the current rendering/device interoperability
architecture as an experimental foundation for hardware validation and
future standardization work.
