# RFC-0009: Molecule Resource Type

- **Status:** Draft
- **Version:** 0.1
- **Date:** 2026-09-05
- **Authors:** OpenSmell contributors
- **Discussion:** OpenSmell project repository
- **Target:** Experimental OpenSmell resource model
- **Depends on:** RFC-0006, RFC-0008
- **Does not modify:** OpenSmell Core 0.1

---

## 1. Abstract

This RFC defines an experimental OpenSmell Resource Type for representing the
identity of a chemical molecule inside an RFC-0008 Generic ResourceGraph.

The Resource Type ID is:

```text
org.opensmell.molecule
```

The Resource Type Version defined by this RFC is:

```text
0.1
```

The Molecule resource is intentionally narrow.

It represents chemical identity information that can be associated with a
molecule.

It does not represent:

- an odor as a perceptual object;
- semantic odor annotations;
- perceptual measurements;
- biological measurements;
- sensor measurements;
- stimulus presentation conditions;
- observations;
- mixtures;
- rendering recipes;
- diffuser commands.

The primary purpose of this RFC is to test whether the extensibility model
introduced by RFC-0008 can support a real OpenSmell-defined Resource Type
without modifying GenericResourceGraph itself.

The current experiment includes:

- a Python Molecule model;
- parser and serializer support;
- explicit RFC-0008 ResourceTypeRegistry integration;
- an experimental Molecule-specific JSON Schema;
- language-independent portable conformance vectors;
- exact-preservation vectors;
- an independent JavaScript conformance verifier;
- real-data validation using 8,892 OdorNet molecules.

---

## 2. Motivation

RFC-0008 introduces a generic resource transport architecture.

Its central principle is:

> **A ResourceGraph MUST NOT require knowledge of every resource type that it
> transports.**

That architecture allows new Resource Types to be registered independently of
the graph implementation.

Before this experiment, RFC-0008 interoperability testing primarily used
synthetic example Resource Types and RFC-0007 compatibility resources.

A real OpenSmell-defined Resource Type is needed to evaluate whether the
architecture remains practical when applied to real olfactory data.

Chemical molecules are a useful first experiment because molecular identity
appears in multiple digital-olfaction workflows while remaining conceptually
distinct from:

- odor perception;
- semantic odor descriptions;
- experimental stimuli;
- observations;
- measurements;
- rendering.

Molecule 0.1 therefore acts as the first concrete test of the RFC-0008
extensible Resource Type architecture.

---

## 3. Design principle

This RFC adopts the following principle:

> **A Molecule resource identifies a chemical molecule without claiming how
> that molecule smells.**

Chemical identity and olfactory interpretation are separate concerns.

For example:

```text
Molecule
    |
    +-- SMILES
    +-- external identifiers
```

does not imply:

```text
Molecule
    |
    +-- floral
    +-- woody
    +-- sweet
```

Semantic odor properties require a separate semantic model.

Likewise, a Molecule does not by itself describe a stimulus presented during an
experiment.

Conceptually:

```text
Molecule
    |
    +------> semantic information
    |
    +------> Stimulus
                 |
                 +------> Observation
                              |
                              +------> Result
```

The exact graph model for attaching semantic annotations directly to resources
is outside the scope of this RFC.

- external identifier transport semantics;
- extension preservation expectations;
- RFC-0008 registry integration;
- version-aware dispatch expectations;
- portable conformance evidence;
- real-data validation evidence.

RFC-0009 does not define:

- chemical structure validation;
- SMILES canonicalization;
- molecular equivalence;
- a universal chemical identifier registry;
- odor identity;
- semantic odor annotations;
- perceptual measurements;
- biological measurements;
- sensor measurements;
- stimulus presentation semantics;

- diffuser commands;

- universal molecule Resource ID generation.

## 5. Resource Type ID

The Resource Type ID defined by this RFC is:

```text
org.opensmell.molecule
```

This follows the RFC-0008 Resource Type naming policy.

The:

```text
org.opensmell.*
```

namespace is reserved for Resource Types defined by the OpenSmell project.

The Resource Type ID identifies the conceptual resource family.

It does not contain the Resource Type Version.

---

## 6. Resource Type Version

This RFC defines:

```text
type_version = "0.1"
```

Resource Type Version is separate from Resource Type ID.

Therefore:

```text
org.opensmell.molecule
```

remains the Resource Type ID, while:

```text
0.1
```

identifies the portable contract version defined by this RFC.

A future version of the same conceptual Molecule Resource Type SHOULD retain the
same Resource Type ID unless it represents a genuinely different resource
concept.

RFC-0008 does not currently impose a universal version grammar.

The value:

```text
0.1
```

is therefore interpreted according to the Molecule Resource Type contract
defined here.

---

## 7. Serialized form

A Molecule 0.1 resource is represented as a JSON object.

Example:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO"
}
```

A resource may also contain external identifiers:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO",
  "identifiers": [
    {
      "scheme": "pubchem.inchikey",
      "value": "LFQSCWFLJHTTHZ-UHFFFAOYSA-N"
    }
  ]
}
```

Unknown extension fields MAY also be present.

---

## 8. Fields

### 8.1 `type`

Required.

The value MUST be:

```text
org.opensmell.molecule
```

for a Molecule 0.1 resource.

---

### 8.2 `type_version`

Required.

The value MUST be:

```text
0.1
```

when the resource is interpreted using the Molecule 0.1 contract.

An RFC-0008 implementation that does not support the received Molecule version
SHOULD preserve the resource generically rather than rejecting the entire
graph.

---

### 8.3 `id`

Required.

`id` is the Resource ID used by the Generic ResourceGraph.

The current experimental implementation requires a non-empty string.

This RFC does not finalize universal Resource ID syntax.

RFC-0006 explores stronger deterministic Resource ID mechanisms separately.

A Molecule Resource ID identifies the graph resource.

It MUST NOT be assumed to be a universal chemical identifier.

---

### 8.4 `smiles`

Optional.

When present, `smiles` MUST be a non-empty string.

The transport contract treats SMILES as an opaque chemical representation.

Molecule 0.1 does not:

- parse SMILES;
- canonicalize SMILES;
- validate chemical syntax;
- determine chemical equivalence;
- require canonical SMILES;
- require a particular SMILES implementation.

This is deliberate.

For example, the following value is structurally acceptable to the Molecule 0.1
transport contract:

```text
this-is-not-chemically-validated
```

even though it is not intended to demonstrate a chemically valid SMILES
representation.

The purpose of the transport layer is not to replace chemistry software.

---

### 8.5 `identifiers`

Optional.

`identifiers` is a list of external identifiers.

Each identifier follows the experimental ExternalIdentifier structure:

```json
{
  "scheme": "pubchem.inchikey",
  "value": "LFQSCWFLJHTTHZ-UHFFFAOYSA-N"
}
```

Both:

```text
scheme
value
```

MUST be non-empty strings.

Unknown extension fields associated with an external identifier MAY be
preserved.

The Molecule transport model does not itself determine whether an external
identifier is scientifically valid.

Applications interpreting a particular identifier scheme are responsible for
understanding its semantics.

---

## 9. Minimum chemical identification requirement

A Molecule MUST contain at least one chemical identification mechanism.

Therefore, at least one of the following MUST be present:

1. a non-empty `smiles` value;
2. one or more valid ExternalIdentifier entries.

The following is invalid:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1"
}
```

because it contains a graph Resource ID but no chemical identification
information.

The Resource ID alone identifies the graph resource, not the chemical entity it
represents.

The following is also invalid:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "identifiers": []
}
```

because an empty identifier list does not provide chemical identification.

However, this is valid:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO",
  "identifiers": []
}
```

because `smiles` already provides the required chemical identification
mechanism.

---

## 10. Empty optional collections and normalization

An explicitly empty optional `identifiers` list and an absent `identifiers`
member carry the same Molecule 0.1 semantic information when another chemical
identification mechanism is present.

For example:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO",
  "identifiers": []
}
```

and:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO"
}
```

both describe a Molecule with SMILES and no external identifiers.

The current Python serializer normalizes the first form into the second by
omitting an empty optional identifier list.

Therefore:

> **Molecule validity and exact serialized-form preservation are distinct
> properties.**

This distinction was discovered while developing the portable conformance
suite.

The valid:

```text
valid_empty_identifiers_with_smiles
```

vector intentionally does not declare:

```text
preserve: true
```

because the Python implementation may normalize the empty optional list.

This normalization does not change Molecule 0.1 semantics.

---

## 11. External identifier schemes

Molecule 0.1 intentionally keeps external identifier schemes extensible.

For example:

```text
pubchem.inchikey
```

is used by the current OdorNet validation experiment for PubChem-derived
InChIKey values.

This RFC does not yet establish a universal registry of chemical identifier
scheme names.

Future work may define recommended identifiers for systems such as:

- InChI;
- InChIKey;
- PubChem;
- CAS;
- ChEBI;
- other chemical databases.

Implementations MUST NOT invent missing identifiers merely to satisfy an
expected identifier scheme.

Absence of a particular external identifier is not equivalent to absence of
chemical identity when another valid identification mechanism is present.

---

## 12. Extension fields

Molecule 0.1 supports forward-compatible extension fields.

Unknown fields SHOULD be preserved by implementations when practical.

The following field names are reserved by the Molecule 0.1 contract:

```text
type
type_version
id
smiles
identifiers
```

Extension data MUST NOT override those fields.

This follows the broader RFC-0008 goal of preserving information that an
implementation does not yet understand.

Extensions may contain JSON-compatible values including:

- strings;
- numbers;
- booleans;
- null;
- arrays;
- objects;
- Unicode text.

---

## 13. Unknown Molecule versions

RFC-0008 registry dispatch is based on the pair:

```text
(Resource Type ID, Resource Type Version)
```

For example, an implementation may register:

```text
(org.opensmell.molecule, 0.1)
```

If the same implementation receives:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.2",
  "id": "future-molecule",
  "smiles": "CCO"
}
```

and does not understand Molecule 0.2, the resource MUST NOT be silently
interpreted as Molecule 0.1.

Under the RFC-0008 experimental architecture, it is instead preserved as a
GenericResource.

Conceptually:

```text
known type + known version
          |
          v
       Molecule


known type + unknown version
          |
          v
   GenericResource
```

This prevents an implementation from accidentally applying outdated semantics
to a future resource contract.

---

## 14. Molecule conformance versus generic transport validity

A resource can fail Molecule 0.1 conformance while remaining valid for generic
RFC-0008 transport.

For example:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.2",
  "id": "future-molecule",
  "smiles": "CCO"
}
```

is:

```text
INVALID as Molecule 0.1
```

because its Resource Type Version is not `0.1`.

However, it may still be:

```text
VALID RFC-0008 generic transport
```

and therefore be preserved as GenericResource.

This distinction is fundamental.

Molecule-specific validation answers:

```text
Do I understand and accept this exact Molecule contract?
```

Generic RFC-0008 validation answers:

```text
Can I transport this resource without necessarily understanding it?
```

These are intentionally different questions.

## 15. Registry integration

Molecule support is installed through an RFC-0008 ResourceTypeRegistry.

The experimental Python implementation provides:

```text
register_molecule_resource_type(registry)
```

The registered contract is:

```text
Resource Type ID:
    org.opensmell.molecule

Resource Type Version:
    0.1
```

The registry associates that contract with:

- the Molecule Python model;
- the Molecule parser;
- the Molecule serializer.

GenericResourceGraph itself does not contain Molecule-specific logic.

This dependency direction is intentional:

```text
GenericResourceGraph
        ^
        |
ResourceTypeRegistry
        ^
        |
Molecule resource module
```

and not:

```text
GenericResourceGraph
        |
        +-- hardcoded Molecule
```

This experiment therefore directly exercises the extensibility principle of
RFC-0008.

---

## 16. Default registry behavior

Molecule 0.1 is not automatically added to the RFC-0007 compatibility handlers
by this experiment.

Registration is explicit.

This allows the experiment to demonstrate two behaviors.

Without Molecule support:

```text
serialized org.opensmell.molecule/0.1
                |
                v
         GenericResource
```

With Molecule 0.1 registered:

```text
serialized org.opensmell.molecule/0.1
                |
                v
             Molecule
```

The graph implementation remains unchanged in both cases.

A future RFC or implementation policy may decide whether standardized OpenSmell
Resource Types should be installed by a higher-level default registry.

That policy is outside the scope of this RFC.

---

## 17. Relationship to OpenSmell Core Odor

Molecule and OpenSmell Core `Odor` are not equivalent concepts.

An OpenSmell Core Odor may contain multiple representations of olfactory
information.

A Molecule represents chemical identity.

Therefore:

```text
Molecule != Odor
```

A chemical molecule may participate in an olfactory workflow without defining
all perceptual information associated with an odor.

Likewise, an odor representation may describe information that is not reducible
to one chemical molecule.

Molecule 0.1 does not replace the Core chemical representation scheme.

The relationship between Core Odor representations and graph resources remains
an area for future architectural work.

---

## 18. Relationship to Stimulus

Molecule and Stimulus are distinct concepts.

A Molecule describes chemical identity.

A Stimulus describes something presented or applied, potentially under
conditions such as:

- concentration;
- dilution;
- carrier;
- temperature;
- flow;
- duration.

Conceptually:

```text
Molecule
    |
    v
Stimulus
```

A Stimulus may reference a Molecule as its source.

The experimental Generic ResourceGraph has demonstrated that an RFC-0007
Stimulus reference can resolve to a registered Molecule resource.

However, Molecule 0.1 does not require every Molecule to participate in a
Stimulus.

---

## 19. Relationship to Observation

A Molecule is not an Observation.

Observation resources represent observations or measurements associated with a
Stimulus.

For example, observations may contain:

- perceptual measurements;
- categorical responses;
- physiological measurements;
- biological measurements;
- sensor-array features;
- model outputs.

A Molecule merely provides chemical identity.

This distinction prevents chemical identity, experimental presentation, and
measured results from being collapsed into one resource.

---

## 20. Relationship to semantic annotations

Semantic odor annotations such as:

```text
floral
fruity
woody
spice
```

are not chemical identity fields.

Therefore Molecule 0.1 deliberately does not contain an odor descriptor field.

For example, this RFC does not define:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "floral": true
}
```

as part of the Molecule contract.

OpenSmell RFC-0004 experimentally explores semantic annotation data.

The current OdorNet adapter uses:

```text
org.opensmell.semantic.annotations
```

with annotation states:

```text
present
absent
unknown
```

Determining how semantic annotations should be associated with arbitrary
Generic ResourceGraph resources is outside the scope of Molecule 0.1.

This separation is intentional and was reinforced by the real-data experiment
described later in this RFC.

---

## 21. OdorNet annotations are not artificial observations

OdorNet contains semantic category annotations associated with molecules.

Those dataset labels are not automatically experimental observations.

Therefore the current Molecule experiment deliberately does not create an
Observation resource for every OdorNet molecule merely to transport semantic
categories.

Doing so would collapse two distinct concepts:

```text
dataset semantic annotation
```

and:

```text
experimental observation
```

The current architectural separation is:

```text
Molecule
│
│ chemical identity
│
├──────────────► semantic annotations
│
└──────────────► Stimulus
                     │
                     ▼
                 Observation
                     │
                     ▼
                   Result
```

A future generic Annotation Resource Type may provide one possible solution for
associating semantic information with arbitrary resources.

RFC-0009 does not define such a resource.

---

## 22. Relationship to mixtures

Molecule 0.1 represents one molecular identity resource.

It does not define a mixture composition model.

A mixture may reference multiple molecules, ingredients, materials, or other
resources in a future Resource Type.

Defining such a Resource Type is outside the scope of this RFC.

---

## 23. Relationship to rendering

Molecule 0.1 does not define how a smell is physically reproduced.

In particular, it does not define:

- diffuser channels;
- cartridges;
- actuator commands;
- primary odorants;
- mixture ratios for hardware;
- timing;
- intensity;
- device capabilities.

This follows the broader OpenSmell architectural principle:

> **OpenSmell MUST NOT assume how an odor is physically reproduced.**

Device-specific interpretation belongs in appropriate adapters, mappings, or
future rendering layers.

---

## 24. SMILES is representation, not universal identity

The distinction between representation and identity is important.

Two different SMILES strings may describe the same chemical structure.

Molecule 0.1 does not attempt to determine whether two strings represent the
same chemical.

Therefore:

> **SMILES string equality MUST NOT be treated as a universal guarantee of
> molecular identity.**

Likewise, different textual SMILES forms MUST NOT automatically be considered
different chemicals merely because their strings differ.

Chemical equivalence is outside the transport responsibilities of this RFC.

The fact that all 8,892 raw SMILES strings in the current OdorNet experiment
were unique is a property of the tested dataset.

It does not establish raw SMILES as a universal deduplication mechanism.

---

## 25. Dataset import identity

A dataset importer may create deterministic or source-specific Resource IDs.

For example:

```text
odornet-molecule-1
odornet-molecule-2
```

Such IDs identify resources within the imported graph.

They do not claim that:

```text
odornet-molecule-1
```

is a globally recognized identifier for that chemical.

RFC-0006 explores stronger deterministic Resource ID strategies.

A future import profile may combine:

- source identity;
- source record identity;
- external identifiers;
- canonical structured identity inputs;
- other deterministic information.

Molecule 0.1 deliberately does not mandate one strategy.

The sequential OdorNet IDs used in the current validation tool are therefore
validation identifiers, not universal chemical identities.

---

## 26. Experimental JSON Schema

Molecule 0.1 now has an experimental resource-specific JSON Schema:

```text
schema/experimental-molecule-0.1.schema.json
```

Its schema identifier is:

```text
https://opensmell.org/schema/experimental-molecule-0.1.schema.json
```

The schema uses:

```text
JSON Schema Draft 2020-12
```

It validates the portable structural contract for Molecule 0.1.

The schema requires:

```text
type
type_version
id
```

and requires at least one chemical identification mechanism through:

```text
smiles
```

or:

```text
one or more identifiers
```

The schema deliberately does not validate chemical SMILES syntax.

Unknown extension fields remain allowed.

The schema is experimental and non-normative.

---

## 27. Separation of generic and resource-specific schemas

The RFC-0008 Generic ResourceGraph schema intentionally does not enumerate every
possible Resource Type.

Molecule-specific validation therefore remains separate.

Conceptually:

```text
Generic ResourceGraph Schema
        |
        +-- graph envelope
        +-- generic resource envelope
        +-- unknown resource transport
        |
        v
generic transport validity


Molecule 0.1 Schema
        |
        +-- exact Molecule type
        +-- exact Molecule version
        +-- Molecule fields
        +-- chemical identification requirement
        |
        v
Molecule-specific validity
```

This preserves the RFC-0008 architectural boundary:

> Type-specific validation belongs outside the generic graph.

## 31. Portable preservation vectors

Valid conformance vectors may additionally declare:

```text
preserve: true
```

For such vectors, an implementation is tested for exact JSON-object semantic
preservation through parse and serialization.

The current suite contains:

```text
9 exact-preservation vectors
```

These cover:

- SMILES;
- identifiers;
- multiple identifiers;
- resource extensions;
- identifier extensions;
- Unicode;
- opaque SMILES text.

Object member ordering is not significant.

Array ordering remains significant.

Canonical textual JSON equality is not required.

---

## 32. Why there are 10 valid vectors but 9 preservation vectors

The valid vector:

```text
valid_empty_identifiers_with_smiles
```

contains:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-5",
  "smiles": "CCO",
  "identifiers": []
}
```

This resource is valid.

However, the current Python serializer normalizes it to:

```json
{
  "type": "org.opensmell.molecule",
  "type_version": "0.1",
  "id": "molecule-5",
  "smiles": "CCO"
}
```

The semantic Molecule information is unchanged.

The vector therefore tests validity but does not require exact serialized-form
preservation.

This is intentional.

It records an important distinction discovered by the conformance experiment:

```text
semantic validity
        !=
exact serialized-form preservation
```

Both must agree with the expected vector validity.

Conceptually:

```text
portable vector
      |
      +----------> JSON Schema
      |
      +----------> Python parser
                         |
                         v
                 same expected result
```

The current Python Molecule portable conformance suite reports:

```text

```

This consists of:

```text
6 vector/meta tests
37 validity tests
9 preservation tests
```

All passed.

## 35. What the JavaScript verifier demonstrates

The independent verifier demonstrates that the Molecule 0.1 contract can be
interpreted outside the Python implementation.

In particular, Python and JavaScript independently agree on:

```text
37 / 37 validity expectations
```

and all declared preservation cases succeed.

This is stronger evidence than Python unit testing alone.

However, it does not yet establish a complete production JavaScript OpenSmell
SDK.

The verifier is intentionally small and conformance-focused.

## 36. OdorNet real-data experiment

Molecule 0.1 has also been tested using the enriched OdorNet dataset already
used by earlier OpenSmell RFC-0004 experiments.

The validation tool is:

```text
tools/validate_odornet_molecule_resources.py
```

The experiment converts each OdorNet dataset row into one Molecule resource.

The original OdorNet SMILES value is preserved as:

```text
Molecule.smiles
```

When available in the locally enriched dataset, PubChem-derived InChIKey is
represented using an ExternalIdentifier with:

```text
scheme = pubchem.inchikey
```

The experiment does not invent missing PubChem identifiers.

The enriched dataset does not provide a PubChem CID field used by this
experiment.

## 40. What the OdorNet experiment demonstrates

The experiment provides evidence for several architectural properties.

### 40.1 A real namespaced Resource Type works

The graph did not need Molecule-specific modifications.

Molecule support was installed through the RFC-0008 registry.

### 40.2 Versioned dispatch works with a real OpenSmell type

The registered contract is:

```text
(org.opensmell.molecule, 0.1)
```

and parsed resources become typed Molecule objects.

### 40.3 Unknown future versions remain transportable

Unit tests demonstrate that an unknown future Molecule version falls back to
GenericResource rather than being interpreted as Molecule 0.1.

### 40.4 External identifiers survive transport

PubChem-derived InChIKey values survived the tested graph round-trip without
observed mismatch.

### 40.5 Optional enrichment is not required for transport

Rows without an InChIKey remain valid Molecule resources because they contain
SMILES.

This demonstrates why the Molecule identity requirement is expressed as:

```text
smiles OR identifiers
```

rather than requiring a particular external database.

### 40.6 Chemical identity remains separate from odor semantics

The experiment intentionally did not copy OdorNet semantic category labels into
Molecule fields.

This preserves the architectural distinction between:

```text
chemical identity
```

and:

```text
olfactory semantic information
```

## 41. What the OdorNet experiment does not demonstrate

The experiment does not prove:

- that raw SMILES is globally unique;
- that two different SMILES strings represent different molecules;
- that PubChem enrichment is scientifically correct;
- that every InChIKey is correct;
- that OdorNet semantic labels are correct;
- that a molecule always produces a particular odor;
- that a molecule can be physically rendered by a smell device;
- that Molecule 0.1 is ready to become normative;
- that the Generic ResourceGraph architecture is stable;
- that the same results will hold for every chemical dataset.

Those questions require separate scientific, interoperability, or conformance
evidence.

## 48. Forward compatibility

Molecule 0.1 follows the RFC-0008 forward-compatibility model.

An implementation that understands:

```text
org.opensmell.molecule / 0.1
```

but receives:

```text
org.opensmell.molecule / 0.2
```

MUST NOT assume the 0.1 contract applies.

The unknown version should remain generically transportable when the enclosing
RFC-0008 document is otherwise valid.

Unknown extension fields within a supported Molecule version SHOULD also be
preserved when practical.

## 50. Security considerations

Molecule resources contain untrusted external data.

Implementations MUST NOT assume that a received SMILES string or external
identifier is valid merely because it appears in a structurally valid Molecule
resource.

Applications may impose reasonable limits on:

- string length;
- identifier count;
- extension size;
- document size;
- nesting depth.

Parsing a Molecule resource MUST NOT itself trigger:

- network requests;
- PubChem lookups;
- code execution;
- chemical computation;
- device operations;
- rendering operations.

Such behavior requires explicit application logic.

---

## 51. Privacy considerations

Molecule 0.1 is designed for chemical identity information and does not require
personal information.

Applications combining Molecule resources with experimental observations may
introduce:

- participant information;
- subject information;
- medical information;
- other sensitive data.

Such privacy concerns belong to those resources and workflows.

A Molecule Resource ID SHOULD NOT unnecessarily encode personal or sensitive
information.

---

## 52. Interoperability considerations

Generic preservation of:

```text
org.opensmell.molecule
```

does not automatically imply semantic understanding.

An implementation claiming Molecule 0.1 support must understand the contract
defined by this RFC.

In particular, it must understand that:

- Molecule represents chemical identity;
- `smiles` is optional but non-empty when present;
- external identifiers are extensible;
- at least one chemical identification mechanism is required;
- raw SMILES equality is not defined as universal molecular equivalence;
- unknown future Molecule versions must not silently use the 0.1 semantics.

This distinction follows RFC-0008:

```text
generic transport compatibility
              !=
semantic interoperability
```

The portable conformance suite now provides an initial machine-readable way to
test that shared interpretation.

## 55. Open questions

The experiment leaves several questions intentionally unresolved.

### 55.1 Identifier scheme naming

Should OpenSmell define a registry or naming convention for common chemical
identifier schemes such as:

- InChIKey;
- PubChem CID;
- CAS;
- ChEBI?

### 55.2 InChI as a first-class field

Should future Molecule versions include fields such as:

```text
inchi
inchikey
```

or should they remain ExternalIdentifier entries?

### 55.3 Chemical equivalence

Should OpenSmell ever define canonical chemical identity rules, or should this
remain the responsibility of specialized chemistry tooling?

### 55.4 Resource IDs

Should Molecule imports adopt a standardized RFC-0006 deterministic identity
profile?

### 55.5 Dataset provenance

Should provenance be:

- attached directly to Molecule;
- represented as an extension;
- represented as a separate graph resource?

### 55.6 Semantic annotations

What is the correct generic graph model for attaching semantic annotations to a
Molecule or another arbitrary resource without incorrectly modeling dataset
annotations as experimental observations?

### 55.7 Default registration

Should future OpenSmell implementations automatically register standardized
OpenSmell Resource Types, or should applications explicitly choose the
contracts they understand?

### 55.8 Normalization rules

Should future stable Resource Type specifications explicitly define which
optional empty fields may be omitted during serialization?

### 55.9 Additional chemical datasets

Does the Molecule 0.1 contract remain practical when applied to datasets with:

- duplicate structures;
- missing SMILES;
- InChI-only identity;
- stereochemistry;
- salts;
- mixtures;
- disconnected structures;
- database-specific identifiers?

## 60. Decision requested

RFC-0009 proposes retaining the following experimental Resource Type contract:

```text
Resource Type ID:
    org.opensmell.molecule

Resource Type Version:
    0.1
```

with the central semantic rule:

> **A Molecule resource represents chemical identity, not odor perception,
> experimental observation, or rendering behavior.**

It also retains the RFC-0008 extensibility rule:

> **Implementations that do not understand a Molecule Resource Type Version
> should preserve it generically rather than silently interpreting it using a
> different version.**

- a Molecule-specific JSON Schema can describe the resource contract without

Acceptance of RFC-0009 as Draft does not make Molecule 0.1 normative.

It records the contract and the evidence produced by the current experiments so
that subsequent interoperability, scientific-data, identity, annotation, and
resource-model work can refine or reject it explicitly.
