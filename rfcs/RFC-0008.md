# RFC-0008: Generic Resource Graph and Extensible Resource Types

- **Status:** Draft
- **Version:** 0.1
- **Date:** 2026-09-04
- **Authors:** OpenSmell contributors
- **Discussion:** OpenSmell project repository
- **Target:** Experimental OpenSmell resource model
- **Depends on:** RFC-0006, RFC-0007
- **Does not modify:** OpenSmell Core 0.1

---

## 1. Abstract

This RFC proposes a generic and extensible resource graph model for OpenSmell.

RFC-0007 introduced an experimental graph capable of representing stimuli,
observation targets, observations, references, identifiers, conditions, and
typed results. That model demonstrated that heterogeneous olfactory research
data can be represented as a flat graph of independently identified resources.

However, the RFC-0007 prototype has one important architectural limitation:
the graph and its parser explicitly know the complete set of supported resource
types.

At the time of RFC-0007, these types are:

- `stimulus`
- `observation_target`
- `observation`

This approach works for a bounded prototype, but it does not scale to an open
interoperability framework.

Future OpenSmell applications may need to represent resources such as:

- molecules;
- mixtures;
- odorants;
- sensors;
- sensor arrays;
- devices;
- subjects;
- experimental sessions;
- datasets;
- physical samples;
- rendering recipes;
- provenance records;
- calibration resources;
- or application-specific resources not defined by OpenSmell.

Requiring the graph implementation to be modified every time a new resource
type is introduced would make the graph itself a closed type system.

This RFC therefore proposes that the graph layer know only the minimum
resource contract required for graph participation, while resource-specific
interpretation is delegated to an extensible resource type registry.

The central principle is:

> **A ResourceGraph MUST NOT require knowledge of every resource type that it
> transports.**

Unknown resource types remain valid transportable resources and SHOULD be
preserved without loss when their contents are structurally compatible with
the generic resource envelope.

Known resource types MAY be interpreted through registered type handlers.

This design separates:

1. resource identity;
2. graph membership;
3. resource type identification;
4. type-specific interpretation;
5. forward-compatible transport.

The proposal is currently experimental and does not modify OpenSmell Core 0.1
or the RFC-0007 ResourceGraph format.

---

## 2. Motivation

OpenSmell is intended to act as an interoperability layer between heterogeneous
digital olfaction systems.

Such systems do not necessarily share the same internal data model.

A molecular dataset may describe chemical entities.

A psychophysical experiment may describe stimuli, subjects, and perceptual
measurements.

A biological experiment may describe physiological observations.

An electronic nose may describe sensor arrays and feature vectors.

A rendering system may eventually describe mixtures, cartridges, devices, or
rendering capabilities.

The interoperability layer therefore cannot reasonably assume that all useful
resource types are known when a version of the graph specification is
published.

A closed graph model would produce the following dependency:

```text
new resource type
        |
        v
modify ResourceGraph
        |
        v
modify parser
        |
        v
modify serializer
        |
        v
release new graph implementation
```

This is undesirable.

The graph should instead provide stable transport infrastructure:

```text
new resource type
        |
        v
register type handler
        |
        v
existing graph infrastructure
```

And when no handler exists:

```text
unknown resource type
        |
        v
generic representation
        |
        v
preserve
        |
        v
forward unchanged
```

This allows OpenSmell implementations with different knowledge and capabilities
to exchange the same graph document.

---

## 3. Relationship to RFC-0007

RFC-0007 defines the current experimental Stimulus and Observation Resource
Model.

Its Python prototype uses a closed resource union conceptually equivalent to:

```python
Resource = Stimulus | ObservationTarget | Observation
```

The RFC-0007 parser dispatches explicitly on the resource `type`.

Conceptually:

```python
if resource_type == "stimulus":
    ...
elif resource_type == "observation_target":
    ...
elif resource_type == "observation":
    ...
else:
    raise ValueError(...)
```

This behavior is intentionally retained in the RFC-0007 implementation.

RFC-0008 does not retroactively change RFC-0007.

Instead, RFC-0008 explores a successor architecture in a separate experimental
module.

The separation is intentional.

It allows the project to evaluate the generic model without changing the
behavior, conformance evidence, serialization rules, or interoperability
vectors already established for RFC-0007.

---

## 4. Scope

RFC-0008 concerns:

- generic graph membership;
- resource identity within a graph;
- resource type identification;
- extensible resource type registration;
- typed parsing;
- typed serialization;
- unknown resource preservation;
- coexistence of known and unknown resources;
- reference resolution across resource types;
- generic graph document serialization.

RFC-0008 does not define:

- a universal ontology of olfactory resources;
- molecule semantics;
- mixture semantics;
- device semantics;
- rendering semantics;
- hardware control;
- odor generation algorithms;
- scheduling;
- scientific truth of resource contents;
- automatic conversion between resource types;
- semantic equivalence between resources;
- canonical JSON serialization;
- cryptographic identity;
- distributed resource resolution;
- network retrieval;
- access control.

Those concerns may be addressed by separate specifications or future RFCs.

## 5. Design principles

### 5.1 The graph is not an ontology

The graph provides transport and identity infrastructure.

It MUST NOT require a complete ontology of everything that can participate in
digital olfaction.

---

### 5.2 Resource identity is separate from resource interpretation

A graph may know that a resource has the identifier:

```text
molecule-42
```

without understanding what the resource means.

Identity and interpretation are separate concerns.

---

### 5.3 Unknown does not mean invalid

A resource type unknown to one implementation may be understood by another.

Therefore:

> An unknown resource type MUST NOT be rejected solely because its type is
> unknown.

This principle mirrors the forward-compatible treatment of unknown
representation schemes elsewhere in OpenSmell.

---

### 5.4 Preservation is distinct from interpretation

An implementation may be unable to interpret a resource while still being
able to preserve and retransmit it.

For example:

```json
{
  "type": "org.example.sensor-array",
  "id": "sensor-42",
  "channels": 64,
  "manufacturer": "Example"
}
```

An OpenSmell implementation that does not understand
`org.example.sensor-array` should still be able to transport this object.

---

### 5.5 Type-specific validation belongs outside the generic graph

The generic graph should enforce graph-level invariants.

A type handler should enforce resource-specific invariants.

For example:

```text
GenericResourceGraph
    |
    +-- unique resource IDs
    +-- resource has an ID
    +-- graph envelope rules

Resource type handler
    |
    +-- molecule fields
    +-- sensor fields
    +-- stimulus fields
    +-- observation fields
```

This prevents the graph layer from becoming coupled to every future resource
definition.

---

## 6. Terminology

### 6.1 Resource

A **Resource** is an independently identifiable object participating in an
OpenSmell resource graph.

A resource has at least a Resource ID.

Serialized resources also have a textual resource type.

---

### 6.2 Resource ID

A **Resource ID** identifies a resource within the graph.

RFC-0008 does not replace the identifier work explored in RFC-0006.

The current prototype requires Resource IDs to be non-empty strings.

A future specification MAY impose stronger identifier requirements.

---

### 6.3 Resource type

A **Resource type** is identified by a stable textual **Resource Type ID** and,
for newly defined RFC-0008 resource contracts, a separate **Resource Type
Version**.

New RFC-0008 Resource Type IDs use namespaced, reverse-domain-style identifiers
such as:

```text
org.opensmell.molecule
org.opensmell.mixture
org.example.sensor-array
```

The Resource Type ID identifies the conceptual resource type. The Resource Type
Version identifies the version of the portable contract used to interpret that
type.

For example:

```text
Resource Type ID:      org.example.sensor-array
Resource Type Version: 0.1
```

RFC-0007 legacy resource type names remain unchanged for compatibility:

```text
stimulus
observation_target
observation
```

RFC-0008 does not retroactively rename or version those RFC-0007 serialized
types.

---

### 6.4 Known resource type

A **known resource type** is a resource type for which an implementation has a
registered type handler.

"Known" is therefore implementation-dependent.

A resource may be known to one implementation and unknown to another.

---

### 6.5 Unknown resource type

An **unknown resource type** is a syntactically valid resource type for which
the implementation has no registered type handler.

Unknown resource types are not inherently invalid.

---

### 6.6 GenericResource

`GenericResource` is the experimental Python representation used to preserve a
resource whose type/version contract is not understood by the current implementation.

It promotes three envelope fields for newly defined RFC-0008 resources:

```text
id
type
type_version
```

`type_version` may be absent only where the serialized contract intentionally uses
an unversioned compatibility form, such as the RFC-0007 compatibility handlers.

and preserves the remaining resource members as generic JSON-compatible data.

---

### 6.7 Resource type handler

A **Resource type handler** associates:

1. a textual Resource Type ID;
2. an optional Resource Type Version;
3. a Python resource class;
4. a parser;
5. a serializer.

Conceptually:

```text
(resource type, type version)
              |
              v
     ResourceTypeHandler
              |
              +-- Python type
              +-- parser
              +-- serializer
```

---

### 6.8 ResourceTypeRegistry

A **ResourceTypeRegistry** stores resource type handlers and performs version-aware
mapping between portable `(type, type_version)` contracts and
implementation-specific resource models. RFC-0007 compatibility handlers remain
unversioned.

---

## 7. Generic resource contract

The graph layer intentionally uses a minimal resource contract.

At runtime, the current experimental Python graph requires each resource
object to expose:

```text
id
```

where `id` is a non-empty string.

Conceptually:

```python
class ResourceLike:
    id: str
```

The graph itself does not need to know whether that object represents:

- a stimulus;
- an observation;
- a molecule;
- a sensor;
- a mixture;
- or a future application-defined resource.

This is a deliberate architectural boundary.

---

## 8. Serialized generic resource envelope

The currently implemented experimental envelope requires:

```json
{
  "type": "resource-type",
  "id": "resource-id"
}
```

For newly defined RFC-0008 resource types, this RFC adopts the following target
portable envelope:

```json
{
  "type": "org.example.resource-type",
  "type_version": "0.1",
  "id": "resource-id"
}
```

Additional members MAY be present.

For example:

```json
{
  "type": "org.example.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO"
}
```

The target RFC-0008 envelope reserves `type`, `type_version`, and `id`.

RFC-0007 resources reused through compatibility handlers retain their existing
RFC-0007 serialized representation. In particular, RFC-0008 does not add
`type_version` to `stimulus`, `observation_target`, or `observation`.

The naming/versioning policy is specified here before its implementation in the
experimental Python model.

---

## 9. Resource `id`

The `id` member identifies the resource.

In the current prototype:

- it MUST be a string;
- it MUST NOT be empty.

Example:

```json
{
  "type": "org.example.molecule",
  "id": "molecule-1"
}
```

The graph MUST reject duplicate Resource IDs within the same graph.

For example, this is invalid at the graph-semantic level:

```json
{
  "resources": [
    {
      "type": "stimulus",
      "id": "shared-id"
    },
    {
      "type": "org.example.molecule",
      "id": "shared-id"
    }
  ]
}
```

The uniqueness rule applies across resource types.

Resource type does not create a separate ID namespace.

---

## 10. Resource type identity and version

### 10.1 Resource Type ID

For newly defined RFC-0008 resource types, the `type` member is a stable
Resource Type ID.

It MUST be a non-empty namespaced string and MUST remain independent from the
Resource Type Version.

OpenSmell-defined resource types use:

```text
org.opensmell.*
```

Examples:

```text
org.opensmell.molecule
org.opensmell.mixture
org.opensmell.sensor-array
```

The `org.opensmell.*` namespace is reserved for resource types defined by the
OpenSmell project.

Third-party specifications SHOULD use a reverse-domain-style namespace derived
from a namespace they control. An organization controlling `example.org`, for
example, could define:

```text
org.example.sensor-array
org.example.calibration
```

This reduces collision risk without requiring OpenSmell to operate a central
registry for every third-party resource type.

A third party MUST NOT define a new type inside `org.opensmell.*` unless that
type is defined by the OpenSmell project.

The generic graph MUST NOT require Resource Type IDs to belong to a closed
enumeration.

### 10.2 Resource Type Version

New RFC-0008 resource types use a separate `type_version` member.

It MUST be a non-empty string identifying the version of the portable contract
associated with `type`.

For example:

```json
{
  "type": "org.example.sensor-array",
  "type_version": "0.1",
  "id": "sensor-1"
}
```

The pair:

```text
(type, type_version)
```

identifies the portable resource contract used to interpret the resource.

The Resource Type ID remains stable while its contract evolves. A version MUST
NOT be embedded into the Resource Type ID merely to express a new version of the
same conceptual resource type.

RFC-0008 therefore prefers:

```text
type = org.example.sensor-array
type_version = 1.0
```

over:

```text
type = org.example.sensor-array.v1
```

when both describe versions of the same resource type.

### 10.3 Version semantics

RFC-0008 separates type identity from version but does not yet impose Semantic
Versioning or another universal version grammar.

A specification defining a resource type MUST document the versions it defines,
their meaning, compatibility expectations, and any migration rules it provides.

Until a stronger grammar is standardized, `type_version` is an opaque non-empty
string to the generic transport layer.

The graph MUST NOT infer compatibility merely from lexical or numeric similarity
between version strings. For example, it does not assume that `0.2` is backward
compatible with `0.1`.

Compatibility is defined by the resource type specification or its handler.

### 10.4 RFC-0007 compatibility

RFC-0007 already serializes:

```text
stimulus
observation_target
observation
```

without a separate Resource Type Version.

Those names and serialized shapes remain unchanged.

RFC-0008 compatibility handlers may continue to reuse the RFC-0007 models and
serializers. Their absence of `type_version` is a legacy compatibility rule,
not the model recommended for newly defined RFC-0008 resource types.

RFC-0008 does not reinterpret `stimulus` as `org.opensmell.stimulus` and does
not silently rewrite one form into the other.

If OpenSmell later defines a namespaced successor to an RFC-0007 resource type,
the relationship and migration rules MUST be specified explicitly.

## 11. GenericResource model

The experimental Python prototype represents unknown resource types using:

```python
@dataclass
class GenericResource:
    id: str
    type: str
    type_version: str | None = None
    data: dict[str, Any] = field(default_factory=dict)
```

For example:

```json
{
  "type": "org.example.molecule",
  "type_version": "0.1",
  "id": "molecule-1",
  "smiles": "CCO",
  "source": {
    "database": "example"
  }
}
```

may be represented conceptually as:

```python
GenericResource(
    id="molecule-1",
    type="org.example.molecule",
    type_version="0.1",
    data={
        "smiles": "CCO",
        "source": {
            "database": "example"
        }
    }
)
```

The `data` mapping MUST NOT contain the reserved members:

```text
id
type
type_version
```

because those members are represented explicitly.

---

## 12. Unknown resource preservation

An implementation parsing an unknown resource type SHOULD preserve all
JSON-compatible members that it does not interpret.

Given:

```json
{
  "type": "org.example.future-sensor",
  "type_version": "0.1",
  "id": "sensor-1",
  "channels": 64,
  "future.extension": {
    "enabled": true,
    "values": [1, 2, 3]
  }
}
```

an implementation that does not recognize the `(org.example.future-sensor, 0.1)` contract should be able to
produce an equivalent resource when serialized again.

Conceptually:

```text
JSON
 |
 v
GenericResource
 |
 v
JSON
```

with semantic equality of the resource object.

Key ordering is not significant.

Canonical textual JSON equality is not required by this RFC.

---

## 13. Ownership of preserved data

The experimental implementation recursively copies generic JSON-compatible
payload data.

This prevents mutations of the caller's original dictionary from silently
modifying the parsed resource.

Similarly, serialization produces independent JSON-compatible structures.

This behavior is an implementation safety property rather than a universal
serialization requirement.

Implementations in other languages MAY use immutable data structures or other
ownership models.

---

## 14. Resource type registry

The experimental `ResourceTypeRegistry` provides an extensible mapping between
serialized resource types and implementation-specific resource models.

Conceptually:

```text
"stimulus"
    |
    v
Stimulus handler
    |
    +-- Stimulus class
    +-- parser
    +-- serializer
```

A handler contains conceptually:

```text
resource_type
type_version
python_type
parser
serializer
```

`type_version` is `None` for explicitly unversioned compatibility handlers.

The registry is not serialized into the graph document.

It is an implementation capability.

---

## 15. Default registry

The current prototype creates a default registry containing the three resource
types already defined by the RFC-0007 implementation:

```text
stimulus
observation_target
observation
```

This allows the generic graph prototype to reuse the existing RFC-0007 models
and serializers instead of duplicating their semantics.

---

## 16. Registering future resource types

Additional resource types may be installed without modifying the generic graph
implementation.

Conceptually:

```python
registry.register(
    "org.example.resource",
    ExampleResource,
    example_resource_from_dict,
    example_resource_to_dict,
    type_version="0.1",
)
```

After registration:

```json
{
  "type": "org.example.resource",
  "type_version": "0.1",
  "id": "example-1",
  "value": "hello"
}
```

may be parsed as:

```text
ExampleResource
```

instead of:

```text
GenericResource
```

This is the central extensibility mechanism explored by RFC-0008.

---

## 17. Interpretation depends on registry capabilities

The same serialized resource may have different in-memory representations in
different implementations.

Without a handler:

```text
{
  type: example.resource,
  id: example-1
}
        |
        v
GenericResource
```

With a handler:

```text
{
  type: example.resource,
  id: example-1
}
        |
        v
ExampleResource
```

Both implementations may still preserve the same serialized resource.

Therefore:

> The Python class used to represent a resource is not part of the portable
> OpenSmell data model.

The portable contract is the serialized resource representation.

---

## 18. Registry constraints

The current prototype rejects ambiguous registrations.

A registry MUST NOT register two handlers for the same `(resource_type, type_version)` contract.

For example:

```text
(example.resource, 0.1) -> Handler A
(example.resource, 0.1) -> Handler B
```

is ambiguous and is rejected.

The current prototype also prevents one Python class from being registered under
multiple portable handler contracts in the same registry.

This keeps serialization deterministic with respect to resource type
selection.

Future implementations MAY support more sophisticated dispatch systems, but
they MUST avoid ambiguous serialization behavior.

---

## 19. Parser contract

A registered parser receives the serialized resource object.

It is responsible for interpreting and validating type-specific fields.

The parser MUST return an instance compatible with the Python type associated
with the handler.

If a handler declares:

```text
resource type: example.resource
Python type: ExampleResource
```

but its parser returns:

```text
Stimulus
```

the current prototype rejects the result.

This protects the registry from internally inconsistent handlers.

---

## 20. Serializer contract

A registered serializer converts a typed resource into a serialized resource
object.

The resulting object MUST contain a `type` equal to the textual Resource Type ID
registered for the handler.

For a versioned RFC-0008 handler, the resulting object MUST also contain a
`type_version` equal to the Resource Type Version registered for the handler.
An explicitly unversioned compatibility handler MUST retain its unversioned
serialized contract.

The resulting object MUST contain an `id` equal to the Resource ID of the
input resource.

For example, a serializer registered for:

```text
(org.example.resource, 0.1)
```

must not emit:

```json
{
  "type": "different.resource",
  "id": "example-1"
}
```

Similarly, serializing a resource with:

```text
id = example-1
```

must not silently produce:

```text
id = example-2
```

These checks protect graph identity across serialization.

---

## 21. GenericResourceGraph

The experimental graph is conceptually:

```python
GenericResourceGraph(
    resources=[...],
    extra={...},
)
```

It is a flat collection of independently identified resources.

The graph validates graph-level invariants without requiring knowledge of all
resource classes.

The central runtime requirement is:

```text
resource.id -> non-empty string
```

The graph does not maintain a closed whitelist such as:

```text
Stimulus
ObservationTarget
Observation
```

This is a deliberate difference from the original RFC-0007 prototype.

---

## 22. Graph membership and serialization capability are separate

A resource may satisfy the structural runtime contract of the graph while no
serializer is installed for its Python class.

For example:

```python
@dataclass
class ExampleResource:
    id: str
    value: str
```

may participate in:

```python
GenericResourceGraph(
    resources=[
        ExampleResource(
            id="example-1",
            value="hello",
        )
    ]
)
```

because it satisfies the graph identity contract.

However, serialization requires a registered handler.

Without one, serialization fails.

This distinction is intentional:

```text
graph membership
      !=
serialization capability
```

The graph should not invent a portable representation for arbitrary
implementation-specific objects.

---

## 23. Known and unknown resources may coexist

A graph may contain typed and generic resources simultaneously.

Example:

```text
GenericResourceGraph
 |
 +-- ExampleResource
 |
 +-- Stimulus
 |
 +-- Observation
 |
 +-- GenericResource(future.sensor)
```

No separate graph is required for unknown resources.

This allows partial understanding of a document.

The prototype's graph query helpers are registry-aware. For example:

```python
graph.known_resources(registry=registry)
graph.unknown_resources(registry=registry)
graph.resources_with_type(
    "example.resource",
    registry=registry,
)
```

For typed Python resources, whether a resource is known and which serialized
resource type it has are determined by the supplied registry. A custom typed
resource therefore becomes queryable without modifying `GenericResourceGraph`.

`GenericResource` instances retain their explicit serialized `type`, so they
remain queryable by type even when no typed handler exists.

The registry is supplied to the query operation rather than stored as graph
state. The same graph can therefore be inspected using different implementation
capabilities.

---

## 24. References across resource types

References identify resources by Resource ID.

Reference resolution does not require the target resource to have a known
type.

For example:

```json
{
  "type": "org.example.molecule",
  "id": "molecule-1",
  "smiles": "CCO"
}
```

may be unknown to an implementation and therefore represented as a
`GenericResource`.

A known stimulus may still reference it:

```json
{
  "type": "stimulus",
  "id": "stimulus-1",
  "source": {
    "resource_id": "molecule-1"
  }
}
```

The graph can resolve:

```text
stimulus.source
       |
       v
molecule-1
       |
       v
GenericResource
```

without understanding molecule semantics.

This demonstrates an important separation:

> Reference resolution depends on identity, not type interpretation.

---

## 25. Unresolved references

As in RFC-0007, unresolved references remain permitted by the experimental
graph.

For example:

```json
{
  "type": "stimulus",
  "id": "stimulus-1",
  "source": {
    "resource_id": "external-or-missing-resource"
  }
}
```

may exist even when the referenced resource is not present in the graph.

Therefore:

```text
reference exists
```

does not imply:

```text
reference resolves locally
```

Applications requiring complete closed graphs MAY impose stronger validation
rules.

---

## 26. Generic graph document envelope

The current experimental prototype uses the document format identifier:

```text
org.opensmell.experimental.generic-resource-graph
```

with version:

```text
0.1
```

A minimal document is:

```json
{
  "format": "org.opensmell.experimental.generic-resource-graph",
  "version": "0.1",
  "resources": []
}
```

A mixed example is:

```json
{
  "format": "org.opensmell.experimental.generic-resource-graph",
  "version": "0.1",
  "resources": [
    {
      "type": "org.example.molecule",
      "id": "molecule-1",
      "smiles": "CCO"
    },
    {
      "type": "stimulus",
      "id": "stimulus-1",
      "source": {
        "resource_id": "molecule-1"
      }
    },
    {
      "type": "future.sensor-array",
      "id": "sensor-1",
      "channels": 64
    }
  ]
}
```

---

## 27. Document extensions

Members other than:

```text
format
version
resources
```

are treated as document-level extensions by the current prototype.

For example:

```json
{
  "format": "org.opensmell.experimental.generic-resource-graph",
  "version": "0.1",
  "future.document": {
    "preserve": true
  },
  "resources": []
}
```

The prototype preserves such members through document round-trips.

When serializing the in-memory model, official envelope fields take precedence
over conflicting extension data.

This follows the extension-preservation approach already explored elsewhere in
OpenSmell.

---

## 28. Strict JSON

The experimental JSON text serializer uses standard JSON.

Non-standard numeric constants such as:

```text
NaN
Infinity
-Infinity
```

are rejected by the strict text parser.

Serialization also rejects non-finite floating-point values rather than
emitting non-standard JSON tokens.

This is consistent with the strict JSON behavior established by the
RFC-0007 experimental serialization work.

---

## 29. Structural validity versus semantic validity

RFC-0008 retains an important distinction established during RFC-0007
conformance work.

### 29.1 Structural validity

Structural validity concerns the shape and primitive types of serialized data.

Examples include:

- `resources` is an array;
- `id` is a string;
- `type` is a string.

---

### 29.2 Graph-semantic validity

Graph-semantic validity concerns relationships and invariants across the
document.

For example:

- Resource IDs are unique.

A JSON Schema may validate structural shape without expressing all graph-level
semantic constraints.

---

### 29.3 Type-specific validity

Type-specific validity is defined by the resource type handler or the
specification defining that resource type.

For example:

```text
org.example.molecule
```

may define requirements unknown to the generic graph.

The generic graph MUST NOT pretend to validate semantics it does not
understand.

---

## 30. Preservation versus validity

Acceptance and preservation are different properties.

A parser may accept:

```json
{
  "type": "future.resource",
  "id": "future-1",
  "extension": {
    "value": 42
  }
}
```

without guaranteeing that `extension` survives serialization.

Therefore conformance testing SHOULD distinguish:

```text
acceptance
```

from:

```text
preservation
```

The RFC-0008 prototype explicitly tests unknown-resource round-trip
preservation.

---

## 31. Forward compatibility

Forward compatibility is a primary motivation for this RFC.

Consider implementation A, released before the resource type:

```text
org.opensmell.sensor-array
```

exists.

Implementation A receives:

```json
{
  "type": "org.opensmell.sensor-array",
  "id": "sensor-1",
  "channels": 64
}
```

It does not understand the type.

It preserves it as a generic resource.

Later, implementation B includes a handler for:

```text
org.opensmell.sensor-array
```

The same serialized object can now become a typed resource.

No graph format migration is required solely because the implementation gained
knowledge of the type.

---

## 32. Third-party extensibility

The registry mechanism is not limited to resource types standardized by
OpenSmell.

Third parties may define application-specific resource types.

For example:

```text
org.example.custom-sensor
```

A third-party package could provide:

```text
parser
serializer
typed model
```

and register them with an OpenSmell implementation.

The graph itself does not need to be modified.

This property is important for an interoperability framework because the set of
future olfactory applications cannot be fully predicted by the core project.

---

## 33. Resource type naming and ownership

RFC-0008 adopts namespaced Resource Type IDs for newly defined resource types.

OpenSmell-defined types use:

```text
org.opensmell.<name>
```

The `org.opensmell.*` namespace is reserved for OpenSmell-defined resource
types.

Third parties SHOULD use reverse-domain-style namespaces based on a namespace
they control, for example:

```text
org.example.sensor-array
com.example.device
```

This policy is decentralized. OpenSmell does not need to approve or centrally
register every third-party resource type.

Namespace ownership identifies who is responsible for defining the portable
semantics of a resource type. It does not imply that OpenSmell endorses,
validates, or trusts resources in that namespace.

RFC-0007 names remain `stimulus`, `observation_target`, and `observation` for
compatibility. They are not renamed by RFC-0008.

Resource Type Version is separate from Resource Type ID. A version change alone
does not create a new namespace or Resource Type ID.

---

## 34. Generic resources are not opaque byte blobs

The current prototype preserves unknown resources as parsed JSON-compatible
data.

This means an implementation understands the generic JSON structure even when
it does not understand the resource semantics.

For example, it may preserve:

```json
{
  "type": "future.resource",
  "id": "future-1",
  "payload": {
    "a": 1,
    "b": [2, 3]
  }
}
```

without knowing what `payload` means.

This design enables normal JSON tooling while retaining forward compatibility.

It does not provide byte-for-byte preservation of the original JSON text.

Whitespace, object member ordering, numeric lexical forms, and other textual
details are not guaranteed to survive.

---

## 35. Semantic round-trip

For the purposes of the current experiment, preservation means semantic
dictionary equality after:

```text
serialized object
       |
       v
parse
       |
       v
in-memory resource
       |
       v
serialize
```

It does not mean textual equality of JSON bytes.

For example:

```json
{"type":"future.resource","id":"x","value":1}
```

and:

```json
{
  "id": "x",
  "value": 1,
  "type": "future.resource"
}
```

are equivalent for the purposes of this model.

---

## 36. Relationship to result schemes

RFC-0007 already separates Observation Result structure from Result Scheme
semantics.

Conceptually:

```text
Result
 |
 +-- scheme
 +-- data
```

RFC-0008 applies a related extensibility principle one level higher.

Conceptually:

```text
Resource
 |
 +-- type
 +-- type-specific fields
```

However, resource types and result schemes are distinct concepts.

A resource type identifies the kind of graph resource.

A Result Scheme identifies how a result payload is interpreted.

They MUST NOT be treated as interchangeable namespaces.

---

## 37. Relationship to OpenSmell Core representations

OpenSmell Core 0.1 already permits multiple representation types and schemes
for an odor.

RFC-0008 does not replace that model.

Core representations describe odor information.

Generic graph resources describe independently identifiable entities that may
participate in datasets, experiments, observations, or future interoperability
workflows.

The two layers may eventually be connected, but this RFC does not define that
integration.

---

## 38. Relationship to RFC-0006 identifiers

RFC-0006 explores deterministic and portable resource identification,
including UUID-based approaches and structured source identity.

RFC-0008 does not finalize those identifier rules.

The current generic graph prototype requires only a non-empty string Resource
ID.

This allows the graph architecture to be evaluated independently from the
final identifier policy.

A future specification may tighten the Resource ID syntax without changing the
core extensibility principle described by this RFC.

---

## 47. Compatibility

RFC-0008 currently defines a separate experimental document format:

```text
org.opensmell.experimental.generic-resource-graph
```

It does not redefine the RFC-0007 envelope:

```text
org.opensmell.experimental.resource-graph
```

This means existing RFC-0007 documents, tests, and interoperability vectors
retain their existing interpretation.

A future RFC may define a migration path or adopt the generic architecture as a
successor to RFC-0007.

That decision is explicitly outside the current draft.

---

## 48. Why not modify RFC-0007 directly?

RFC-0007 has already accumulated implementation and interoperability evidence.

Changing its unknown-resource behavior would make it difficult to distinguish:

```text
RFC-0007 behavior
```

from:

```text
new experimental behavior
```

Keeping RFC-0008 separate allows both designs to be evaluated independently.

This is especially useful while resource type naming, schemas, registries, and
conformance rules remain experimental.

## 49. Security considerations

Unknown-resource preservation introduces several considerations.

### 49.1 Unknown data is untrusted data

Preserving an unknown resource MUST NOT imply trusting its contents.

Applications MUST treat unknown resource fields as untrusted input.

---

### 49.2 Interpretation must not happen accidentally

A generic resource SHOULD NOT trigger device operations, code execution,
network requests, or hardware behavior merely because a particular field name
is present.

Semantic behavior requires an implementation that explicitly understands the
resource type.

---

### 49.3 Resource size

Implementations MAY impose resource, nesting, string, array, or document size
limits to protect against resource exhaustion.

Such implementation limits should be documented.

---

### 49.4 Recursive structures

JSON itself cannot directly contain object-reference cycles, but deeply nested
objects may still cause resource exhaustion.

Implementations MAY limit nesting depth.

---

### 49.5 Registered handlers

Resource type handlers are executable implementation components.

Installing a handler is therefore different from merely receiving an unknown
resource type.

Implementations SHOULD only load trusted handler code.

---

## 50. Interoperability considerations

The generic graph architecture improves forward transport compatibility, but
it does not automatically provide semantic interoperability.

Two implementations may both preserve:

```text
org.example.sensor
```

without agreeing on what its fields mean.

True semantic interoperability for a resource type requires a shared
specification for that type.

Therefore:

```text
generic transport compatibility
              !=
semantic understanding
```

RFC-0008 provides infrastructure on which type-specific interoperability can
be built.

---

## 51. Conformance direction

A future normative version of this work should define separate conformance
layers.

Possible layers include:

### 51.1 Generic graph structural conformance

Tests document envelope structure and generic resource requirements.

### 51.2 Generic graph semantic conformance

Tests Resource ID uniqueness and other graph-wide invariants.

### 51.3 Preservation conformance

Tests whether unknown resource data survives parse/serialize round-trips.

### 51.4 Registered type conformance

Tests the semantics of individual standardized resource types.

### 51.5 Cross-language interoperability

Tests whether independent implementations preserve the same generic resources
and dispatch known resource types consistently.

These layers SHOULD remain distinguishable.

---

## 52. Future JSON Schema

RFC-0008 does not yet standardize a JSON Schema for the generic graph envelope.

A future experimental schema could require resources to contain at least:

```json
{
  "type": "...",
  "id": "..."
}
```

while allowing additional properties.

Conceptually:

```json
{
  "type": "object",
  "required": ["type", "id"],
  "properties": {
    "type": {
      "type": "string",
      "minLength": 1
    },
    "id": {
      "type": "string",
      "minLength": 1
    }
  },
  "additionalProperties": true
}
```

Such a schema must not enumerate all resource types if forward-compatible
unknown resources are to remain structurally valid.

Resource-specific schemas may be layered separately.

## 53. Open questions

The following questions remain intentionally unresolved.

### 53.1 Registry metadata

Should resource type handlers expose:

- schema identifiers;
- specification URLs;
- capabilities;
- validation functions;
- migration functions?

Resource Type ID and Resource Type Version are now part of the proposed portable
contract, but richer registry metadata remains unresolved.

---

### 53.2 Generic reference discovery

RFC-0007 can identify references in fields whose semantics it knows.

For unknown resource types, the generic graph cannot safely infer that an
arbitrary string is a Resource ID reference.

A future design may need an explicit generic reference mechanism.

---

### 53.3 Handler lifecycle

The current prototype assumes a registry is constructed before parsing.

Future implementations may need:

- plugin discovery;
- dynamic handler installation;
- immutable registries;
- application-specific registries;
- security policies.

---

### 53.4 Canonical serialization

RFC-0008 currently requires semantic preservation, not byte-level
canonicalization.

Canonical JSON may be useful later for hashing, signatures, content-addressed
identity, or reproducible fixtures.

That work is outside this RFC.

---

## 54. Non-goals

RFC-0008 deliberately does not attempt to make every possible resource
interoperable merely by wrapping it in:

```text
id
type
```

The envelope provides extensibility infrastructure.

The meaning of each standardized resource type still requires a specification.

Similarly, RFC-0008 does not claim that arbitrary third-party resource types
are mutually understandable.

It only allows them to coexist and survive transport without forcing the graph
layer to understand them.

---

## 55. Proposed requirements summary

If this architecture progresses toward a normative specification, the
following requirements are proposed.

1. Every serialized graph resource MUST have a non-empty Resource ID.
2. Every serialized graph resource MUST have a non-empty resource type.
3. Resource IDs MUST be unique within a graph.
4. The graph MUST NOT require knowledge of every resource type it transports.
5. A resource MUST NOT be rejected solely because its resource type is unknown.
6. Unknown resource contents SHOULD be preserved through parse/serialize
   round-trips.
7. Known resource types MAY be interpreted using registered type handlers.
8. Type-specific validation SHOULD be performed by the corresponding type
   specification or handler rather than by the generic graph.
9. Reference resolution MUST depend on Resource ID rather than requiring the
   target resource type to be understood.
10. Unresolved references MAY remain representable.
11. Serialization of implementation-specific typed resources MUST require a
    defined portable serialization mapping.
12. A serializer MUST preserve the resource's Resource ID.
13. A registered serializer MUST emit the resource type associated with its
    handler.
14. Implementations MUST NOT execute semantic behavior merely because unknown
    resource fields are present.
15. Generic transport compatibility MUST NOT be presented as proof of semantic
    interoperability.

## 56. Proposed architecture

The architecture explored by this RFC can be summarized as:

```text
                    OpenSmell Generic Resource Graph
                               |
          +--------------------+--------------------+
          |                    |                    |
          v                    v                    v
      Resource A           Resource B           Resource C
      type known           type known           type unknown
          |                    |                    |
          v                    v                    v
       handler              handler          GenericResource
          |                    |                    |
          v                    v                    |
      typed model          typed model              |
          |                    |                    |
          +--------------------+--------------------+
                               |
                               v
                       common graph identity
                               |
                               v
                         Resource IDs
```

Type interpretation is optional.

Graph identity is common.

---

## 57. Architectural consequence

The intended dependency direction is:

```text
GenericResourceGraph
        ^
        |
ResourceTypeRegistry
        ^
        |
resource type modules
```

and not:

```text
GenericResourceGraph
        |
        +-- knows Stimulus
        +-- knows Observation
        +-- knows Molecule
        +-- knows Sensor
        +-- knows Mixture
        +-- knows every future resource
```

The latter would recreate a closed graph architecture.

## 60. Decision requested

RFC-0008 proposes accepting the following architectural direction for further
experimentation:

> OpenSmell resource graphs should provide a stable, generic identity and
> transport layer while resource-specific semantics remain independently
> extensible.

More specifically:

> The graph should know that a resource exists and how it is identified without
> requiring the graph implementation to understand what every resource means.

And:

> Unknown resource types should remain transportable rather than becoming a
> compatibility failure.

Acceptance of this RFC as Draft does not make the experimental generic graph
format normative.

It records the architectural direction and the evidence produced by the
current prototype so that subsequent experiments can refine or reject it
explicitly.
