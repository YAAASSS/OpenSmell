# RFC-0011: Structural Reference Discovery and Graph Navigation

- Status: Draft
- Category: Experimental Graph Capability
- Version: 0.1
- Date: 2026-09-05
- Depends on: RFC-0006, RFC-0007, RFC-0008, RFC-0009, RFC-0010
- Modifies OpenSmell Core 0.1: No

## 1. Summary

This RFC explores a generic mechanism for discovering and navigating
structural references between resources contained in an RFC-0008
GenericResourceGraph.

The mechanism separates four concerns:

```text
Resource Type knowledge
        |
        v
ReferenceDiscoveryRegistry
        |
        v
structural Reference discovery
        |
        v
DiscoveredReference
        |
        v
ReferenceIndex
        |
        +-- outgoing navigation
        +-- incoming navigation
        +-- resolved references
        +-- unresolved references
```

A resource type that is understood by an implementation may register a
discoverer describing which of its fields are structural References.

Unknown or unregistered resource types remain transportable but
uninterpreted.

The mechanism deliberately does not scan arbitrary JSON payloads for fields
that happen to look like References.

This RFC is experimental and non-normative.

---

## 2. Motivation

RFC-0008 introduced an experimental GenericResourceGraph capable of
transporting heterogeneous resources, including Resource Types and Resource
Type Versions unknown to the receiving implementation.

RFC-0009 introduced the Molecule resource.

RFC-0010 introduced the Annotation resource and its structural `subject`
Reference.

RFC-0007 already contains structural relationships such as:

```text
Stimulus.source
Observation.stimulus
Observation.target
```

As heterogeneous graphs become more useful, applications need to answer
questions such as:

```text
What resources does this resource reference?

What resources reference this Molecule?

Which references are unresolved?

Which Annotation resources concern this resource?
```

RFC-0008 can resolve a Reference when the caller already possesses that
Reference, but the generic graph does not itself know where every Resource
Type stores its structural relationships.

A tempting implementation would recursively scan arbitrary resource JSON for
objects containing:

```json
{
  "resource_id": "some-resource"
}
```

That approach is unsafe.

Scheme-defined payloads, result data, extension data, or unknown future
resource structures may contain the same field name without declaring a
structural graph relationship.

This RFC therefore explores explicit structural reference discovery rather
than heuristic JSON inspection.

---

## 3. Design Principle

The central design principle of this RFC is:

> Structural relationships are discovered only when the implementation
> understands the resource type and explicitly knows how that type declares
> References.

Consequently:

- implementations MUST NOT infer structural graph relationships merely from
  JSON field names;
- arbitrary `data`, `extra`, `context`, or other opaque payloads MUST NOT be
  recursively scanned for Reference-like objects;
- unknown resources MUST remain transportable without requiring their
  relationships to be understood;
- an unregistered resource type MUST contribute no discovered structural
  references;
- unresolved structural References MUST remain discoverable;
- reference discovery MUST NOT require referenced targets to exist locally;
- discovery MUST remain separate from resource parsing and serialization.

This preserves the RFC-0008 principle that an implementation does not need
knowledge of every Resource Type transported by a graph.

---

## 4. Terminology

### 4.1 Structural Reference

A Structural Reference is a `Reference` occurring in a field whose Resource
Type contract declares that field to represent a graph relationship.

Examples in the current experiment include:

```text
Stimulus.source
Observation.stimulus
Observation.target
Annotation.subject
```

A Structural Reference may be resolved or unresolved.

### 4.2 Opaque Payload

An Opaque Payload is data whose interpretation belongs to another contract,
Scheme, extension, application, or unknown Resource Type.

Examples include:

```text
Observation Result.data
Observation.context
Annotation.data
resource extra fields
graph extra fields
GenericResource.data
```

An object inside an opaque payload does not become a Structural Reference
merely because it contains a key named `resource_id`.

### 4.3 Discovered Reference

A Discovered Reference associates:

```text
source Resource ID
+
original Reference
```

The referenced target is identified by:

```text
Reference.resource_id
```

The target resource does not need to exist in the graph.

### 4.4 Resolved Reference

A discovered reference is resolved when its target Resource ID exists in the
graph used for resolution.

### 4.5 Unresolved Reference

A discovered reference is unresolved when its target Resource ID does not
exist in that graph.

Unresolved does not mean invalid.

### 4.6 Reference Index

A ReferenceIndex is an indexed snapshot of discovered structural
relationships for one GenericResourceGraph.

It provides efficient incoming and outgoing navigation without repeatedly
rescanning all understood resources.

---

## 5. Separation from Resource Type Serialization

RFC-0008 uses a ResourceTypeRegistry to determine how known Resource Types
are parsed and serialized.

RFC-0011 deliberately explores a separate registry:

```text
ResourceTypeRegistry
    = parse / serialize resource contracts

ReferenceDiscoveryRegistry
    = discover structural relationships
```

These responsibilities MUST NOT be assumed to be equivalent.

Knowledge of how to serialize a resource does not necessarily imply knowledge
of which fields should participate in generic graph navigation.

Likewise, structural reference discovery does not define the serialized
resource contract.

The current experiment therefore does not modify RFC-0008
ResourceTypeRegistry or GenericResourceGraph.

---

## 6. ReferenceDiscoveryRegistry

A ReferenceDiscoveryRegistry associates an exact Python resource type with a
Reference discoverer.

Conceptually:

```text
Python Resource Type
        |
        v
Reference discoverer
        |
        v
list[Reference]
```

A discoverer receives one understood resource instance and returns the
Structural References declared by that Resource Type contract.

The current Python experiment uses exact Python type dispatch.

Subclasses are not implicitly interpreted as their parent Resource Type.

This avoids silently assigning relationship semantics to a type that has not
explicitly registered them.

### 6.1 Registration

An implementation MUST reject duplicate discovery registration for the same
exact implementation resource type.

A registered discoverer MUST return a collection containing only valid
Reference objects according to the implementation's resource model.

Invalid discoverer output MUST be rejected rather than interpreted
heuristically.

### 6.2 Unregistered Types

If a resource type has no registered discoverer, discovery MUST return no
Structural References for that resource.

The resource itself remains valid and transportable according to the
underlying GenericResourceGraph rules.

---

## 7. Current Known Resource Discovery Rules

The current experimental default registry understands five resource classes:

```text
Stimulus
ObservationTarget
Observation
Molecule
Annotation
```

Their discovery rules are:

| Resource | Structural References |
| --- | --- |
| Stimulus | `source`, when present |
| ObservationTarget | none |
| Observation | `stimulus`, followed by `target` when present |
| Molecule | none |
| Annotation | `subject` |

These rules describe only the current experimental contracts.

They do not imply that every future version of these Resource Types has the
same structural relationships.

Unknown future Resource Type Versions remain subject to RFC-0008 dispatch and
may therefore be represented as GenericResource until explicitly understood.

---

## 8. DiscoveredReference

The current experiment represents one discovered relationship as:

```text
DiscoveredReference
    source_id
    reference
```

`source_id` identifies the resource containing the Structural Reference.

`reference` is the original Reference object.

The target Resource ID is obtained from:

```text
reference.resource_id
```

Conceptually:

```text
source_id
    |
    v
Reference -----------------> target_id
                              |
                              +-- resource may exist
                              +-- resource may be absent
```

Reference extension fields remain part of the original Reference and MUST NOT
be discarded merely because the Reference has been discovered.

This RFC does not currently define a serialized DiscoveredReference format.

DiscoveredReference is a navigation result, not a new graph resource.

---

## 9. Discovery Order

Deterministic discovery order is useful for testing, interoperability
experiments, debugging, and predictable APIs.

The current experiment defines discovery order as follows:

1. resources are visited in GenericResourceGraph order;
2. each resource's Structural References are emitted in the order defined by
   that resource's registered discoverer.

For the current Observation contract:

```text
Observation.stimulus
Observation.target
```

the `stimulus` Reference is emitted before `target` when both exist.

Implementations following this experimental behavior SHOULD preserve this
order.

Discovery MUST NOT deduplicate identical References.

Two separately declared structural relationships remain two discoveries even
if they target the same Resource ID.

---

## 10. Unknown Resources

RFC-0008 allows unknown Resource Types and unknown Resource Type Versions to
be transported as GenericResource.

RFC-0011 preserves that property.

GenericResource is intentionally not interpreted by the default structural
reference discovery registry.

For example:

```json
{
  "type": "org.example.future-resource",
  "type_version": "7",
  "id": "future-1",
  "resource_id": "molecule-1",
  "nested": {
    "resource_id": "target-1"
  }
}
```

does not generically declare either value to be a Structural Reference.

The implementation does not know the Resource Type contract and therefore
does not know whether either field represents:

- a graph relationship;
- application data;
- provenance;
- an external identifier;
- a cached value;
- an unrelated domain concept.

Unknown means transportable, not interpretable.

---

## 11. Unknown Future Versions of Known Resource Types

Knowledge of one Resource Type Version MUST NOT be generalized to unknown
future versions.

For example, an implementation that understands:

```text
org.opensmell.annotation / 0.1
```

does not thereby understand:

```text
org.opensmell.annotation / 9.0
```

RFC-0008 may transport the latter as GenericResource.

RFC-0011 MUST NOT inspect that GenericResource as if it followed the
Annotation 0.1 structural contract.

This prevents an older implementation from assigning obsolete relationship
semantics to a future resource version.

---

## 12. Opaque Data Must Not Be Scanned

Structural discovery MUST NOT recursively scan arbitrary JSON for keys such
as:

```text
resource_id
subject
source
target
stimulus
```

For example:

```json
{
  "data": {
    "resource_id": "molecule-1"
  }
}
```

inside an Annotation does not create an additional Structural Reference.

Likewise:

```json
{
  "data": {
    "resource_id": "molecule-1"
  }
}
```

inside an Observation Result does not create a Structural Reference unless
the Result Scheme itself is interpreted by some separate, explicitly defined
mechanism.

The current generic discovery layer does not interpret such Scheme-defined
payloads.

The same rule applies to:

```text
Annotation.data
Observation Result.data
Observation.context
resource extensions
Reference extensions
Scheme extensions
graph extensions
GenericResource payloads
```

This rule is essential to avoid false graph edges.

---

## 13. Graph-Level Discovery

Graph-level discovery visits all resources in graph order and applies the
registered discoverer for each understood resource.

Conceptually:

```text
for resource in graph.resources:
    references = discover(resource)

    for reference in references:
        emit DiscoveredReference(
            source_id=resource.id,
            reference=reference
        )
```

Unknown and unregistered resources contribute no discoveries.

The operation does not require all targets to resolve.

Therefore a graph may produce:

```text
known source
    |
    +----> known target

known source
    |
    +----> missing target
```

in the same discovery pass.

---

## 14. Outgoing Navigation

Outgoing navigation answers:

> What Structural References originate from resource X?

Conceptually:

```text
references_from(source_id)
```

returns discovered relationships whose:

```text
source_id == requested source_id
```

If the source Resource ID does not occur in the graph, the current experiment
returns an empty collection.

A resource that exists but declares no Structural References also returns an
empty collection.

These cases are intentionally equivalent at this query layer.

Applications requiring a distinction may separately query the graph for the
source resource.

---

## 15. Incoming Navigation

Incoming navigation answers:

> What understood structural relationships point to Resource ID X?

Conceptually:

```text
references_to(target_id)
```

returns discovered relationships whose:

```text
reference.resource_id == target_id
```

The target Resource ID does not need to exist in the graph.

This is important for unresolved-reference analysis.

For example:

```text
Annotation
    |
    +---- subject ----> external-resource-42
                        |
                        +-- absent locally
```

may still be returned by:

```text
references_to("external-resource-42")
```

---

## 16. Resolution

RFC-0008 GenericResourceGraph already provides Reference resolution against
the resources locally contained in the graph.

RFC-0011 does not redefine Resource ID resolution.

Instead, discovered relationships may be partitioned according to whether:

```text
graph.resolve(reference)
```

returns a resource.

Conceptually:

```text
discovered references
        |
        +-- resolved
        |
        +-- unresolved
```

Resolution is local to the graph.

An unresolved Reference may identify a valid resource managed externally or
transported separately.

Therefore unresolved References MUST NOT be treated as structurally invalid
merely because the target is absent.

---

## 17. ReferenceIndex

Repeated incoming queries would otherwise require rescanning every understood
resource in the graph.

The current experiment therefore introduces ReferenceIndex.

During construction, the index:

1. discovers all known Structural References once;
2. stores them in discovery order;
3. builds an outgoing index keyed by source Resource ID;
4. builds an incoming index keyed by target Resource ID;
5. records which discoveries are resolved;
6. records which discoveries are unresolved.

Conceptually:

```text
GenericResourceGraph
        |
        v
discover once
        |
        v
ReferenceIndex
   |        |
   |        +-- incoming[target_id]
   |
   +----------- outgoing[source_id]

   +----------- resolved
   +----------- unresolved
```

This changes navigation cost for repeated queries without changing serialized
graph data.

ReferenceIndex is an implementation/navigation facility, not a serialized
OpenSmell resource.

---

## 18. Snapshot Semantics

ReferenceIndex is a snapshot.

Its discovered relationships and resolved/unresolved partitions correspond to
the graph state observed during index construction.

If the graph is later mutated, the index MUST NOT be assumed to update
automatically.

For example:

```text
1. graph contains Annotation -> missing-resource
2. ReferenceIndex is built
3. missing-resource is added to graph
```

The index's stored unresolved partition still describes the state observed at
step 2.

Applications requiring an updated index should rebuild it.

### 18.1 Live Resolution Through the Underlying Graph

The current Python prototype retains the original graph and its `resolve`
operation.

Consequently, resolving an already discovered edge through the index may
consult the current graph even though the index's stored
resolved/unresolved partitions remain snapshots.

This distinction is experimental and MUST be documented by implementations
that expose equivalent behavior.

Future work may determine whether index resolution itself should also be
strictly snapshot-based.

## 19. Heterogeneous Graph Validation

The structural discovery architecture was tested with a deliberately
heterogeneous GenericResourceGraph containing:

```text
Molecule
Stimulus
ObservationTarget
Observation
Annotation
unresolved Annotation
unknown GenericResource
unknown future Annotation version as GenericResource
```

The intended structural relationships were:

```text
Molecule
   ^
   |
 source
   |
Stimulus
   ^
   |
 stimulus
   |
Observation -------- target --------> ObservationTarget

Annotation ---------- subject ------> Molecule

Annotation ---------- subject ------> missing-resource
                                      |
                                      +-- unresolved
```

The same graph deliberately contained false Reference-like JSON values inside:

```text
Molecule.extra
Stimulus.extra
ObservationTarget.extra
Observation Result.data
Observation Result.extra
Observation.context
Observation.extra
Annotation.data
Annotation.extra
GenericResource.data
graph.extra
```

It also contained a GenericResource using the known Annotation Resource Type
ID with an unknown future Resource Type Version.

Expected Structural References:

```text
Stimulus -> Molecule
Observation -> Stimulus
Observation -> ObservationTarget
Annotation -> Molecule
Annotation -> missing-resource
```

Observed discoveries:

```text
5
```

Observed false-positive discoveries:

```text
0
```

Observed resolved discoveries:

```text
4
```

Observed unresolved discoveries:

```text
1
```

The dedicated heterogeneous validation suite contained:

```text
18 tests
18 passed
0 failed
```

The complete Python regression suite after adding the heterogeneous test
contained:

```text
1,146 tests
1,146 passed
0 failed
```

A known local pytest cache-permission warning was unrelated to OpenSmell
behavior.

This experiment provides evidence that explicit type-aware structural
discovery can coexist with heterogeneous graph transport without heuristic
inspection of opaque data.

## 20. OdorNet Reference Navigation Validation

Before the heterogeneous graph experiment, ReferenceIndex was tested against
the complete enriched OdorNet graph experiment.

The graph contained:

```text
8,892 Molecule resources
8,892 Annotation resources
17,784 total resources
106,704 semantic annotation states
```

Each Annotation structurally referenced its corresponding Molecule.

The index discovered:

```text
8,892 structural references
8,892 unique source-target relationships
8,892 resolved references
0 unresolved references
```

Observed relationship errors:

```text
missing Annotation edges: 0
unexpected sources:       0
Molecule outgoing errors: 0
Annotation incoming edges: 0
false-edge/error count:   0
```

The experiment also demonstrated that repeated incoming and outgoing
navigation through the index was substantially faster than repeatedly
rescanning the full graph.

These performance measurements are implementation evidence only and do not
define normative performance requirements.

## 21. Relationship to Annotation

RFC-0010 defines:

```text
Annotation.subject
```

as a Reference to the resource being annotated.

RFC-0011 classifies that field as a Structural Reference for the understood
Annotation 0.1 resource contract.

Therefore:

```text
Annotation
    |
 subject
    |
    v
Resource
```

participates in generic structural graph navigation.

Annotation `data` does not.

For example:

```json
{
  "subject": {
    "resource_id": "molecule-1"
  },
  "data": {
    "resource_id": "not-a-structural-edge"
  }
}
```

produces exactly one Structural Reference under the current experiment:

```text
Annotation -> molecule-1
```

This preserves RFC-0010's distinction between the attachment mechanism and
Scheme-defined annotation data.

---

## 22. Relationship to Observation

The current RFC-0007 experimental Observation contract contains:

```text
stimulus
target
results
context
```

RFC-0011 treats:

```text
Observation.stimulus
Observation.target
```

as Structural References.

It does not generically inspect:

```text
Observation.results[*].data
Observation.context
```

A Result Scheme may define domain-specific relationships inside Result data,
but such semantics belong to that Scheme or to a future explicit discovery
mechanism.

They MUST NOT be inferred by the generic RFC-0011 discovery layer.

---

## 23. Relationship to Stimulus

The current RFC-0007 experimental Stimulus contract contains the optional:

```text
source
```

Reference.

When present, it is treated as a Structural Reference.

Stimulus conditions and extensions are not recursively inspected for
additional relationships by the generic discovery layer.

---

## 24. Relationship to Molecule

RFC-0009 Molecule currently declares no Structural References.

Therefore Molecule contributes no outgoing discoveries to the default
registry.

A Molecule may nevertheless have incoming relationships from resources such
as:

```text
Stimulus.source
Annotation.subject
```

This distinction demonstrates why incoming navigation cannot be implemented
solely as a method on the target Resource Type.

---

## 25. Extensibility

Reference discovery is intended to be extensible.

A future or third-party understood resource type may register its own
structural Reference discoverer without modifying GenericResourceGraph.

Conceptually:

```text
CustomResource
    |
    +-- registered discoverer
            |
            +-- structural Reference A
            +-- structural Reference B
```

The discoverer, rather than generic JSON inspection, defines the
relationship boundary.

Third-party registration MUST NOT alter the meaning of resource types owned
by another namespace without an explicit agreement or implementation-level
override mechanism.

The exact governance model for third-party discovery registration remains
outside the scope of this RFC.

---

## 26. Serialization

RFC-0011 introduces no new graph serialization fields.

The following remain runtime/navigation concepts in the current experiment:

```text
ReferenceDiscoveryRegistry
ReferenceDiscoveryHandler
DiscoveredReference
ReferenceIndex
```

The underlying Resources and References continue to serialize according to
their existing RFC contracts.

This means two implementations may transport the same graph losslessly even
if one implementation understands more Structural References than the other.

For example:

```text
Implementation A
    understands CustomResource
    discovers 3 relationships

Implementation B
    does not understand CustomResource
    discovers 0 relationships from it

Both
    preserve the CustomResource through RFC-0008 transport
```

Different discovery knowledge therefore does not imply different transport
validity.

---

## 27. Forward Compatibility

RFC-0011 is designed around explicit knowledge rather than exhaustive
knowledge.

An implementation should preserve the following distinction:

```text
unknown Resource Type
    = transportable
    != structurally understood
```

and:

```text
known Resource Type
+
unknown Resource Type Version
    = transportable through RFC-0008
    != safe to interpret using an older version's discovery rules
```

Adding support for a new Resource Type or Resource Type Version may increase
the number of discoverable relationships without changing the underlying
serialized graph.

Applications MUST therefore avoid treating the absence of a discovered
relationship from an unknown resource as proof that no relationship exists.

It means only that the current discovery implementation does not know one.

---

## 28. Non-Goals

RFC-0011 does not define:

- new Resource Types;
- new Resource Type serialization;
- a universal relationship ontology;
- relationship labels or predicates;
- graph query languages;
- recursive arbitrary JSON reference scanning;
- inference from field names;
- semantic interpretation of Annotation data;
- semantic interpretation of Observation Result data;
- Scheme-specific reference discovery;
- external resource retrieval;
- network resolution of Resource IDs;
- automatic loading of missing resources;
- reference deduplication;
- graph mutation tracking;
- automatic ReferenceIndex refresh;
- a persistent serialized graph index;
- normative performance requirements;
- authorization rules for referenced resources;
- normative Resource ID generation;
- physical odor reproduction;
- diffuser control.

---

## 29. Security and Robustness Considerations

Reference discovery may operate on large or untrusted graphs.

Implementations should consider:

- very large resource collections;
- resources declaring many Structural References;
- large numbers of unresolved references;
- duplicate References;
- cyclic relationships;
- self-references;
- malicious or buggy third-party discoverers;
- resource mutation after index construction;
- untrusted extension data;
- unknown Resource Types;
- unknown Resource Type Versions.

The discovery layer MUST NOT execute behavior based merely on arbitrary JSON
field names.

A discoverer supplied by an application or third party should be treated as
implementation code rather than untrusted data.

Resolution of a Resource ID MUST NOT automatically imply authorization to
access an external system or retrieve external content.

RFC-0011 defines local structural navigation only.

## 30. Portable Conformance Work

Before RFC-0011 can be considered for promotion beyond Draft, portable
evidence should be produced for the behavior defined by this experiment.

Candidate conformance work includes:

1. language-independent heterogeneous graph discovery vectors;
2. vectors distinguishing Structural References from Reference-like opaque
   JSON;
3. resolved and unresolved relationship vectors;
4. deterministic discovery-order vectors;
5. unknown Resource Type vectors;
6. unknown future Resource Type Version vectors;
7. duplicate-reference preservation vectors;
8. Reference extension preservation vectors;
9. Python conformance tests independent from the current unit-test fixtures;
10. an independent JavaScript reference-discovery implementation;
11. Python/JavaScript agreement on discovered source-target relationships;
12. regression validation against the complete OdorNet Annotation graph.

The portable vectors should test observable relationship behavior rather than
Python-specific class or registry implementation details.

ReferenceIndex itself may remain an implementation facility if independent
implementations can provide equivalent navigation behavior using different
internal data structures.

---

## 31. Open Questions

The experiment intentionally leaves several questions unresolved:

1. Should Structural Reference discovery become a normative graph capability
   or remain an SDK-level facility?
2. Should discovery rules eventually be associated directly with Resource
   Type handlers, or should serialization and relationship discovery remain
   permanently separate registries?
3. Should discovered relationships expose an explicit relationship role such
   as `source`, `stimulus`, `target`, or `subject`?
4. If roles are introduced, are they local field names or globally identified
   predicates?
5. Should ReferenceIndex resolution become strictly snapshot-based?
6. Should a mutable graph provide index invalidation or rebuilding hooks?
7. Should Scheme-defined payloads be able to register their own explicit
   reference discoverers?
8. Should applications be able to distinguish an absent source resource from
   a source resource that exists but has no outgoing Structural References in
   one query?
9. Should duplicate identical References remain independently discoverable in
   all future versions?
10. Should discovery metadata identify which Resource Type contract produced
    each relationship?
11. Should portable conformance specify discovery ordering normatively?
12. What additional heterogeneous real-world datasets should be used beyond
    OdorNet?
13. Should graph navigation eventually expose traversal helpers, or should it
    remain limited to direct incoming/outgoing relationships?

These questions should be resolved from interoperability requirements and
independent implementation experience rather than API symmetry alone.

---

## 32. Current Recommendation

Keep structural reference discovery experimental.

The current evidence supports the architectural separation:

```text
resource transport
        !=
relationship interpretation
```

and:

```text
known structural Reference
        !=
Reference-like JSON
```

The Python prototype has demonstrated:

- explicit per-type Structural Reference discovery;
- preservation of unknown resource opacity;
- navigation of resolved and unresolved references;
- deterministic discovery order;
- incoming and outgoing indexing;
- successful navigation across Molecule, Stimulus, ObservationTarget,
  Observation, and Annotation resources;
- zero false edges in the dedicated heterogeneous validation graph;
- successful indexing of 8,892 Annotation-to-Molecule relationships in the
  OdorNet experiment;
- no regressions across the complete 1,146-test Python suite.

However, the current evidence comes primarily from one implementation.

The next step should therefore be portable, language-independent conformance
vectors and an independent JavaScript implementation before considering the
capability for promotion beyond Draft.
