# RFC-0007: Stimulus and Observation Resource Model

- **Status:** Draft
- **Category:** Experimental
- **Target:** Future OpenSmell version
- **Authors:** OpenSmell contributors
- **Created:** 2026-09-03
- **Depends on:** RFC-0003, RFC-0005, RFC-0006
- **Does not modify:** OpenSmell 0.1 Core

---

## 1. Abstract

This RFC proposes an experimental resource model for representing olfactory
stimuli, observation targets, observations, and scheme-defined observation
results in OpenSmell.

The model introduces the following concepts:

- `Reference`
- `ExternalIdentifier`
- `Condition`
- `Stimulus`
- `ObservationTarget`
- `Observation`
- `Result`

The central architectural distinction is:

```text
Odor or source resource
        |
        v
     Stimulus
        |
        v
   Observation -----> ObservationTarget
        |
        v
     Result(s)
```

An odor, molecule, or mixture describes something that may participate in an
olfactory stimulus.

A stimulus describes something presented or applied under particular
conditions.

An observation describes a result associated with a stimulus and, optionally,
an observation target.

A result is interpreted according to a scheme.

This RFC deliberately does not define a universal measurement model.

Instead, observations contain one or more scheme-defined `Result` resources
whose internal data are interpreted according to the declared result scheme.

This architecture has been experimentally evaluated against two substantially
different real-world olfactory datasets:

1. Burton et al. 2022 physiological mouse olfactory bulb measurements.
2. Keller/Vosshall human psychophysical odor measurements.

Together, these experiments represented 242,748 observations without requiring
a universal observation measurement structure.

This RFC remains experimental.

Nothing defined here is part of the OpenSmell 0.1 Core specification.

---

## 2. Status

This document is a Draft RFC.

The structures described here are experimental.

Implementations MUST NOT assume that the structures or identifiers described
in this RFC are stable until the RFC is promoted to a normative status.

In particular:

- the Python experimental API may change;
- field names may change;
- result schemes may change;
- serialization rules are not yet normative;
- resource graph storage is not yet normative;
- the experimental namespace used by current prototypes is not automatically
  reserved for future normative use.

---

## 3. Motivation

OpenSmell 0.1 focuses on describing an odor through one or more
representations.

That model is useful for statements such as:

```text
This odor has the semantic descriptor "coffee".
```

or:

```text
This molecule is represented by this SMILES string.
```

or:

```text
This odor has these perceptual properties.
```

However, experimental olfactory datasets frequently represent a different
kind of information.

They may describe:

- a molecule presented at a particular concentration;
- an odor presented at a particular dilution;
- a human rating after exposure;
- whether a participant detected an odor;
- a physiological response in an animal;
- the response of a receptor;
- the response of an olfactory bulb region;
- the output of an electronic sensor;
- the output of a computational model.

These are not all properties of the odor itself.

They are observations made under particular experimental circumstances.

Trying to store all such information directly inside `Odor` would collapse
several distinct concepts into one resource.

This RFC therefore introduces an explicit stimulus and observation layer.

---

## 4. Core distinction

The following resources MUST be conceptually distinguished:

```text
Odor / Molecule / Mixture
           |
           v
        Stimulus
           |
           v
       Observation
           |
           +------> ObservationTarget
           |
           v
        Result(s)
```

The following statements are therefore fundamental:

```text
Odor != Stimulus
Stimulus != Observation
Odor != Observation
ObservationTarget != Observation
Result != Observation
```

These distinctions are semantic, not merely implementation details.

---

## 5. Source resource

A `Stimulus` MAY reference another OpenSmell resource describing what was
presented.

Examples include:

- an `Odor`;
- a molecule;
- a mixture;
- a material;
- another future OpenSmell resource type.

This RFC does not define a universal source resource type.

The source is referenced using a `Reference`.

Example:

```json
{
  "source": {
    "resource_id": "9c7b4d6c-..."
  }
}
```

The referenced resource might represent a molecule while the stimulus adds
experimental presentation conditions.

---

## 6. Odor is not Stimulus

An odor describes olfactory information.

A stimulus describes a presentation or application event or configuration.

For example:

```text
Molecule:
    vanillin

Stimulus A:
    vanillin
    dilution = 1/1000

Stimulus B:
    vanillin
    dilution = 1/100000
```

The same molecule participates in two different stimuli.

Therefore:

```text
1 molecule -> N stimuli
```

is valid and expected.

---

## 7. Evidence from Keller/Vosshall

The Keller/Vosshall experimental dataset contains:

```text
480 unique PubChem CIDs
960 unique molecule+dilution stimuli
```

The experimental OpenSmell adapter therefore produced:

```text
480 molecule identities
960 Stimulus resources
```

This demonstrates that molecule identity and stimulus identity cannot safely be
treated as equivalent.

---

## 8. Evidence from Burton 2022

The Burton dataset contains:

```text
186 molecules
227 stimuli
```

Again:

```text
Molecule != Stimulus
```

Some molecules occur in more than one stimulus configuration.

This independently supports the same architectural distinction observed in the
Keller/Vosshall dataset.

---

## 9. Reference

A `Reference` identifies another OpenSmell resource.

Experimental conceptual form:

```json
{
  "resource_id": "6136624f-5105-52f1-875e-53a177ef2134"
}
```

A reference contains:

```text
resource_id
```

The referenced resource does not need to be embedded inside the referencing
resource.

---

## 10. Reference semantics

A `Reference` expresses identity, not object containment.

For example:

```text
Observation
    stimulus -> Resource ID of Stimulus
```

does not imply that the complete Stimulus must be serialized inside the
Observation.

This enables graph-oriented representations.

---

## 11. Reference resolution

Structural validity and graph resolution SHOULD remain distinct concepts.

A reference MAY be structurally valid even when its target is not currently
available.

For example:

```json
{
  "resource_id": "missing-resource"
}
```

may still be preserved by a parser or adapter.

An implementation MUST NOT automatically discard an unresolved reference.

---

## 12. Unresolved references

Unresolved references may occur because:

- a dataset is incomplete;
- resources are stored separately;
- resources are loaded incrementally;
- the source dataset contains inconsistent metadata;
- a remote resource is temporarily unavailable;
- a resource is intentionally external.

Therefore:

```text
unresolved reference != invalid reference
```

Graph validation MAY report unresolved references separately.

---

## 13. ExternalIdentifier

An `ExternalIdentifier` preserves an identifier assigned by an external system
or source dataset.

Conceptual form:

```json
{
  "scheme": "pubchem.cid",
  "value": "240"
}
```

The fields are:

```text
scheme
value
```

Both are strings.

---

## 14. External identifiers are not Resource IDs

An external identifier MUST NOT automatically become an OpenSmell Resource ID.

For example:

```text
PubChem CID:
240
```

is an external identifier.

An OpenSmell Resource ID may instead be:

```text
c3120f5d-...
```

The two identifiers serve different purposes.

---

## 15. Source-native identifiers

Adapters SHOULD preserve identifiers genuinely supplied by their source
dataset.

Examples include:

```text
PubChem CID
Burton stimulus identifier
Burton ROI identifier
Keller/Vosshall subject identifier
```

Adapters SHOULD NOT invent external identifiers merely because a convenient
string can be constructed.

For example:

```text
CID@dilution
```

MUST NOT be presented as a source-native external identifier unless the source
dataset actually defines that identifier.

---

## 16. Generated identity

OpenSmell Resource IDs MAY be generated from structured source identity as
described experimentally by RFC-0006.

For example, a stimulus source identity may be:

```json
{
  "cid": "240",
  "dilution": "1/1000"
}
```

The resulting OpenSmell Resource ID is generated identity.

The structured source identity does not need to be exposed as an external
identifier.

---

## 17. Identity and metadata

Resource identity and resource metadata are separate concerns.

A resource MAY have:

- an OpenSmell Resource ID;
- zero external identifiers;
- one external identifier;
- multiple external identifiers.

None of these imply semantic equality between resources.

---

## 18. Stimulus

A `Stimulus` represents something presented to, or applied to, an observation
target under defined or partially defined conditions.

Experimental conceptual structure:

```json
{
  "id": "...",
  "source": {
    "resource_id": "..."
  },
  "identifiers": [],
  "conditions": [],
  "extra": {}
}
```

---

## 19. Stimulus fields

The experimental `Stimulus` model contains:

```text
id
source
identifiers
conditions
extra
```

where:

- `id` identifies the Stimulus resource;
- `source` optionally references what was presented;
- `identifiers` preserves source-native external identifiers;
- `conditions` describes presentation conditions;
- `extra` preserves additional experimental information.

---

## 20. Stimulus source

`source` is optional.

A missing source means that the source is unknown, unavailable, intentionally
unspecified, or not represented.

It MUST NOT automatically imply:

- blank stimulus;
- control stimulus;
- odorless stimulus;
- no stimulus;
- invalid stimulus.

The meaning depends on the source dataset.

---

## 21. Source-less stimuli

The Burton dataset contains a stimulus whose source identifier is:

```text
empty
```

Its source molecule is not represented.

The experimental adapter preserves this as a valid `Stimulus` with:

```text
source = None
```

No semantic role such as `control` is invented.

This illustrates an important rule:

> OpenSmell adapters SHOULD preserve source information without inventing
> scientific meaning not supported by the source.

---

## 22. Condition

A `Condition` describes one presentation condition associated with a
Stimulus.

Experimental conceptual structure:

```json
{
  "property": "concentration",
  "value": 0.000001,
  "unit": "mol/L"
}
```

or:

```json
{
  "property": "dilution",
  "value": "1/1000"
}
```

---

## 23. Condition fields

A Condition contains:

```text
property
value
unit
extra
```

`property` identifies the condition.

`value` is intentionally open-ended.

`unit` is optional.

`extra` permits experimental extensions.

---

## 24. Open condition values

This RFC deliberately does not require all conditions to be numeric.

Examples:

```text
concentration = 0.001 mol/L
dilution = "1/1000"
carrier = "air"
delivery_method = "headspace"
temperature = 25 C
```

A future condition vocabulary or quantity specification MAY define stronger
semantics.

---

## 25. Missing condition

A missing condition MUST NOT be interpreted as zero.

For example:

```text
missing concentration != concentration 0
```

Similarly:

```text
missing dilution != zero dilution
```

Missing means that the condition is not represented.

---

## 26. Burton missing concentration evidence

The Burton experimental conversion contains:

```text
227 stimuli
225 with conditions
2 without conditions
```

The two stimuli without represented concentration are preserved without
inventing numeric values.

This demonstrates why concentration cannot be a mandatory Stimulus field.

---

## 27. ObservationTarget

An `ObservationTarget` identifies the entity with respect to which an
Observation is made.

The term `target` is deliberately generic.

It MUST NOT be interpreted as meaning only a human participant.

---

## 28. Possible observation targets

Examples include:

```text
human participant
animal
olfactory receptor
glomerulus
region of interest
electronic sensor
sensor array
computational model
```

Future OpenSmell specifications MAY define more specialized target models.

---

## 29. ObservationTarget structure

Experimental conceptual structure:

```json
{
  "id": "...",
  "identifiers": [
    {
      "scheme": "dataset.subject",
      "value": "42"
    }
  ],
  "extra": {}
}
```

---

## 30. Target identity

An ObservationTarget is an OpenSmell resource.

It therefore has its own Resource ID.

Source dataset identifiers SHOULD be preserved separately through
`ExternalIdentifier`.

---

## 31. Burton target evidence

The Burton experiment produced:

```text
1,008 ObservationTarget resources
```

These represent source ROI/target identifiers.

The source metadata contained four identifiers referenced by physiological
observations but absent from the declared target metadata.

The source also contained four declared target identifiers that were not
referenced by observations.

The experimental model preserved both situations.

---

## 32. Source inconsistency and graph representation

The Burton source contained four referenced target identifiers absent from the
source target metadata:

```text
113L_038
113L_039
113R_064
113R_077
```

Rather than discarding 748 observations or inventing biological metadata, the
experimental adapter created target resources preserving those source
identifiers.

This distinction is important:

```text
unresolved in source metadata
```

does not necessarily mean:

```text
unresolved in OpenSmell resource graph
```

An adapter MAY create a minimal resource representing the unresolved source
identity.

---

## 33. Observation

An `Observation` represents a result obtained in association with a Stimulus
and optionally an ObservationTarget.

Experimental conceptual structure:

```json
{
  "id": "...",
  "stimulus": {
    "resource_id": "..."
  },
  "target": {
    "resource_id": "..."
  },
  "results": [],
  "context": {},
  "identifiers": [],
  "extra": {}
}
```

---

## 34. Observation fields

The experimental Observation model contains:

```text
id
stimulus
target
results
context
identifiers
extra
```

---

## 35. Required stimulus reference

An Observation currently requires a Stimulus reference.

Conceptually:

```text
Observation -> Stimulus
```

This ensures that the observation identifies what was presented or applied.

Whether future OpenSmell versions should permit observations without a
Stimulus remains an open question.

---

## 36. Optional target reference

An Observation target is optional.

Some datasets or future use cases may not expose an identifiable target.

Therefore:

```text
target = absent
```

is structurally representable.

A scheme or application MAY impose stronger requirements.

---

## 37. Observation context

`context` contains observation-level contextual information that is not part
of the generic graph structure.

Experimental examples include:

```json
{
  "measurement_domain": "psychophysical"
}
```

or:

```json
{
  "measurement_domain": "physiological"
}
```

These values are currently experimental.

This RFC does not define a normative context vocabulary.

---

## 38. Observation results

An Observation contains:

```text
results[]
```

Each entry is a `Result`.

An Observation MAY contain:

```text
zero results
one result
multiple results
```

A scheme, dataset adapter, or application MAY impose stronger requirements.

---

## 39. Why Result exists

Early experiments used a universal `Measurement` class directly inside
Observation.

That approach appeared attractive because many datasets contain numeric
measurements.

However, the model quickly encountered semantically different data:

```text
detection state
recognition response
psychophysical rating
physiological DeltaF
future sensor output
future model output
```

These are not necessarily instances of one universal measurement concept.

The universal Measurement abstraction was therefore removed from the generic
resource graph.

---

## 40. Result

A `Result` contains data interpreted according to a declared scheme.

Experimental conceptual structure:

```json
{
  "scheme": "org.opensmell.perceptual.measurements",
  "data": {
    "measurements": []
  },
  "extra": {}
}
```

---

## 41. Result fields

The experimental Result model contains:

```text
scheme
data
extra
```

where:

- `scheme` identifies the interpretation rules;
- `data` contains scheme-defined data;
- `extra` preserves additional information.

---

## 42. Result scheme

A Result scheme defines how `data` should be interpreted.

The generic Observation model MUST NOT attempt to interpret arbitrary Result
data without knowledge of the scheme.

This follows the same general extensibility principle used by OpenSmell
representations.

---

## 43. Unknown Result schemes

Unknown Result schemes MUST be representable.

A generic OpenSmell implementation SHOULD preserve Result data even when it
does not understand the scheme.

For example:

```json
{
  "scheme": "vendor.example.future-result",
  "data": {
    "something": 123
  }
}
```

should not automatically make the enclosing Observation invalid.

---

## 44. Scheme-specific validation

Generic structural validation and scheme-specific validation are separate.

Generic validation may verify:

```text
scheme is a non-empty string
data is an object
```

A scheme-specific validator may then impose additional requirements.

For example, a perceptual measurement scheme may require:

```text
measurements
property
numeric value
scale
```

while a biological scheme may define entirely different fields.

---

## 45. Multiple Result schemes

An Observation MAY contain Results from multiple schemes.

Example:

```text
Observation
|
+-- Result
|   scheme = categorical observation scheme
|
+-- Result
    scheme = perceptual measurement scheme
```

This was required by the Keller/Vosshall experiment.

---

## 46. Keller/Vosshall categorical Result

The experimental Keller/Vosshall adapter represented detection and recognition
using an experimental categorical Result scheme:

```text
org.opensmell.experimental.observation.categories
```

Example conceptual data:

```json
{
  "detection": "detected",
  "recognition": "I don't know what the odor is"
}
```

This scheme is experimental.

Its appearance in the prototype MUST NOT be interpreted as reserving or
standardizing this scheme identifier.

---

## 47. Keller/Vosshall perceptual Result

Quantitative psychophysical measurements were represented separately using:

```text
org.opensmell.perceptual.measurements
```

Example:

```json
{
  "measurements": [
    {
      "property": "intensity",
      "value": 59.0,
      "scale": {
        "min": 0,
        "max": 100
      }
    }
  ]
}
```

The semantics of this quantitative perceptual model belong to RFC-0005.

RFC-0007 does not redefine them.

---

## 48. Detection is not a quantitative rating

Detection state and quantitative perceptual rating are deliberately separate.

For example:

```text
detected
```

is not equivalent to:

```text
intensity = 1
```

Similarly:

```text
not detected
```

is not equivalent to:

```text
intensity = 0
```

The absence of a quantitative rating MUST NOT automatically be interpreted as
a zero rating.

## 53. Zero is data

Numeric zero MUST be preserved when explicitly present.

For example:

```json
{
  "property": "delta_f",
  "value": 0.0
}
```

contains an explicit value.

It MUST NOT be treated as equivalent to:

```text
missing measurement
```

---

## 54. Negative zero

Source datasets may contain IEEE-754 negative zero:

```text
-0.0
```

The Burton source produced such a value in the experimental conversion.

The current experiment preserves it.

This RFC does not currently require canonicalization:

```text
-0.0 -> 0.0
```

Whether numeric canonicalization should occur during serialization is outside
the scope of this RFC.

---

## 55. Missing Result

An Observation with no Result is structurally representable by the current
experimental model.

This does not mean that such an Observation is scientifically useful.

Possible reasons include:

- incomplete dataset;
- incremental graph construction;
- result stored separately;
- failed measurement;
- unknown result;
- future workflow requirements.

Future schemes MAY require one or more Results.

---

## 56. Missing Result is not zero

The following distinction MUST be preserved:

```text
no result
```

is not equivalent to:

```text
result value = 0
```

Similarly:

```text
no measurement
```

is not equivalent to:

```text
measurement value = 0
```

---

## 57. Result versus Representation

`Result` and OpenSmell Core `Representation` have related extensibility
patterns but different semantic roles.

A Representation describes an odor representation.

A Result describes the outcome of an Observation.

Conceptually:

```text
Odor
└── Representation

Observation
└── Result
```

They MUST NOT be treated as interchangeable merely because both use schemes.

---

## 58. Scheme architecture

Both concepts follow the architectural principle:

```text
stable generic container
+
scheme-defined semantics
```

This reduces pressure to continuously expand the generic OpenSmell data model
whenever a new scientific modality appears.

---

## 59. Future sensor data

The proposed Result architecture is intended to permit future sensor
observations.

For example:

```text
Observation
|
+-- stimulus -> Stimulus
|
+-- target -> electronic sensor
|
+-- Result
    scheme = future sensor scheme
```

RFC-0007 does not define such a sensor scheme.

---

## 60. Future computational model data

Similarly, a future computational prediction may be represented conceptually
as:

```text
Observation
|
+-- stimulus -> Stimulus
|
+-- target -> model
|
+-- Result
    scheme = model-specific result scheme
```

This RFC does not define model output semantics.

---

## 61. Human observations

Human psychophysical observations may use:

```text
ObservationTarget = human participant
```

and one or more Result schemes.

A human target does not imply that every Result is perceptual.

For example, physiological measurements from a human could use a different
Result scheme.

---

## 62. Animal observations

Animal experiments may use:

```text
ObservationTarget = animal
```

or a more specific biological structure when that is what the dataset
actually identifies.

The generic model does not impose one biological hierarchy.

---

## 63. ROI observations

The Burton experiment demonstrates that the target may represent a
dataset-specific region of interest rather than the entire animal.

OpenSmell SHOULD preserve the level of identity actually expressed by the
source dataset.

It SHOULD NOT automatically collapse ROI identity into animal identity.

---

## 64. Resource graph

The proposed model naturally forms a directed graph.

Example:

```text
Molecule M1
    ^
    |
Stimulus S1
    ^
    |
Observation O1 ----> Target T1
    |
    +---- Result R1
```

Multiple observations may reference the same Stimulus.

Multiple stimuli may reference the same source resource.

Multiple observations may reference the same target.

---

## 65. Resource reuse

Resources SHOULD be reusable through references.

For example:

```text
Molecule M1
   ^
   |
   +---- Stimulus S1
   |
   +---- Stimulus S2
```

and:

```text
Stimulus S1
   ^
   |
   +---- Observation O1
   |
   +---- Observation O2
   |
   +---- Observation O3
```

This avoids unnecessary duplication.

---

## 66. Resource identity

Resource identity SHOULD follow the principles developed in RFC-0006.

Those principles include:

- stability;
- uniqueness within the intended scope;
- opacity;
- independence from external systems;
- referenceability;
- round-trip preservation.

RFC-0007 does not redefine Resource ID syntax.

---

## 67. Experimental UUID generation

Current experiments use deterministic UUIDv5 Resource IDs for imported dataset
resources.

Conceptually:

```text
dataset
+
resource type
+
canonical source identity
        |
        v
      UUIDv5
```

This generation mechanism belongs to RFC-0006.

RFC-0007 depends on resource identity but does not standardize UUID generation.

---

## 68. Resource type and identity

Resource type participates in the current experimental deterministic identity
generation.

Therefore identical source strings used for different resource types do not
necessarily identify the same OpenSmell resource.

For example:

```text
source identity "42" as target
```

and:

```text
source identity "42" as stimulus
```

are different resource identities.

---

## 69. Composite source identity

Some resources require composite source identity.

For example, Keller/Vosshall Stimulus identity currently uses:

```json
{
  "cid": "240",
  "dilution": "1/1000"
}
```

This is appropriate because neither CID nor dilution alone uniquely identifies
the stimulus configuration.

---

## 70. Observation identity

Observation identity may also require multiple source fields.

The Keller/Vosshall experiment currently uses:

```json
{
  "cid": "...",
  "dilution": "...",
  "occurrence": "...",
  "subject": "..."
}
```

This is an adapter-level experimental choice.

It MUST NOT be interpreted as a normative OpenSmell observation identity
algorithm.

---

## 71. Keller/Vosshall occurrence limitation

The current Keller/Vosshall adapter uses an occurrence counter to distinguish
repeated observations sharing:

```text
subject
CID
dilution
```

The occurrence counter depends on source row ordering.

Therefore, reordering the source dataset may alter generated observation IDs.

This is a known limitation.

RFC-0007 does not standardize occurrence-based identity.

A future adapter SHOULD prefer a stable source-native observation identifier
when one is available and semantically justified.

---

## 72. Identity stability requirement

A future normative resource model SHOULD distinguish:

```text
resource model
```

from:

```text
dataset-specific identity extraction strategy
```

The generic resource model should not require knowledge of how every source
dataset determines observation identity.

---

## 73. Identity is not equality

Two resources containing identical data are not automatically the same
resource.

For example:

```text
Observation A:
intensity = 50

Observation B:
intensity = 50
```

does not imply:

```text
Observation A == Observation B
```

They may correspond to different participants, trials, stimuli, times, or
experimental contexts.

---

## 74. Content is not identity

Resource IDs MUST NOT be treated merely as hashes of current resource
contents.

Resource metadata may evolve while resource identity remains stable.

This principle is inherited from RFC-0006.

---

## 75. Serialization

This RFC does not yet define a normative JSON serialization for the complete
resource graph.

The JSON fragments in this document are conceptual examples.

Future work must determine whether resources are serialized:

- inside one OpenSmell document;
- as separate resources;
- as collections;
- through linked documents;
- through an API;
- through another transport format.

## 76. OpenSmell 0.1 compatibility

OpenSmell 0.1 does not define:

```text
Stimulus
Observation
ObservationTarget
Result
```

Therefore an OpenSmell 0.1 implementation is not required to support this RFC.

Experimental implementations SHOULD keep these concepts outside the 0.1 Core
schema until a future specification explicitly adopts them.

---

## 77. Experimental use through extensions

Because OpenSmell 0.1 permits extension fields in relevant locations,
experimental resource graphs may be explored without immediately changing the
Core specification.

However, extension use MUST NOT be mistaken for normative adoption.

---

## 78. Forward compatibility

Future OpenSmell resource models SHOULD preserve the general principle that
unknown extension data and unknown schemes can survive parsing and
serialization when structurally possible.

This is consistent with the forward-compatible design of OpenSmell Core
representations.

## 79. Scheme ownership

This RFC defines the Result mechanism.

It does not automatically define the schemes used by experimental adapters.

In particular:

```text

org.opensmell.experimental.biological.measurements
```

are prototype identifiers.

They are not normative registrations.

```text

```

is associated with the experimental quantitative perceptual model described by
RFC-0005.

RFC-0007 only defines how such scheme-defined data may participate in an
Observation Result.

## 82. Result scheme versioning

The current experimental `Result` structure contains:

```text
scheme
data
extra
```

It does not currently contain a dedicated scheme version field.

This is intentionally unresolved.

Possible future designs include:

```json
{
  "scheme": {
    "id": "...",
    "version": "0.1"
  }
}
```

or reuse of the existing OpenSmell `Scheme` model.

No decision is made in this RFC.

---

## 83. Reusing Core Scheme

OpenSmell Core already defines a `Scheme` structure containing:

```text
id
version
extra
```

A future resource model may reuse this structure for Result.

Advantages include:

- architectural consistency;
- explicit versioning;
- shared validation patterns.

Potential disadvantages include:

- coupling experimental resource models to Core representation structures;
- premature assumptions that Representation and Result scheme lifecycle must be
  identical.

This remains an open design question.

## 84. Conditions versus context

Stimulus `conditions` and Observation `context` serve different purposes.

Conceptually:

```text
Stimulus.conditions
```

describes how something was presented or applied.

```text
Observation.context
```

describes circumstances associated with the observation or result.

The exact boundary may require refinement.

## 88. Dataset adapters

Dataset adapters are responsible for mapping source semantics into OpenSmell
resources.

Adapters SHOULD:

- preserve source-native identifiers;
- preserve explicit zero values;
- preserve missingness;
- avoid inventing scientific meaning;
- distinguish source resources from stimuli;
- distinguish observations from results;
- report unresolved references when useful.

---

## 89. Adapter-specific logic

Some logic necessarily remains dataset-specific.

Examples include:

```text
which source columns define stimulus identity
which source columns define observation identity
which values mean missing
which columns contain measurements
which identifiers are source-native
```

RFC-0007 MUST NOT attempt to standardize every dataset adapter.

---

## 90. Missingness

Missingness is a first-class semantic concern.

The following distinctions SHOULD be preserved:

```text
missing source
missing condition
missing target
missing result
explicit zero
explicit empty string
unknown state
not detected
```

These values MUST NOT be collapsed without scheme- or dataset-specific
justification.

---

## 91. Explicit absence

Some schemes may define explicit absence states.

For example:

```text
detection = not_detected
```

is explicit data.

It is different from:

```text
detection field missing
```

Similarly, RFC-0004 distinguishes explicit semantic absence from missing
annotation.

---

## 92. Open data payload

`Result.data` is intentionally an open object.

This provides flexibility but reduces generic semantic validation.

This trade-off is deliberate during the experimental phase.

A future normative specification may impose additional constraints.

---

## 93. Why not one universal Result schema

Olfactory observations can span multiple scientific domains.

A universal schema would need to simultaneously model:

```text
human perception
animal physiology
receptor response
sensor signals
chemical analysis
model predictions
categorical outcomes
time series
multidimensional vectors
```

Attempting to standardize all of these inside the generic Observation resource
would make the base model complex and brittle.

Scheme-defined Result data avoids this problem.

---

## 94. Why not store everything in extra

Using only arbitrary extension fields would technically permit the same data,
but would provide little interoperability.

The explicit `Result` abstraction provides a stable extension point:

```text
Observation
    results[]
        scheme
        data
```

Applications can therefore discover the interpretation mechanism without
understanding every possible result type.

---

## 95. Why not put results directly in Observation

A flat Observation structure such as:

```json
{
  "detection": "...",
  "intensity": 42,
  "delta_f": 0.3
}
```

would mix unrelated scientific domains and make future extension difficult.

The Result abstraction isolates domain semantics.

---

## 96. Experimental Python model

The current prototype contains conceptual Python structures equivalent to:

```python
@dataclass(frozen=True)
class Reference:
    resource_id: str


@dataclass(frozen=True)
class ExternalIdentifier:
    scheme: str
    value: str


@dataclass
class Condition:
    property: str
    value: Any
    unit: str | None = None
    extra: dict[str, Any] = field(default_factory=dict)


@dataclass
class Result:
    scheme: str
    data: dict[str, Any] = field(default_factory=dict)
    extra: dict[str, Any] = field(default_factory=dict)


@dataclass
class Stimulus:
    id: str
    source: Reference | None = None
    identifiers: list[ExternalIdentifier] = field(default_factory=list)
    conditions: list[Condition] = field(default_factory=list)
    extra: dict[str, Any] = field(default_factory=dict)


@dataclass
class ObservationTarget:
    id: str
    identifiers: list[ExternalIdentifier] = field(default_factory=list)
    extra: dict[str, Any] = field(default_factory=dict)


@dataclass
class Observation:
    id: str
    stimulus: Reference
    target: Reference | None = None
    results: list[Result] = field(default_factory=list)
    context: dict[str, Any] = field(default_factory=dict)
    identifiers: list[ExternalIdentifier] = field(default_factory=list)
    extra: dict[str, Any] = field(default_factory=dict)
```

This code is informative.

The RFC defines concepts, not a mandatory Python implementation.

The prototype currently validates only basic structural requirements.

Examples include:

```text

Condition property is non-empty.
```

Stronger validation belongs to future specifications and scheme-specific

## 98. Resource ID validation separation

The experimental resource classes deliberately do not currently enforce the
RFC-0006 UUID candidate syntax.

This prevents premature coupling between:

```text

```

and:

```text

```

An implementation may combine both validators when appropriate.

## 99. Graph validation

Graph validation MAY perform checks beyond structural resource validation.

Examples include:

```text

Resource IDs are unique

Observation target resolves
scheme is supported
```

Failure of one graph-level check does not necessarily imply that the
individual resource is structurally invalid.

## 106. Relationship to RFC-0004

RFC-0004 defines an experimental semantic annotation model.

Semantic annotation and Observation Result are distinct concepts.

For example:

```text

    floral = present
```

does not necessarily describe:

```text
a participant's response during one experimental trial
```

Dataset adapters must preserve this distinction.

## 107. Relationship to RFC-0005

RFC-0005 defines quantitative perceptual measurements.

RFC-0007 provides an Observation architecture capable of carrying RFC-0005
data as a Result.

Conceptually:

```text
Observation
└── Result
    ├── scheme = org.opensmell.perceptual.measurements
    └── data = RFC-0005 measurement data
```

RFC-0007 does not redefine RFC-0005 measurement semantics.

## 108. Relationship to RFC-0006

RFC-0006 explores resource identification.

RFC-0007 relies on the concept of Resource IDs and references.

Current experimental dataset adapters use RFC-0006 deterministic Resource ID
generation.

```text

```

and:

```text
RFC-0006 identity generation
```

remain separable concerns.

## 109. Relationship to OpenSmell 0.1

OpenSmell 0.1 remains focused on the representation of an Odor.

RFC-0007 is a candidate extension for a future OpenSmell version.

Nothing in this RFC changes conformance requirements for OpenSmell 0.1.

---

## 110. Relationship to rendering

A Stimulus is not a rendering command.

For example:

```text
Stimulus:
    molecule X
    concentration Y
```

does not tell a diffuser how to physically reproduce that stimulus.

Rendering remains a separate concern.

OpenSmell MUST NOT assume how an odor or stimulus is physically reproduced.

---

## 111. Security considerations

Resource graphs may contain externally supplied identifiers and arbitrary
scheme-defined data.

Implementations SHOULD treat these values as untrusted input.

Implementations SHOULD NOT:

- execute arbitrary Result data;
- interpret identifiers as filesystem paths without validation;
- construct executable queries without escaping;
- assume scheme identifiers are trustworthy merely because they use an
  OpenSmell-like namespace.

---

## 112. Privacy considerations

Observation datasets may contain information associated with human
participants.

External subject identifiers may be sensitive or indirectly identifying.

OpenSmell serialization does not make such data safe to publish.

Implementations and dataset publishers are responsible for:

- appropriate anonymization;
- consent;
- access control;
- applicable privacy law;
- dataset licensing;
- ethical requirements.

OpenSmell Resource IDs MUST NOT be assumed to provide anonymization by
themselves.

---

## 113. Scientific integrity considerations

Adapters MUST avoid inventing unsupported scientific meaning.

For example, an adapter SHOULD NOT automatically interpret:

```text
source missing
```

as:

```text
control
```

unless the source dataset or documentation supports that interpretation.

Likewise:

```text
missing measurement
```

MUST NOT automatically become:

```text
measurement = 0
```

---

## 114. Licensing considerations

The OpenSmell resource model does not alter the license of imported datasets.

Adapters and examples MUST respect the license and redistribution terms of
their source datasets.

OpenSmell MUST NOT imply ownership of imported scientific data.

---

## 115. Interoperability principle

The objective of RFC-0007 is not to create a universal ontology for every
olfactory experiment.

The objective is to provide a stable interoperability layer:

```text
resource identity
+
references
+
Stimulus
+
ObservationTarget
+
Observation
+
scheme-defined Result
```

while allowing domain-specific semantics to evolve independently.

## 162. Experimental conclusion

The current evidence supports the following generic architecture:

```text
Source resource
      |
      v
   Stimulus
      |
      v
 Observation -----> ObservationTarget
      |
      v
   Result(s)
      |
      v
scheme-defined semantics
```

The architecture successfully represented both:

```text
mouse physiological observations
```

and:

```text
human psychophysical observations
```

without requiring those domains to share one universal measurement class.

## 167. Final principle

OpenSmell should standardize the boundaries between olfactory information
systems without pretending that every scientific domain measures smell in the
same way.

The proposed resource graph therefore standardizes the relationship:

```text
what was presented
        |
        v
what was observed
        |
        v
how that result is interpreted
```

rather than attempting to standardize every possible observation result inside
one universal structure.
