# RFC-0004: Semantic Annotation Model

- Status: Draft
- RFC: 0004
- Target: Future OpenSmell version
- Category: Representation Scheme
- Authors: OpenSmell contributors

## Summary

This RFC proposes a semantic annotation representation for OpenSmell.

The purpose of the representation is to preserve not only positive odor
descriptors, but also explicit negative annotations and unresolved annotation
states when they are provided by a source dataset or model.

This proposal is motivated by interoperability requirements observed while
importing real-world olfactory data.

It does not modify OpenSmell 0.1.

---

## Motivation

The existing OpenSmell semantic descriptor scheme represents positive
human-readable descriptors.

For example:

```json
{
  "type": "semantic",
  "scheme": {
    "id": "org.opensmell.semantic.descriptors",
    "version": "0.1"
  },
  "data": {
    "descriptors": [
      {
        "value": "floral",
        "language": "en"
      }
    ]
  }
}
```

This is appropriate when the available information is simply:

```text
floral
```

However, some olfactory datasets contain more information.

A source may distinguish between:

```text
floral = present
woody = absent
spice  = unresolved
```

Converting such a source to a list containing only:

```text
floral
```

loses information.

After conversion, an application cannot determine whether `woody` was
explicitly marked absent or was never evaluated.

The same problem applies to any descriptor that was unknown, missing,
unresolved, or otherwise not positively asserted.

---

## Observed interoperability problem

Experiments with the OdorNet dataset exposed this distinction.

OdorNet records contain multiple olfactory categories whose values may
represent:

```text
1      positive annotation
0      negative annotation
blank  unresolved or missing information
```

A simple positive-descriptor conversion preserves only the first state.

For example, the source record:

```text
floral = 1
woody&mossy = 0
spice = blank
```

cannot be represented losslessly as:

```json
{
  "descriptors": [
    {
      "value": "floral",
      "language": "en"
    }
  ]
}
```

The negative and unresolved information disappears.

This is a concrete interoperability requirement rather than a theoretical
extension.

---

## Goals

The proposed scheme SHOULD:

1. represent positive semantic annotations;
2. represent explicit negative semantic annotations;
3. preserve unresolved annotation states;
4. remain independent from any particular dataset;
5. support human-readable descriptors;
6. support machine-readable processing;
7. preserve provenance through OpenSmell extension mechanisms;
8. avoid treating missing information as negative information;
9. coexist with the existing semantic descriptor scheme.

---

## Non-goals

This RFC does not attempt to:

- define a universal odor vocabulary;
- define universal odor categories;
- determine whether a semantic annotation is scientifically correct;
- define chemical structure;
- predict odor from molecular structure;
- define odor intensity;
- define physical scent reproduction;
- define a confidence model;
- define a universal ontology;
- replace existing dataset vocabularies.

---

## Proposed scheme

Provisional scheme identifier:

```text
org.opensmell.semantic.annotations
```

Provisional version:

```text
0.1
```

Representation type:

```text
semantic
```

Example:

```json
{
  "type": "semantic",
  "scheme": {
    "id": "org.opensmell.semantic.annotations",
    "version": "0.1"
  },
  "data": {
    "annotations": [
      {
        "value": "floral",
        "language": "en",
        "state": "present"
      },
      {
        "value": "woody&mossy",
        "language": "en",
        "state": "absent"
      },
      {
        "value": "spice",
        "language": "en",
        "state": "unknown"
      }
    ]
  }
}
```

---

## Annotation object

Each annotation contains at minimum:

```text
value
state
```

It MAY contain:

```text
language
```

Example:

```json
{
  "value": "floral",
  "language": "en",
  "state": "present"
}
```

### `value`

`value` identifies the semantic descriptor or category.

It MUST be a non-empty string.

OpenSmell Core does not assign universal meaning to arbitrary values.

The interpretation may depend on the source vocabulary or external scheme
documentation.

### `language`

`language` identifies the natural language of the annotation value when
applicable.

It SHOULD use a standard language identifier where possible.

The field MAY be omitted when the value is an identifier rather than
natural-language text.

### `state`

`state` describes the relationship between the odor and the annotation.

The initial proposed states are:

```text
present
absent
unknown
```

---

## State semantics

### `present`

The source positively associates the annotation with the odor.

Example:

```json
{
  "value": "floral",
  "state": "present"
}
```

This does not necessarily imply certainty, intensity, or universal scientific
agreement.

It means only that the source positively asserted the annotation.

### `absent`

The source explicitly indicates that the annotation does not apply.

Example:

```json
{
  "value": "spice",
  "state": "absent"
}
```

`absent` MUST NOT be inferred merely because an annotation is missing from a
representation.

### `unknown`

The source does not provide enough information to determine whether the
annotation is present or absent.

Example:

```json
{
  "value": "woody&mossy",
  "state": "unknown"
}
```

An implementation MUST NOT interpret `unknown` as `absent`.

---

## Missing annotation versus unknown annotation

The distinction between an omitted annotation and an annotation explicitly
marked `unknown` requires careful treatment.

For example:

```json
{
  "annotations": [
    {
      "value": "floral",
      "state": "present"
    }
  ]
}
```

does not necessarily mean:

```text
spice = absent
woody = absent
fruity = absent
...
```

It means only that the representation contains a positive `floral`
annotation.

Similarly, an explicit:

```json
{
  "value": "spice",
  "state": "unknown"
}
```

means that the source carried an unresolved state for `spice`.

This distinction is necessary for lossless dataset conversion.

---

## Dataset-specific vocabularies

OpenSmell MUST NOT assume that all semantic annotation sources use the same
vocabulary.

For example, one dataset may use:

```text
floral
green
woody
```

while another may use a different taxonomy.

The semantic annotation scheme therefore transports annotation values without
declaring them universal OpenSmell categories.

A future extension MAY introduce explicit vocabulary identifiers.

For example:

```json
{
  "vocabulary": {
    "id": "org.example.odor-taxonomy",
    "version": "1.0"
  }
}
```

This is deliberately not part of the initial proposal.

---

## Relationship to semantic descriptors

The existing scheme:

```text
org.opensmell.semantic.descriptors
```

SHOULD remain available.

It is useful for simple positive descriptor lists and human-authored odor
descriptions.

The proposed:

```text
org.opensmell.semantic.annotations
```

addresses a different requirement: preserving explicit annotation state.

Conceptually:

```text
semantic.descriptors
        |
        +-- positive descriptive information

semantic.annotations
        |
        +-- present
        +-- absent
        +-- unknown
```

The annotation scheme is therefore not necessarily a replacement for the
descriptor scheme.

---

## Odorless

Experiments with OdorNet also exposed an important semantic distinction.

An explicit `odorless` annotation is not equivalent to the absence of positive
odor descriptors.

For example:

```text
odorless = present
```

is an explicit assertion.

By contrast:

```text
no positive annotations
```

may result from incomplete or unresolved data.

An implementation MUST NOT infer that an odor is odorless merely because no
positive descriptors are present.

This RFC does not yet decide whether `odorless` should ultimately remain a
semantic annotation or become a separate olfactory state in a future
OpenSmell model.

---

## Provenance

Annotation meaning depends strongly on its source.

For example:

```text
floral = present
```

may represent:

- a human sensory evaluation;
- a dataset annotation;
- a literature-derived label;
- a machine-learning prediction;
- a transformed value from another taxonomy.

Therefore provenance is expected to be important for semantic annotations.

Until provenance becomes normative, implementations MAY use the extension
mechanism described by RFC-0003.

Example:

```json
{
  "type": "semantic",
  "scheme": {
    "id": "org.opensmell.semantic.annotations",
    "version": "0.1"
  },
  "data": {
    "annotations": [
      {
        "value": "floral",
        "language": "en",
        "state": "present"
      }
    ]
  },
  "provenance": {
    "source": "OdorNet"
  }
}
```

---

## Confidence

This RFC deliberately does not introduce a `confidence` field.

A value such as:

```json
{
  "confidence": 0.8
}
```

is ambiguous without defining what the number represents.

It could represent:

- model probability;
- annotator agreement;
- measurement confidence;
- normalized source score;
- classification probability.

These quantities are not necessarily comparable.

Confidence SHOULD therefore be addressed separately if concrete
interoperability requirements justify it.

---

## Mapping OdorNet

A lossless semantic mapping from the observed OdorNet category values can use:

```text
1 / 1.0  -> present
0 / 0.0  -> absent
missing  -> unknown
```

Example:

```text
OdorNet

floral = 1
spice = 0
woody&mossy = blank

            |
            v

OpenSmell semantic.annotations

floral       -> present
spice        -> absent
woody&mossy  -> unknown
```

This mapping is adapter-specific.

The OpenSmell semantic annotation scheme itself MUST NOT depend on OdorNet.

---

## Backward compatibility

This proposal does not modify the OpenSmell 0.1 document structure.

The representation can be transported as an unknown scheme by existing
OpenSmell implementations.

Therefore an OpenSmell 0.1 implementation should still be able to:

1. validate the core document structure;
2. preserve the representation;
3. serialize it again;
4. leave interpretation to implementations that understand the scheme.

This behavior is an intentional consequence of the OpenSmell extension model.

---

## Security and validation considerations

Implementations SHOULD treat annotation values as untrusted text.

Validators SHOULD enforce structural requirements without attempting to
determine whether an annotation is scientifically correct.

A future validator for this scheme would likely verify:

- `annotations` is an array;
- the array is not empty;
- every annotation contains a non-empty `value`;
- every annotation contains a recognized `state`;
- `language`, when present, is a non-empty string;
- state values conform to the scheme version.

---

## Open questions

Before this RFC can become normative, the following questions require further
investigation.

### 1. Is `unknown` sufficiently precise?

Real datasets may distinguish:

```text
unknown
not measured
not annotated
not applicable
uncertain
```

It is not yet clear whether these should be separate normative states.

### 2. Should vocabularies have identifiers?

Dataset-specific descriptors may require a machine-readable vocabulary
identifier to avoid semantic collisions.

### 3. Should `odorless` be a descriptor?

`odorless` may represent an olfactory state rather than a semantic descriptor.

This requires additional investigation.

### 4. Should annotations support confidence?

Confidence may be useful for machine-learning outputs but requires explicit
semantics.

### 5. Should provenance exist per representation or per annotation?

A representation may combine annotations derived from multiple sources.

RFC-0003 currently explores representation-level provenance, but value-level
provenance may eventually be necessary.

### 6. Should negative annotations always be transported?

Large vocabularies could make explicit negative annotations expensive.

For a vocabulary containing thousands of descriptors, serializing every
negative value may be undesirable.

The relationship between vocabulary completeness and omission semantics must
therefore be investigated.

## Experimental validation

The proposed semantic annotation model was evaluated against the OdorNet
dataset using the experimental OpenSmell OdorNet adapter.

The validation dataset contained:

```text
OdorNet records:        8,892
Categories per record:     12
Annotation states:     106,704
```

Each OdorNet category value was mapped as follows:

```text
1 / 1.0  -> present
0 / 0.0  -> absent
missing  -> unknown
```

For every record, the validation pipeline performed the following operations:

```text
OdorNet CSV record
        |
        v
OpenSmell OdorNet adapter
        |
        v
RFC-0004 semantic annotation representation
        |
        v
OpenSmell serialization
        |
        v
.osmell document
        |
        v
OpenSmell parser
        |
        v
Recovered semantic annotations
        |
        v
Comparison with original OdorNet values
```

The validation result was:

```text
Molecules:   8,892
Annotations: 106,704
Expected:    106,704
Mismatches:  0
```

All 106,704 annotation states survived the OpenSmell serialization and
parsing round trip without information loss.

This experiment demonstrates that the proposed `present`, `absent`, and
`unknown` state model is sufficient to represent the annotation states
observed in the tested OdorNet dataset.

The experiment also exercises the OpenSmell serialization and parsing path,
rather than testing only the adapter-level transformation.

This result does **not** demonstrate that these three states are sufficient
for all olfactory datasets, sensory studies, prediction systems, or future
digital olfaction applications.

It also does not establish the scientific correctness of the OdorNet
annotations themselves. The experiment tests preservation of source
information through the OpenSmell representation.

Additional independent datasets and representation systems should therefore
be evaluated before this scheme becomes normative.

## Implementation plan

This RFC should initially remain experimental.

Proposed development sequence:

```text
1. Define semantic annotation semantics
              |
              v
2. Test mapping against OdorNet
              |
              v
3. Identify ambiguous states
              |
              v
4. Implement experimental scheme validator
              |
              v
5. Implement adapter support
              |
              v
6. Test lossless round trips
              |
              v
7. Evaluate additional datasets/models
              |
              v
8. Decide whether the scheme belongs in OpenSmell 0.2
```

Steps 1, 2, 5, and 6 have now been experimentally exercised with OdorNet.

The OpenSmell Core specification SHOULD NOT be modified until this experiment
demonstrates that the proposed abstraction generalizes beyond a single
dataset.

---

## Conclusion

Real olfactory datasets demonstrate that semantic odor information is not
always equivalent to a list of positive descriptors.

A useful interoperability format must be able to distinguish at least:

```text
present
absent
unknown
```

without confusing missing information with negative information.

The OdorNet experiment demonstrates that these states can preserve all
106,704 tested annotation values through an OpenSmell serialization and
parsing round trip without information loss.

This RFC therefore provides an experimentally supported candidate semantic
annotation model while preserving OpenSmell's core principles:

- device independence;
- source independence;
- extensibility;
- forward compatibility;
- preservation of information.

Further validation against independent olfactory data sources is required
before the model should become normative.
