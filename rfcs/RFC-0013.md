# RFC-0013: Multi-Source and Multi-Mapper Interoperability

- Status: Draft
- Category: Experimental Architecture
- Version: 0.1
- Date: 2026-09-09
- Depends on: RFC-0004, RFC-0005, RFC-0006, RFC-0007, RFC-0008, RFC-0009, RFC-0010, RFC-0011, RFC-0012
- Modifies OpenSmell Core 0.1: No

## 1. Summary

This RFC documents an experimental OpenSmell interoperability pattern in which
multiple independent data sources can describe different aspects of a shared
scientific subject without requiring their semantics to be merged.

The same heterogeneous GenericResourceGraph may contain, for example:

```text
Molecule
  |
  +-- Annotation
  |
  +-- Stimulus -> ObservationTarget -> Observation
```

where the branches originate from different datasets and retain different
interpretation contracts.

The experiment also demonstrates that materially different mapping policies can
consume different resource types and converge on the same device-facing
RenderingPlan abstraction:

```text
Annotation  -> SemanticChannelMapper   -> RenderingPlan
Observation -> PerceptualChannelMapper -> RenderingPlan
```

The common RenderingPlan boundary permits both policies to participate in the
same rendering pipeline and target the same DeviceAdapter architecture without
making their source semantics equivalent.

The central principle of this RFC is:

> Shared identity permits resources to be connected. It does not make their
> semantics, measurements, provenance, or physical rendering meaning
> equivalent.

This RFC is experimental and non-normative.

---

## 2. Motivation

OpenSmell experiments now transport several distinct kinds of olfactory
information.

RFC-0004 explores categorical semantic annotations.

RFC-0005 explores quantitative perceptual measurements.

RFC-0007 explores Stimulus, ObservationTarget, and Observation resources.

RFC-0008 explores a heterogeneous GenericResourceGraph.

RFC-0009 separates Molecule identity from other olfactory information.

RFC-0010 permits scheme-defined Annotation resources to refer to another
resource.

RFC-0011 permits explicit structural graph relationships to be discovered
without scanning opaque payloads.

RFC-0012 separates OpenSmell information from mapping policy, RenderingPlan,
device capabilities, adapters, protocol, transport, and physical reproduction.

These pieces make a new interoperability question concrete:

> What happens when two independent datasets describe the same chemical entity
> using different scientific semantics, and different mapping policies consume
> those descriptions through the same rendering architecture?

A naive integration could flatten all available information into one object or
translate labels from one dataset into measurements from another.

That would destroy important distinctions.

For example:

```text
green&herbal = present
```

is not the same assertion as:

```text
GRASS = 86 on a 0..100 measurement scale
```

The former may be a categorical dataset annotation.

The latter may be a quantitative result associated with a particular stimulus,
subject, dilution, and experimental record.

OpenSmell therefore needs to demonstrate interoperability without semantic
collapse.

---

## 3. Scope

This RFC describes the experimental architecture and evidence for:

- heterogeneous multi-source graphs;
- explicit cross-dataset identity linking;
- preservation of source-specific semantics;
- preservation of source-specific provenance;
- independent Annotation and Observation branches;
- a structural RenderingMapper contract;
- materially different semantic and perceptual mapping policies;
- convergence on RenderingPlan rather than convergence of source semantics;
- use of the same device-facing architecture by different mapping policies;
- the current multi-source (-)-beta-pinene reference experiment.

This RFC does not define a new OpenSmell Core representation.

It does not define a universal dataset merge algorithm.

It does not define a universal chemical-equivalence algorithm.

It does not define a universal relationship between semantic descriptors and
perceptual measurements.

It does not claim physical odor reproduction.

---

## 4. Terminology

### 4.1 Source

A Source is an independently produced dataset, publication, experiment,
repository, or other origin from which information is derived.

Two resources contained in the same OpenSmell graph may originate from
different Sources.

### 4.2 Source record

A Source record is the source-local record from which an OpenSmell resource or
assertion was derived.

Source-record identity is provenance information.

It is distinct from cross-dataset entity identity.

### 4.3 Shared identity

Shared identity is evidence used by an integration process to determine that
resources from independent sources concern the same entity for the purpose of
that integration.

The current reference experiment uses an exact PubChem InChIKey match as its
cross-dataset identity evidence.

This RFC does not generalize that rule into a universal OpenSmell chemical
identity algorithm.

### 4.4 Semantic equivalence

Semantic equivalence would mean that two assertions have the same meaning under
their interpretation contracts.

Shared identity does not establish semantic equivalence.

### 4.5 Mapping policy

A Mapping policy is application or device configuration that interprets
OpenSmell information and produces a RenderingPlan.

A mapping policy is not automatically part of the scientific meaning of the
source data.

### 4.6 Multi-source graph

A Multi-source graph is a GenericResourceGraph containing resources derived
from more than one independent Source.

### 4.7 Multi-mapper interoperability

Multi-mapper interoperability is the ability of materially different mapping
policies to participate in a common rendering architecture while preserving
their different interpretation rules.

It does not mean that those mapping policies are semantically equivalent.

## 5. Architectural Principle

The experimental architecture is:

```text
                     shared identity evidence
                              |
                              v
                          Molecule
                         /        \
                        /          \
               Annotation         Stimulus
                  |                  |
                  |                  v
                  |          ObservationTarget
                  |                  |
                  |                  v
                  |             Observation
                  |                  |
                  v                  v
        SemanticChannelMapper   PerceptualChannelMapper
                  |                  |
                  v                  v
            RenderingPlan        RenderingPlan
                   \                /
                    \              /
                     v            v
                      DeviceAdapter
                           |
                           v
                    target device
```

The diagram does not imply that every Multi-source graph must have this exact
shape.

It documents the current implemented reference experiment.

The important separation is:

```text
source integration
    !=
semantic interpretation
    !=
mapping policy
    !=
device execution
    !=
physical odor reproduction
```

## 6. Multi-Source Graphs

RFC-0008 permits heterogeneous resources to coexist in one
GenericResourceGraph.

RFC-0013 uses that property to preserve independent source branches rather than
flattening them.

A graph may therefore contain:

```text
Molecule
Annotation
Stimulus
ObservationTarget
Observation
```

without requiring all five resources to originate from one dataset.

The graph container does not make their payloads semantically interchangeable.

The Resource Type and Scheme contracts remain responsible for interpretation.

Unknown resources and unknown future Resource Type Versions retain the
transport behavior established by RFC-0008.

---

## 7. Dataset Independence

An OpenSmell integration SHOULD preserve distinctions that exist in the source
data.

A source classification SHOULD NOT be converted into an Observation merely to
make it resemble another dataset.

A quantitative experimental Observation SHOULD NOT be flattened into a
categorical Annotation merely to make two branches look uniform.

The reference experiment therefore represents:

```text
OdorNet categorical information
    -> Annotation
```

and:

```text
Keller/Vosshall psychophysical information
    -> Stimulus
    -> ObservationTarget
    -> Observation
```

The difference is intentional.

The source semantics determine the resource model used by the integration.

---

## 8. Cross-Dataset Chemical Identity

The current (-)-beta-pinene experiment links the independent source branches
only after an exact PubChem InChIKey identity match.

The reference identity value is:

```text
WTARULDDTDQWMU-IUCAKERBSA-N
```

The integration records this match separately from scientific provenance.

Conceptually:

```text
OdorNet source record
        |
        +----\
              \
               exact identity evidence -> Molecule
              /
        +----/
        |
Keller/Vosshall source record
```

This evidence is sufficient for the current experiment to connect the source
branches to one Molecule resource.

It does not establish a general chemical-equivalence rule for OpenSmell.

Different applications may require different identity evidence, normalization,
stereochemical treatment, confidence rules, or authority sources.

Those questions remain outside this RFC.

---

## 9. Identity Is Not Semantic Equivalence

This distinction is fundamental.

The current experiment contains information such as:

```text
OdorNet:
green&herbal = present
```

and:

```text
Keller/Vosshall:
GRASS = 86
scale = 0..100
```

These values concern a shared chemical identity in the reference integration.

They are nevertheless different assertions.

OpenSmell MUST NOT infer:

```text
green&herbal == GRASS
```

as a universal semantic equivalence.

Likewise:

```text
floral == FLOWER
woody&mossy == WOOD
```

are not universal equivalence rules established by this RFC.

An application MAY deliberately configure a demonstration mapping policy that
uses such fields in related ways.

That configuration remains application policy.

It does not rewrite the scientific semantics of either source.

## 10. Annotation Branch

The current OdorNet integration uses:

```text
org.opensmell.annotation
```

with Scheme:

```text
org.opensmell.semantic.annotations / 0.1
```

The source states are preserved as categorical values such as:

```text
present
absent
unknown
```

The reference mapper only uses configured descriptors whose state is
`present`.

This does not convert categorical presence into perceptual intensity.

In particular, an OdorNet source value indicating category presence MUST NOT be
described as an intensity measurement.

---

## 11. Observation Branch

The current Keller/Vosshall integration represents psychophysical data through
Observation resources.

The quantitative result Scheme is:

```text
org.opensmell.perceptual.measurements / 0.1
```

Measurements carry an explicit numeric scale.

For example:

```json
{
  "property": "grass",
  "value": 86,
  "scale": {
    "min": 0,
    "max": 100
  }
}
```

The meaning of this result remains attached to its Observation context and
source record.

The existence of a numeric value does not make it a universal physical
concentration or universal rendering intensity.

---

## 12. Provenance Separation

Scientific provenance and cross-dataset identity serve different purposes.

The experimental provenance model separates:

```text
source
record
derivation
```

For the OdorNet branch, the current integration records the source as OdorNet
and identifies the source record using its source SMILES.

For the Keller/Vosshall branch, the current reference fixture records the
source as Keller/Vosshall and identifies the source record using:

```text
source_row = 46426
```

The exact InChIKey used to link the datasets is not inserted into the Keller
source-record identity.

Instead, identity-match evidence remains integration metadata.

Therefore:

```text
provenance
    = where this assertion/resource came from

identity evidence
    = why the integration connected source branches
```

These concepts MUST NOT be conflated.

---

## 13. RenderingMapper

Implementation experience now includes a structural mapping contract:

```text
map(
    GenericResourceGraph,
    RenderRequest
) -> RenderingPlan
```

The current Python reference implementation expresses this contract as
`RenderingMapper`.

The contract deliberately does not prescribe:

- semantic annotation rules;
- perceptual measurement rules;
- dataset-specific rules;
- universal channel meanings;
- physical odor reproduction.

A mapper interprets only the information required by its own policy.

This addresses the earlier RFC-0012 question of what common Mapper contract
emerges after implementation of materially different mappers.

The current evidence supports a minimal structural contract centered on
producing a RenderingPlan from a graph and RenderRequest.

This RFC does not promote that contract into OpenSmell Core.

---

## 14. SemanticChannelMapper

The experimental SemanticChannelMapper consumes semantic Annotation resources.

Its current behavior is conceptually:

```text
requested subject resource
        |
        v
ReferenceIndex
        |
        v
incoming Annotation resources
        |
        v
org.opensmell.semantic.annotations / 0.1
        |
        v
state == present
        |
        v
configured descriptor binding
        |
        v
DeviceCommand
```

Configured bindings contain:

```text
descriptor
channel
intensity
```

The configured intensity is mapping policy.

It is not derived from an OdorNet presence value.

`absent`, `unknown`, malformed, and unconfigured annotation entries do not
produce commands.

The mapper may perform an early configuration-level compatibility check against
DeviceCapabilities.

Concrete RenderingPlan validation remains required afterward.

---

## 15. PerceptualChannelMapper

The experimental PerceptualChannelMapper consumes an Observation resource.

It interprets only results using:

```text
org.opensmell.perceptual.measurements / 0.1
```

Configured bindings contain:

```text
property
channel
```

Unlike SemanticChannelMapper, command intensity is data-derived.

For each usable measurement:

```text
normalized =
    (value - scale.min)
    /
    (scale.max - scale.min)
```

The mapper therefore does not assume that the source scale is always 0..100.

The current mapper does not know about Keller/Vosshall as a dataset.

It consumes the OpenSmell measurement contract.

This is important interoperability evidence: the mapping implementation is
coupled to an explicit OpenSmell Scheme, not to the filename or source dataset
that happened to produce the Observation.

---

## 16. Materially Different Mapping Policies

The two current mappers are not merely two configurations of one algorithm.

SemanticChannelMapper:

- consumes Annotation resources related to a requested subject;
- interprets categorical semantic states;
- uses configured command intensity;
- can inspect configured bindings against DeviceCapabilities before mapping.

PerceptualChannelMapper:

- requires the requested resource itself to be an Observation;
- interprets quantitative measurements;
- derives command intensity from each measurement's explicit scale;
- does not require a configuration-level support hook because relevant
  intensity is data-derived.

Both nevertheless satisfy the same structural RenderingMapper contract.

This provides implementation evidence for a common mapper boundary without
requiring a common scientific interpretation algorithm.

---

## 17. RenderingPlan Convergence

The source branches converge at the RenderingPlan boundary, not at the
scientific-data boundary.

Conceptually:

```text
categorical semantic information
        |
        v
semantic mapping policy
        |
        v
RenderingPlan
```

and:

```text
quantitative perceptual information
        |
        v
perceptual mapping policy
        |
        v
RenderingPlan
```

A RenderingPlan contains device-facing commands and duration.

Once a valid plan has been produced, the DeviceAdapter does not need to know
whether those commands originated from:

- OdorNet;
- Keller/Vosshall;
- an Annotation;
- an Observation;
- a semantic mapper;
- a perceptual mapper.

That separation is the principal multi-mapper interoperability result.

---

## 18. Common Rendering Pipeline

The experimental high-level pipeline accepts a mapper satisfying the
RenderingMapper structural contract.

Its operation is:

```text
validate graph/request/mapper/adapter
        |
        v
optional mapper-level capability check
        |
        v
mapper.map(...)
        |
        v
RenderingPlan
        |
        v
concrete DeviceCapabilities validation
        |
        v
DeviceAdapter.render(...)
```

The optional mapper-level compatibility hook does not replace concrete plan
validation.

This distinction matters because some constraints are request-specific or
data-derived.

The pipeline therefore permits different mapping strategies without weakening
the technical validation boundary.

---

## 19. Device Independence

Multi-mapper interoperability does not assign universal meaning to a device
channel.

For example:

```text
channel 1
```

does not universally mean:

```text
green&herbal
```

or:

```text
GRASS
```

or any molecule, cartridge, physical concentration, or odor.

Any such association belongs to mapping configuration, a device profile, or
another explicit hardware-specific layer.

The same OpenSmell information may legitimately produce different
RenderingPlans for different devices.

Likewise, different source semantics may produce different plans for the same
device.

The current reference record preserves all twelve OdorNet semantic states.

Selected values useful to the demonstration include:


The OpenSmell integration preserves those categorical states.

It does not transform:

```text

```

into a measured numeric intensity.

A SemanticChannelMapper demonstration may configure, for example, positive
descriptors to device channels and command intensities.

Those intensities belong to the demonstration mapping configuration.

They are not OdorNet measurements.

## 23. Demonstration Mapping Policy

The current reference demonstration deliberately uses related-looking
semantic and perceptual fields to make the two mapping paths observable.

For example, a demonstration may configure relationships such as:

```text
floral       <-> flower
green&herbal <-> grass
woody&mossy  <-> wood
```

This is demonstration policy only.

RFC-0013 does not define those pairs as ontology mappings.

It does not assert that the terms are scientifically interchangeable.

It does not assert that a categorical source state and a psychophysical
measurement encode the same phenomenon.

The demonstration asks a narrower engineering question:

> Can different explicitly configured interpretations of heterogeneous
> OpenSmell information produce technically valid plans through one common
> rendering architecture?

The current experiment answers that question affirmatively for the tested
software and prototype device path.

## 24. Multi-Mapper Reference Results

For the current (-)-beta-pinene demonstration, the semantic mapping path
produced the following commands:

```text
channel 1 -> 0.6
channel 2 -> 1.0
```

The perceptual mapping path produced the following commands:

```text
channel 0 -> 0.01
channel 1 -> 0.86
channel 2 -> 0.97
```

The plans are intentionally different.

That difference is not an interoperability failure.

It follows from the fact that the mappers consume different source semantics
under different mapping policies.

Interoperability occurs because both outputs satisfy the same RenderingPlan and
device-facing architecture.

## 27. Physical ESP32 Control Validation

The current rendering/device architecture has also been exercised against a
physical three-channel ESP32 LED prototype.

The prototype is a control-path stand-in.

It permits the project to observe whether a RenderingPlan reaches distinct
physical outputs through:

```text
RenderingPlan
    ->
DeviceAdapter
    ->
Device Protocol 0.1
    ->
SerialDeviceTransport
    ->
ESP32
    ->
physical channels
```

Both the semantic and perceptual (-)-beta-pinene demonstration paths have been
exercised through the current multi-channel control prototype.

This validates the tested software-to-device control path.

It does not validate:

- odor synthesis;
- molecule release;
- chemical concentration;
- olfactory perception;
- perceptual equivalence;
- physical reproduction of (-)-beta-pinene;
- physical reproduction of the OdorNet annotations;
- physical reproduction of the Keller/Vosshall measurements.

The LED channels are observable actuators, not odor generators.

## 28. What the Experiment Demonstrates

The current evidence supports the following claims.

### 28.1 Heterogeneous representation

OpenSmell can transport categorical annotation information and quantitative
Observation information in one heterogeneous graph without forcing both into
one resource model.

### 28.2 Explicit identity integration

Independent source branches can be connected through explicit identity
evidence while preserving their own provenance.

### 28.3 Semantic preservation

The integration can preserve different interpretation contracts instead of
flattening them into a common pseudo-measurement.

### 28.4 Multiple mapping strategies

Materially different mappers can interpret different OpenSmell resource types
and satisfy a common structural RenderingMapper contract.

### 28.5 Common execution boundary

Different mappers can produce RenderingPlans accepted by the same
device-facing architecture.

### 28.6 Physical control path

The resulting plans can reach a tested physical multi-channel control endpoint.

These are interoperability and architecture results.

They are not odor-reproduction results.

---

## 29. What the Experiment Does Not Demonstrate

The experiment does not demonstrate that:

- OdorNet and Keller/Vosshall measure the same thing;
- `green&herbal` is universally equivalent to `GRASS`;
- `floral` is universally equivalent to `FLOWER`;
- `woody&mossy` is universally equivalent to `WOOD`;
- an OdorNet `present` state has a numeric perceptual magnitude;
- Keller/Vosshall 0..100 values are physical concentrations;
- normalized mapper output is a physical concentration;
- two RenderingPlans are perceptually equivalent;
- two devices produce perceptually equivalent stimuli;
- the ESP32 LEDs reproduce an odor;
- OpenSmell defines universal olfactory primaries;
- an InChIKey match alone solves every chemical identity problem;
- the demonstrated mapping bindings should be standardized.

Any presentation, publication, or demonstration based on this RFC SHOULD keep
these limitations explicit.

## 39. Provenance Requirements for Multi-Source Experiments

A multi-source integration SHOULD make it possible to distinguish:

1. the source from which information originated;
2. the source-local record used;
3. the derivation that created the OpenSmell assertion or resource;
4. the independent evidence used to connect sources.

The current experimental structured provenance model represents the first
three concerns as:

```text
source
record
derivation
```

Cross-source identity evidence remains separate.

An implementation SHOULD NOT silently replace source identity with an enriched
external identity.

For example, resolving a PubChem InChIKey for an OdorNet record does not make
PubChem the provenance source of the original OdorNet semantic assertion.

---

## 40. Forward Compatibility

RFC-0013 introduces no new serialized Resource Type.

Existing RFC-0008 forward-compatibility behavior therefore remains applicable.

A future mapper may interpret a new Resource Type or Scheme without requiring
all existing mappers to understand it.

Likewise, the RenderingMapper structural contract should remain independent of
specific dataset names.

New mapping policies SHOULD be introduced only when a concrete interoperability
use case justifies them.

A future mapper SHOULD NOT require changes to unrelated source resources merely
to participate in the rendering pipeline.

---

## 41. Security, Robustness, and Scientific Integrity

Multi-source integration introduces both software and scientific risks.

Implementations should consider:

- malformed or untrusted source data;
- non-finite numeric values;
- unsupported or unknown Schemes;
- unresolved structural references;
- ambiguous chemical identity;
- accidental merging of stereochemical variants;
- duplicate source records;
- stale enrichment caches;
- incorrect source-row provenance;
- mapping configurations that target unsupported channels;
- physical-device safety constraints.

Scientific integrity additionally requires that integrations not silently
upgrade evidence.

Examples of prohibited inference at this architectural layer include:

```text
shared identity -> semantic equivalence
```

```text
categorical presence -> quantitative intensity
```

```text
normalized command -> physical concentration
```

```text
successful device command -> successful odor reproduction
```

Technical validation and scientific interpretation remain separate
responsibilities.

---

## 42. Portable Interoperability Strategy

A useful portable validation strategy for multi-source experiments should
include:

1. a stable serialized heterogeneous fixture;
2. unique Resource IDs;
3. preservation of all source-specific resource types;
4. preservation of source-specific Scheme data;
5. explicit cross-source identity evidence;
6. structural-reference resolution checks;
7. provenance preservation checks;
8. independent implementation verification where practical;
9. strict JSON behavior;
10. mapper-specific tests;
11. common rendering-pipeline tests;
12. device-facing validation independent of source dataset names.

Portable tests SHOULD verify structural and semantic preservation only for
contracts they explicitly understand.

They SHOULD NOT infer relationships from arbitrary opaque JSON fields.

## 44. Open Questions

The experiment intentionally leaves several questions unresolved:

1. Should RenderingMapper eventually become a public non-experimental
   interface?
2. Is `map(graph, request) -> RenderingPlan` sufficient for additional
   materially different mapping strategies?
3. Should mapper capability inspection acquire a formal structural contract,
   or remain optional?
4. How should applications declare which Resource Types and Schemes a mapper
   understands?
5. Should mapping policies themselves have portable identifiers and versions?
6. Should mapping configuration have a standardized serialized form?
7. How should confidence in cross-dataset identity evidence be represented?
8. Should chemical identity matching become a separate explicit integration
   resource or relationship?
9. How should conflicting independent annotations be represented without
   collapsing provenance?
10. How should repeated observations of one stimulus be selected or aggregated
    by mapping policy?
11. Should a RenderingPlan record a stronger machine-readable derivation trail
    from source resources?
12. Which additional independent datasets should be used to test multi-source
    interoperability?
13. Which additional mapper families would provide useful pressure on the
    RenderingMapper contract?
14. What interoperability requirements emerge when real olfactory actuators
    replace observable LED stand-ins?
15. Which parts of this experiment, if any, should eventually be proposed for a
    future OpenSmell version?

These questions should be answered from implementation and interoperability
evidence rather than API symmetry or speculation.

## 45. Current Recommendation

Keep the multi-source and multi-mapper architecture experimental.

Retain the current separation between:

```text
identity
provenance
semantics
measurement
mapping
rendering
device execution
physical reproduction
```

Treat the current (-)-beta-pinene graph as a reference interoperability
experiment rather than a universal odor model.

Retain both SemanticChannelMapper and PerceptualChannelMapper as explicit
mapping policies.

Retain RenderingPlan as the common device-facing convergence point.

Do not standardize the demonstration descriptor/property correspondences.

Do not promote RenderingMapper into Core solely because two implementations now
exist.

Instead, use additional independent datasets, mapper families, and physical
endpoints to determine whether the current structural contract remains stable.

---

## 46. Conclusion

The multi-source experiment demonstrates that interoperability does not require
semantic flattening.

Independent sources can remain scientifically distinct while participating in
one connected OpenSmell graph:

```text
source A ----\
              \
               shared identity
              /
source B ----/
```

Different information types can then be interpreted by different explicit
mapping policies:

```text
Annotation  -> SemanticChannelMapper
Observation -> PerceptualChannelMapper
```

and converge only at the device-facing execution abstraction:

```text
RenderingPlan
```

This separation is the key result.

OpenSmell can experimentally connect heterogeneous olfactory information,
preserve source-specific semantics and provenance, and route materially
different interpretations through a common device architecture without
claiming that the underlying datasets mean the same thing or that the target
physically reproduces the represented odor.

RFC-0013 therefore records multi-source and multi-mapper interoperability as an
experimental architectural capability and a basis for further implementation,
scientific validation, and interoperability work.
