# RFC-0015: Offline Planning Profiles and Artifacts

Status: Draft — experimental, non-normative

## Motivation

An external developer should be able to take an existing generic ResourceGraph,
choose a mapping policy and obtain a checked plan from the installed package,
without Local Explorer or a device connection. The existing SDK already separates
representation, mapping, capabilities and execution (RFC-0012/0013). This proposal
adds a portable application configuration and a passive output envelope to that
workflow. It does not modify Core 0.1 or Device Protocol 0.1.

## Mapping profile 0.1

The JSON object has `format: org.opensmell.experimental.mapping-profile`,
`version: 0.1`, `mapper`, a non-empty `bindings` array, and `capabilities`.
The supported mapper names are `semantic` and `perceptual`:

- Semantic binding: `descriptor`, `channel`, `intensity`, consumed by the existing
  `SemanticChannelMapper`. Only positive supported annotations contribute.
- Perceptual binding: `property`, `channel`, consumed by the existing
  `PerceptualChannelMapper`. Intensity follows the explicit measurement scale.

Binding names/types and duplicate rules are checked by the existing binding and
mapper constructors. Unknown binding fields are rejected. Unknown top-level
profile extensions may be carried through but cannot affect mapping.
`capabilities` uses the existing Device Protocol 0.1 `capabilities` response
shape: protocol version, type, device ID, channel ranges and duration bounds.
These values are supplied configuration, not discovered device telemetry.
The included example profiles assign no universal meaning to channels.

## Planning

The caller explicitly selects a resource ID and positive finite duration.
`plan_with_profile(graph, request, profile)` creates the specified mapper, runs
its support check when available, maps the request and validates the concrete
plan against capabilities. A plan with no commands is rejected at this entry
point, rather than being reported as a useful device action. Existing mappers'
standalone behavior is unchanged.

The installed `opensmell plan` entry point accepts generic ResourceGraph 0.1;
automatic Core conversion and dataset import are outside this first contract.
It requires no application code, transport, adapter or network operation.

## Offline artifact 0.1

Successful CLI output has `format: org.opensmell.experimental.offline-plan`,
`version: 0.1`, `status: planned`, `execution: not_attempted`, and
`capability_basis: supplied_profile_not_live_device`. It carries:

- source/profile parsed documents, including opaque extensions and provenance;
- SHA-256 hashes of the original source/profile bytes, not of reserialized JSON;
- the explicit request and computed plan (duration, channel/intensity commands,
  and existing mapper metadata);
- structural validation warnings and the limits of the result.

Source snapshots preserve parsed JSON values, not whitespace or numeric lexical
spellings. Duplicate members and non-finite values are rejected by the CLI's
strict text boundary. Hashes are content identifiers, not signatures. Provenance
is supplied evidence, not authenticated scientific truth. No timestamp/random
identity is added, so identical inputs/paths and options yield identical output.

The artifact is not a Device Protocol request, execution receipt, replay format
or interchange standard. It cannot establish hardware compatibility, odor
reproduction, cartridge composition or safe physical operation. The CLI has no
send/flash mode. Any future execution consumer must independently verify live
capabilities, identity, request freshness and user intent.

## Implementation evidence and open questions

The installed CLI and SDK use both existing mappers against the committed
diphenyl-ether graph. Tests check the two distinct expected command sets, retained
source/profile data, unknown contracts, duration/channel/intensity rejection and
installation outside the checkout. CI repeats the wheel smoke check across its
Python matrix. These are repository-owned software checks, not third-party or
physical validation.

Future work: explicit Core bridging/import without losing document-level
provenance, profile namespace/version governance, optional validation of known
scheme payloads, and an independently implemented reader of the output envelope.
Promotion beyond Draft requires further interoperability evidence.
