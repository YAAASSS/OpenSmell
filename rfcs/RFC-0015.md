# RFC-0015: Offline Planning Profiles and Artifacts

Status: Draft — experimental, non-normative

## Motivation

An external developer should be able to take an existing generic ResourceGraph,
choose a mapping policy and obtain a checked plan from the installed package,
without Local Explorer or a device connection. The existing SDK already separates
representation, mapping, capabilities and execution (RFC-0012/0013). This proposal
adds a portable application configuration and a passive output envelope to that
workflow. It does not modify Core 0.1 or Device Protocol 0.1.

## Mapping profile 0.1

The JSON object has `format: org.opensmell.experimental.mapping-profile`,
`version: 0.1`, `mapper`, a non-empty `bindings` array, and `capabilities`.
The supported mapper names are `semantic` and `perceptual`:

- Semantic binding: `descriptor`, `channel`, `intensity`, consumed by the existing
  `SemanticChannelMapper`. Only positive supported annotations contribute.
- Perceptual binding: `property`, `channel`, consumed by the existing
  `PerceptualChannelMapper`. Intensity follows the explicit measurement scale.

Binding names/types and duplicate rules are checked by the existing binding and
mapper constructors. Unknown binding fields are rejected. Unknown top-level
profile extensions may be carried through but cannot affect mapping.
`capabilities` uses the existing Device Protocol 0.1 `capabilities` response
shape: protocol version, type, device ID, channel ranges and duration bounds.
These values are supplied configuration, not discovered device telemetry.
The included example profiles assign no universal meaning to channels.

## Planning

The caller explicitly selects a resource ID and positive finite duration.
`plan_with_profile(graph, request, profile)` creates the specified mapper, runs
its support check when available, maps the request and validates the concrete
plan against capabilities. A plan with no commands is rejected at this entry
point, rather than being reported as a useful device action. Existing mappers'
standalone behavior is unchanged.

The installed `opensmell plan` entry point accepts generic ResourceGraph 0.1;
automatic Core conversion and dataset import are outside this first contract.
It requires no application code, transport, adapter or network operation.

## Offline artifact 0.1

Successful CLI output has `format: org.opensmell.experimental.offline-plan`,
`version: 0.1`, `status: planned`, `execution: not_attempted`, and
`capability_basis: supplied_profile_not_live_device`. It carries:

- source/profile parsed documents, including opaque extensions and provenance;
- SHA-256 hashes of the original source/profile bytes, not of reserialized JSON;
- the explicit request and computed plan (duration, channel/intensity commands,
  and existing mapper metadata);
- structural validation warnings and the limits of the result.

Source snapshots preserve parsed JSON values, not whitespace or numeric lexical
spellings. Duplicate members and non-finite values are rejected by the CLI's
strict text boundary. Hashes are content identifiers, not signatures. Provenance
is supplied evidence, not authenticated scientific truth. No timestamp/random
identity is added, so identical inputs/paths and options yield identical output.

The artifact is not a Device Protocol request, execution receipt, replay format
or interchange standard. It cannot establish hardware compatibility, odor
reproduction, cartridge composition or safe physical operation. The CLI has no
send/flash mode. Any future execution consumer must independently verify live
capabilities, identity, request freshness and user intent.

## Implementation evidence and open questions

The installed CLI and SDK use both existing mappers against the committed
diphenyl-ether graph. Tests check the two distinct expected command sets, retained
source/profile data, unknown contracts, duration/channel/intensity rejection and
installation outside the checkout. CI repeats the wheel smoke check across its
Python matrix. These are repository-owned software checks, not third-party or
physical validation.

Future work: explicit Core bridging/import without losing document-level
provenance, profile namespace/version governance, optional validation of known
scheme payloads, and an independently implemented reader of the output envelope.
Promotion beyond Draft requires further interoperability evidence.


## Experimental offline protocol-frame export

An application may consume an unexecuted offline-plan 0.1 artifact through
`encode_plan_frame` / `opensmell encode-frame`. It recomputes actionable mapping
from embedded source/profile/request, checks separate supplied target capabilities
and a framing byte bound, and returns a
`org.opensmell.experimental.protocol-frame-export` version `0.1` envelope.
`frame.line` is an existing Device Protocol 0.1 render message plus LF, with exact
line hash/count; no protocol field is added. Input and target byte snapshots retain
unknown extensions. Original source/profile hashes remain unverified declarations.
The export states transport not opened and acceptance/execution not observed.
It does not add live discovery, freshness guarantees, authenticated identity,
lifecycle/Stop support or physical compatibility. See the CLI guide for bounds.
This report envelope is experimental and non-normative; this RFC remains Draft.


## Native software replay observation envelope

An application may validate a frame-export artifact and observe an explicitly
chosen trusted native harness using `replay-frame`. The experimental report
identifier is `org.opensmell.experimental.native-frame-replay` version `0.1`.
It retains exact export bytes, the executable's observed file identity, ordered
request/reply lines, native capability comparison, selected-frame acceptance,
separately labeled negative control and fake PWM/clock samples. Unknown/failure
and acceptance are distinct: a known acceptance need not imply a completed trial.
It adds no protocol wire field, serial transport, authentication, lifecycle/Stop
or physical result. The report and this RFC remain experimental and non-normative.


## Experimental Core perceptual selection application policy

The opt-in `plan-core` consumer may interpret one explicitly indexed provisional
perceptual-measurements0.1 representation under the recognized profile extension
`org.opensmell.experimental.core-perceptual-policy`, version0.1. It requires
`normalization:value-minus-min-over-range` and `measurements` entries matching
all bound properties, with explicit expected numeric scales and exact unit
presence/value. Units are compared, never converted. Duplicate/missing bound
measurements refuse. Unknown fields remain passive; ordinary graph/semantic
mapping is unchanged. See the Core perceptual guide for complete examples.

Its reserved `org.opensmell.experimental.core-perceptual-selection` projection
retains exact source bytes/index and one opaque representation resource; it does
not invent a Stimulus or observed experiment. The normal planning/frame/sequence
boundaries recompute it from the source and validate the policy before commands
are actionable. This is an experimental application convention, not a Core wire
change, global scheme registration or promotion of RFC-0005/0015 beyond Draft.


## Experimental selected observation to Core export

An opt-in `export-observation-core` application entry selects one explicit
Observation/result index using provisional perceptual measurements0.1 and a
caller-owned Core odor ID. It copies selected scheme/data without conversion,
retains extra result fields in representation context, and embeds the exact
whole graph in `org.opensmell.experimental.observation-core-export`, version0.1.
The extension records selection and Base64/SHA-256/byte count; it does not infer
chemical/stimulus/participant identity or a new presentation.

Extraction and Core planning consumers recompute this reserved projection before
using it; contradictory edits refuse. Exact source recovery is not graph editing
or authentication. Unsupported/unmeasured results refuse without fallback.
Other Core sources and the chemical bridge are unchanged. See observation-core.md
for bounds and normal entries. This remains an experimental application convention;
Core/Device Protocol and Draft RFC-0005/0015 status are unchanged.

### Independent installed JavaScript Core inspection — 2026-11-26

The explicit `inspectCoreBytes`/installed `--core` entry now reads Core0.1
envelopes and the provisional perceptual0.1 quantitative fields. Real locally
packed CJS/ESM/CLI consumers outside checkout transfer exact bytes back to the
installed Python source-recovery/planning path. Numeric tokens, missing/null/zero
and opaque representations remain distinct. This is bounded partial inspection,
not full Python registry/schema conformance, scientific validation or a scheme
maturity change. Export-marker consistency stays with Python extraction/planning.
See [the runnable proof and limits](../docs/javascript-core.md). No physical
execution or measured olfactory result is established; this RFC remains Draft.

### Explicit per-trial profile dossier experiment

The opt-in trial-profiles0.1 bundle maps every trial ID to one explicit normal
mapping/capability profile. The compiler emits a prepared-experiment0.2 local
application dossier with exact bundle bytes and normal offline-plan0.1 artifacts.
The loader dispatches0.1/0.2 dossiers and recomputes all bindings before transport;
shared-profile behavior is unchanged. This is not a Core or device-wire version
change, automatic mapping selection or scientific completeness rule. See
[the installed entry and scope](../docs/trial-profiles.md). This RFC remains Draft.
